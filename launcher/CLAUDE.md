# Vibb One (the launcher) — Project Context for Claude Code

## What this is

An Android home screen for a kid's phone that is also, in the same process, the [Device Owner](https://developer.android.com/work/dpc/build-dpc) parental-control agent. Package (applicationId) `me.vibb.launcher` since 2026-10-06 (debug `me.vibb.launcher.debug`; was `com.kidslauncher.mdm`) - the Kotlin namespace and every class name stay `com.kidslauncher.mdm.*`, so components are `me.vibb.launcher/com.kidslauncher.mdm.…`. An installed `com.kidslauncher.mdm` build can't update into the renamed app (a different package is a different app; `pendingApkCheck` refuses it as NOT_OURS): such a phone is provisioned again. It speaks directly to kid-phone-server, which lives next to it in this monorepo (`../server/`, repo `palchrb/vibb-launcher`; see the root `CLAUDE.md` for the layout) - there is no other server, protocol, or MDM stack involved; an earlier prototype used something else entirely and has been fully retired.

Originated as a fork of Josia Pietsch's µLauncher, itself descended from Finn Glas's Launcher, but almost nothing of that lineage remains functionally: the gesture-binding system, Minimalist Mode (as an optional toggle), torch, private-space lock, and audio-track controls were all removed. What's still genuinely shared is the app-list screen (`ui/list/`, `apps/`) - see `LICENSE-MIT-UPSTREAM`. Don't describe this project as "a fork" in user-facing copy; it's its own thing now built on a small inherited component, not vice versa.

## Tech stack

Kotlin, single Gradle module (`app/`). `minSdk = 34`, `compileSdk`/`targetSdk = 36`. Retrofit + kotlinx.serialization (`JsonNamingStrategy.SnakeCase`, matching the server's plain snake_case JSON) for the device-facing API client in `server/`. `androidx.preference` for Settings, `eu.jonahbauer.android.preference.annotations` (kapt-generated) for the typed `LauncherPreferences` accessor API.

**One Java file**: `preferences/LauncherPreferences$Config.java` - not a choice made in this fork, Josia Pietsch wrote it in Java originally (Sept 2024). It's the annotation config kapt reads to generate the real `LauncherPreferences` class every `mdm.xxx()` call in the codebase goes through - keep editing it in Java when adding new preference entries rather than converting it, since deeply-nested annotation arrays through kapt's Kotlin→Java stub bridge is a real source of subtle bugs that writing it directly in Java sidesteps.

## Architecture

- **Device Owner is the whole point.** `MdmDeviceAdminReceiver` + `dpm.isDeviceOwnerApp()` gate every enforcement call in `server/AppEnforcer.kt` - it's a no-op if not device owner, so it's safe to ship before a phone is actually provisioned.
- **`server/MdmSyncWorker.kt`**'s `performMdmSync()` is the heartbeat: fetches policy, evaluates the lock decision, calls `AppEnforcer.apply()`, and reports status. Since handy step 7 every background trigger - an SSE nudge (the only kind since design 19), the `BackstopAlarm` (30 min), process start - goes through `push/SyncRunner` inside the anchor service (wake lock, timeouts, coalescing); the Settings "Sync now" button still calls it directly (it uses the `Boolean` return value - whether the server was actually reached - to show an honest success/failure toast). See "Push, battery and Play (handy step 7)" below.
- **`server/AppEnforcer.kt`** is the enforcement engine: suspends/hides packages not on the allowlist, engages/disengages lock-task kiosk mode (when an allowlist exists and `kioskDesired` is set), applies the `lockTaskFeatures` bitmask (always with `LOCK_TASK_FEATURE_KEYGUARD` forced on), and applies WiFi/Bluetooth `UserManager` restrictions. *What* to suspend and pin is decided by the pure `computeEnforcementPlan` (`server/EnforcementPlan.kt`, unit-tested); `apply()` only diffs that plan against the live state. `controllablePackages()` is the safety-critical bit - see gotchas below.
- **The parent PIN** (the offline override PIN, "unlock code", "Parent code"; design 24): PBKDF2-HMAC-SHA256 verified fully offline against a hash+salt cached from the last successful sync, **only** through `server/ParentPin.check` - with its escalating lockout and its events - see "Parent PIN hardening (design 24)" below. `OfflineOverride.activate()` (the "lift restrictions for 2 hours" side effect) is called only by that gate.
- **Settings is PIN-gated** (`ui/settings/SettingsActivity.kt`, pure `SettingsGate.kt`/`SettingsGateTest`): open only before the phone's first policy (setup: server URL, enroll, scan QR); afterwards it needs the parent PIN, and with no PIN on the server (or during a PIN lockout) it doesn't open at all - the gate's dialog then says why, OK disabled, Cancel finishes (handy step 4, QA #12; design 24). Checked on every `onCreate`/`onStart`, so the drawer, the exported `APPLICATION_PREFERENCES` filter, explicit intents, recents and a restore after process death all hit it; a passed gate ends in `onStop` (kept only across a configuration change via `onSaveInstanceState`), and recents screenshots are off. The gate is a non-cancelable modal dialog over the normally-inflated (but `INVISIBLE` until verified) content, not by deferring `binding` initialization, because `UIObjectActivity`'s `onStart()` unconditionally calls `setOnClicks()` which needs `binding` to already exist.
- **`restrictions_paused`** is a separate, manually-toggled kill-switch in Settings - an emergency escape hatch if a policy or launcher update ever ships something broken. In this fork (`server/RestrictionsPause.kt`, the only reader/writer of `restrictions_paused`/`restrictions_paused_until`): turning it on always asks for the parent PIN, and the gate (`ParentPin`) starts the pause (so it's unavailable while the server has no PIN configured - and since step 4 Settings doesn't even open then on a managed phone), it ends by itself after 2 hours by the wall clock *and* by `SystemClock.elapsedRealtime()`, and on any reboot (`Settings.Global.BOOT_COUNT` changes) - so setting the clock back can't stretch it (`timedWindowActive`, `BootClock`, initialised in `Application.onCreate`; the offline-override PIN window uses the same check). A window saved by an older build counts as expired, it doesn't end on sync, and every status report sends `restrictionsPaused` so the server shows it. Toggling it re-runs `AppEnforcer.apply()` and `reevaluateLockReasonFromCache()` immediately and offline, on a background coroutine (see the ANR note further down).
- **`LockActivity.kt`** is the full-screen time-rule / screen-time block (time, rule name, what still works - see "Time rules" below; since design 34 P6 one calm card, see "The time-rule screen as one calm card"), with a visible (not hidden-behind-a-gesture) "Enter unlock code" button - the PIN itself is the security boundary, not the button's obscurity - a "Phone book" row while calls are managed and allowed, and always "Emergency call". Since handy step 4 the lock is also **enforced by suspension**: see "Hardening (handy step 4)" below.
- **Silent self-update is unified with third-party app updates** - the launcher is just another row in kid-phone-server's `tracked_apps` table (in this fork: package `me.vibb.launcher` - migration 0037 renamed a row on the old name -, GitHub repo `palchrb/vibb-launcher` (the monorepo; the server's sync skips its `server-v*` releases), asset `kids-launcher-mdm.apk`, `include_prereleases` **off** so release candidates never reach phones - see `../server/DEPLOY.md`; upstream used the debug package from a rolling `pre-release` tag), going through the exact same `AppInstaller`/`AppInstallReceiver`/`checkForTrackedAppUpdates` path as everything else via Device Owner's `PackageInstaller` privilege - no launcher-specific update code exists anymore (the old `LauncherUpdater`/`LauncherUpdateInstallReceiver`/`launcher_releases` system was fully retired). The one place self-update still differs from a third-party install: `AppInstallReceiver` skips deleting its cache file on success when the install is the launcher's own self-update, since installing over yourself can kill/replace the process before that line gets to run. A release that already failed to install is cached per-app in `TrackedAppUpdateState` (`tracked_app_update_state` preference) so it isn't retried every 2 minutes forever - covers the launcher the same as any tracked app now.
- **`GET /api/devices/apps` is scoped per-device now** (2026-08-08, server-side `device_tracked_apps` join table - see kid-phone-server's CLAUDE.md) - a device only receives updates for apps an admin actually selected for it on that device's own page, plus the launcher's own self-update (always included). No client change was needed for the scoping itself; the server just stopped advertising apps this device wasn't given. What *did* need a client change: `TrackedAppUpdate.packageName` is optional server-side now (an admin can add an app to the catalog without typing its real Android package name), so `MdmSyncWorker`/`AppInstaller`/`AppInstallReceiver`/`TrackedAppUpdateState` no longer key install-state tracking, cache filenames, or the `PackageInstaller.openWrite()` session label off it - they use `TrackedAppUpdate.id` (the server's stable tracked-app id, stringified) instead. Self-update detection (deciding whether `AppInstallReceiver` should skip its cache-cleanup) switched the same way, from a `packageName == context.packageName` string comparison to the server-reported `TrackedAppUpdate.isLauncher` flag - more robust anyway, since it no longer depends on the launcher's own catalog row happening to have its package name typed in correctly. `packageName` is still sent and still shown in the admin UI for reference; it just isn't load-bearing for anything client-side anymore.
- **Background app installs/updates (including the launcher's own self-update) now show a notification** (`Notifications.kt`'s `notifyAppInstalling`/`notifyAppInstallResult`, channel `launcher:app_install`, LOW importance - visible but silent) - previously this "just happened" with zero on-device indication, reported as worth surfacing. `MdmSyncWorker.checkForTrackedAppUpdates` shows an ongoing "Installing X…" notification for the whole download+install span before it starts; `AppInstallReceiver` cancels it on success (disappearing is enough signal) or swaps it for a dismissible "Couldn't install X" on failure, keyed by `TrackedAppUpdate.id` so concurrent/queued installs in the same sync cycle don't clobber each other's notification. Needed a new `TrackedAppUpdate.name` field from the server (the admin-facing catalog name) since `packageName` can no longer be trusted to be present or meaningful for a notification title - see kid-phone-server's CLAUDE.md.
- **Since handy step 11 the launcher's own update is no longer installed in `checkForTrackedAppUpdates`**: it is only downloaded there (kept pending) and committed as the very last step of `performMdmSync`, in the night update window, behind the update fence - see "Kiosk escapes (handy step 11)" below. The history that follows still explains why nothing may run after that commit.
- **`checkForTrackedAppUpdates` always processes the launcher's own self-update last**, after every other queued app - reported live as "installing two apps at once breaks the sync." Root cause: the launcher is unconditionally in every device's update batch whenever a new build's been published (see `TrackedAppUpdate.isLauncher`, always included regardless of per-device app scoping), so a sync cycle with any other pending app install very often includes it too. `AppInstaller.installSilently`'s `session.commit()` for the launcher's own APK can get this process SIGKILLed the moment Android starts replacing it - and everything queued *after* that point in the same for-loop (another app's whole download+install, plus `reportBlockedDnsEvents` back in `performMdmSync`) would simply never execute this cycle. Reordering so the launcher goes last doesn't lose anything: a `PackageInstaller` session, once committed, is handled by the OS from that point on regardless of whether this process survives - every other app's install is safe to have already been kicked off first. **This reordering helped but wasn't the actual root cause** - see the `syncMutex` bullet below, found via live `adb logcat` after the user reported installs still silently failing.
- **`performMdmSync` is now wrapped in a `syncMutex` (`Mutex.withLock`)** - `CommandListenerService`'s periodic timer, its SSE push-nudge handler, and the Settings "Sync now" button each independently launched their own `performMdmSync` coroutine with zero coordination between them. Confirmed live via `adb logcat`: two overlapping calls processing the same pending tracked-app update (almost always the launcher's own self-update, present in every batch whenever a new build's published) raced on the shared per-app cache file (`tracked_app_{id}.apk`) - one call's `AppInstallReceiver` cleanup (delete on failure) could delete a file a second, still-in-flight call had just written, or corrupt it mid-write, producing exactly the `INSTALL_PARSE_FAILED_NO_CERTIFICATES` / `FileNotFoundException` failures seen in the log. `withLock` (not `tryLock`-and-skip) so a sync that lands while another's running queues and still completes rather than silently no-oping - occasionally redundant, never lossy. `checkForTrackedAppUpdates` also now writes each download to a `System.nanoTime()`-suffixed filename (unique per attempt, not just per app id) as defense in depth, so even a future caller that somehow bypasses the mutex can't have two downloads collide on the same path.
- **Unchecking "Apps to install" (today the app's switch on the phone's Apps page in the PWA) now silently uninstalls the app** (`AppInstaller.uninstallSilently`, `PackageInstaller.uninstall()` - same Device Owner privilege class as install, no confirmation dialog), at the admin's explicit request - previously it only stopped future pushes, leaving the app on the device. Driven by `PolicyResponse.packagesToUninstall`, which `performMdmSync` acts on right after every fresh policy fetch. `AppUninstallReceiver` (new, manifest-registered, mirrors `AppInstallReceiver`'s pattern) only logs the result - there's no local state to update, since the server confirms completion itself from the next status report rather than needing a client-side acknowledgement (see kid-phone-server's CLAUDE.md, `device_pending_uninstalls`).

## Fail closed (palchrb fork)

Upstream treated every "no usable policy" case as `null`, and `AppEnforcer.apply(null)` means "no restrictions" - a corrupt cache or a server answering a default policy after an error unsuspended everything and unpinned kiosk. Now:
- **`server/PolicyGate.kt`** (pure, no Android imports, `PolicyGateTest`): `decodeCached` (Absent/Ok/Corrupt), `decodeFresh`, `judgeFresh` (rejects a fresh policy with `allowlist == null` when the phone was managed - cached allowlist present, cache corrupt, or cache missing although `policy_ever_applied` is set), `choosePolicy` (fresh > cache; `Apply(null)` only on a phone that has never applied a policy, so setup works; otherwise `Fallback`), `policyState`, `shouldSuspendNewPackage`.
- **`Fallback` enforces the `LastEnforcedPlan`**: a tiny separate JSON (allowlist, kiosk, lock-task features, schedule) stored in `last_enforced_plan` with every accepted policy. If that's unreadable too, the fallback is "nothing allowed, kiosk on". So an override or pause that ends while the cache is unusable re-locks on the next sync instead of staying open (upstream-era "keep current state" left the phone as the override had opened it).
- **`performMdmSync`** fetches the raw body (`MdmApi.getPolicy()` returns `ResponseBody`): no network = unreachable, 5xx = `server_error` (the server answers 500 instead of a default policy), undecodable = `fresh_decode_failed`. Only an accepted fresh policy is cached - together with `policy_ever_applied` and the `LastEnforcedPlan`, in one synchronous `commit()` (`storeAcceptedPolicy`) - and only then do the PIN hash, command dispatch and uninstalls run. Every status report carries `policyState` (`ok`/`cache_corrupt`/`rejected_suspect`/`fresh_decode_failed`/`server_error`), shown as a warning on the server.
- **`cachedPolicy()` returns `CachedPolicy`**; offline callers use `currentPolicyDecision()` (`reevaluateLockReasonFromCache`, the Settings pause switch, `AppEnforcer.enforceOnNewPackage`), and `KidSettingsActivity` only reads an `Ok` cache (`controlsSection`).
- **`allowlist = []` means nothing allowed**: every controllable package except our own (and the system dialer, below) is suspended and hidden, and kiosk pins only our own package (it's HOME and holds LockActivity/Settings). Upstream treated `[]` as "open" and never pinned with an empty allowlist. `null` still means unmanaged.
- **The system dialer is never suspended or hidden, managed or not** (`TelecomManager.getSystemDialerPackage()`, `computeEnforcementPlan`'s `neverRestrict`; `apply()` also force-releases it if an older build left it hidden): it's the in-call UI for emergency calls. Unsuspended, its keypad would bypass the allowlist (any number, MMI/USSD, call forwarding), so **while managed and the dialer isn't allowlisted, `apply()` sets `DISALLOW_OUTGOING_CALLS`** (before releasing the dialer; emergency calls are exempt) and `AppFilter` leaves the dialer off Home and the app list while that restriction is set. It's cleared when unmanaged or under an override. Keeping the dialer out of the lock-task packages does **not** keep it out of kiosk: with `LOCK_TASK_FEATURE_KEYGUARD` set, AOSP's `LockTaskController` lets any system-dialer task run (its emergency-call exemption), e.g. via a `tel:` link - the call restriction is the real gate. Keyguard is forced on with kiosk on the launcher side too, not only by the server.
- **`DISALLOW_CONFIG_DATE_TIME` (plus automatic time) while managed**, lifted under an override like every other restriction, so the clock can't be moved to stretch a schedule.
- `ServerJson` lives in `server/ServerJson.kt` so JVM tests don't load Retrofit. It has no `coerceInputValues`: one `null` in a non-nullable field fails the whole decode (`PolicyResponseCompatTest`); the server's `policy_json_keys_snapshot` test keeps that from happening.

## Calls & SMS (palchrb fork, design `docs/design/02-calls.md`, at the monorepo root)

The server's `call_policy` (always sent by our server with an explicit `managed`) turns the launcher into the phone app. Decisions are pure Kotlin in `calls/` (JVM-tested); the Android classes there only feed them and act:
- **Pure**: `PhoneNumbers.kt` (normalisation + `tel:`/`sip:` handle parsing; runs the server's shared `phone_vectors.json`, copy in `app/src/test/resources/`, must be identical to `../server/testdata/phone_vectors.json` - `PhoneNumbersTest` fails otherwise; change both together), `CallRules.kt` (`decideOutgoing`/`decideIncoming`, `Emergency`, `callbackWindowUntil`), `CallPolicyStates.kt` (`callPolicyState`, `callPrefsUpdate`), `DialerRole.kt` (take/release the role, prompt, default-apps lock), `MessageButtons.kt`. `PolicyGate.judgeFresh` and `computeEnforcementPlan` carry the call parts of acceptance and enforcement.
- **States**: `Unmanaged` (explicit `managed: false`, or no `call_policy` on a phone whose calls never were managed), `Managed(rules)`, `UnknownFailClosed` (emergency calls and the callback window only). A response **without** `call_policy` after managed calls is rejected whole (REJECT_SUSPECT); `calls_managed_last` and `last_call_rules` are written in the same `commit()` as the cache, only from an explicit `managed`, and a corrupt/missing cache falls back to those last rules before fail-closed. `CallPolicyStore` holds the state in memory (the services answer from memory within Telecom's budget), starts `UnknownFailClosed`, and is refreshed first thing in `Application.onCreate` (reads SharedPreferences directly, not `LauncherPreferences`), after every accepted sync, and by each call service's `onCreate`. Everything after it in `Application.onCreate` (`BootClock`, `LauncherPreferences.init`, the rest) is wrapped so an exception there no longer kills the process (QA #10: a dead process means unscreened calls); an uncaught exception elsewhere still does (global handler).
- **The override PIN and "pause all restrictions" never open calls** (decision after QA review): they lift app restrictions only; call rules, `DISALLOW_SMS`, `DISALLOW_OUTGOING_CALLS` (when calls are managed), the SMS-app suspension and the call-permission denials stay. This is the explicit exception to the "every restriction is liftable" standing rule below. They **do** lift a time rule's call block (school mode, step 6, user decision 2026-10-05) - back to the call rules, never beyond.
- **Dialer role**: while managed (or fail-closed) `AppEnforcer.applyDialerRole` takes it with `setDefaultDialerApplication` (no prompt); a failure is reported in `callState.lastError` and Home shows the system role prompt at most once a day. Unmanaged, a role we took (`CallPrefs.dialerRoleTakenByUs`) is handed back to the system dialer. `ROLE_CALL_REDIRECTION` has no device-owner API: grant it at provisioning (`adb shell cmd role add-role-holder android.app.role.CALL_REDIRECTION me.vibb.launcher`) (Home can't prompt for it: see below). The same for `ROLE_CALL_SCREENING` (security review L7, `... android.app.role.CALL_SCREENING ...`): Telecom binds one screening service besides the carrier's - the screening role holder's, else the default phone app's (`CallsManager.setUpCallFilterGraph`) - so holding it keeps incoming calls screened by us also when we aren't the phone app, and keeps another app from screening instead of us; reported as `callState.screeningRoleHeld`, prompted by Home only while we aren't the phone app (`rolePromptFor`, one prompt a day), and the server warns when calls are managed and neither the dialer nor the screening role is ours. As soon as the dialer role is held, `DISALLOW_CONFIG_DEFAULT_APPS` is set (cleared before the dialer role changes) - not waiting for the redirection role, which must be granted with adb before handover. The restriction stays on: on Android 14+ PermissionController refuses every exclusive role's request under it (AOSP `Role.getRestrictionIntentAsUser` opens "blocked by your admin"), so Home never prompts for redirection or screening while we hold the dialer role - lifting it for a prompt was tried and dropped (QA of cmd-expiry, Medium 2: the kid could hold the lift open and change default apps). Provisioning grants both with adb.
- **Outgoing**: `KidCallRedirectionService` cancels a not-allowed call before it's placed (the other phone never rings), and redirects an allowed call typed differently to the contact's stored E.164 number (`outgoingDialTarget` - dial what was checked); `KidInCallService` disconnects anything that slips through, and calls of unknown direction unless emergency or a contact allowed either way (`decideUnknownDirection`). Emergency numbers are always allowed (platform `isEmergencyNumber` ORed with the country's real numbers - 112/911 plus 110/113 for +47 - never 000/08/118). `DISALLOW_OUTGOING_CALLS` (emergency exempt) replaces our rules only when calls are off, the rules are unknown, or our dialer isn't in place; with calls unmanaged, step 1's rule (managed allowlist + dialer not allowlisted) still applies.
- **Incoming**: `KidCallScreeningService` rejects first (no ring); `KidInCallService` re-checks every incoming call (withheld numbers are never screened, screening fails open after 5 s). Withheld and failed-verification callers are blocked when managed. The **callback window** (60 min, anyone may call) opens only after a call the platform confirms as an emergency number that connected (call log `DURATION > 0`, or our in-call service seeing it active) - never from the static list. Our own record of such a call is checked by wall clock, elapsed realtime and boot count (`timedWindowActive`), and date/time stay locked whenever calls are managed (call-log times are wall-clock). The status report carries the last emergency call, the window and `callLogReadable` (warned on the server: without the call log the window can't open).
- **UI**: `PhoneBookActivity` is the DIAL/`VIEW tel:`/`CALL_BUTTON` handler and the kid's phone book (outbound contacts, Call immediately, a Message button only when the chosen app - SMS while SMS is on, Element X with a Matrix ID, Signal/Molly - is installed, unsuspended and allowed). No free keypad, no built-in emergency buttons - but contacts whose number is an emergency number stay in the phone book and on Home with calls off or the rules unknown (`phoneBookView`), and with no readable rules at all the phone book shows one "Emergency call" row (112). Home shows "Phone book" plus contacts flagged Home (`ContactsHomeAdapter`, before the apps in a `ConcatAdapter`). `InCallActivity` (over the lock screen, own task, proximity wake lock) and a `CallStyle` notification with a full-screen intent; the service also starts the activity directly (device owner + HOME may start activities from the background). Telecom plays the ringtone (no `IN_CALL_SERVICE_RINGING`). The system dialer is kept off Home while calls are managed, never suspended or hidden (emergency calls always use it), never pinned in kiosk while calls are managed.
- **Permissions/SMS**: while managed, third-party apps' `CALL_PHONE`/`ANSWER_PHONE_CALLS` are denied (also right after an install), and the launcher self-grants `READ_CONTACTS` (screening only sees non-contacts without it), `CALL_PHONE`, `READ_PHONE_STATE`, `READ_CALL_LOG`. SMS off sets `DISALLOW_SMS` and suspends the default SMS app, Google Messages, AOSP Messaging and STK whatever the allowlist says (RCS bypasses `DISALLOW_SMS`).
- **Status report**: `capabilities = ["call_policy_v1"]` and `callState` (state, both roles, default/system dialer, restrictions, default SMS app, last error, last emergency call, callback window).
- **Direct boot (task 15)**: only the call path is `directBootAware` - `KidCallScreeningService`, `KidCallRedirectionService`, `KidInCallService`, `InCallActivity`, `CallActionReceiver` and `BootCallReceiver` (`LOCKED_BOOT_COMPLETED`, only loads the policy). **Never mark `HomeActivity`, `LockActivity`, `PinLockActivity` or anything that starts lock task direct-boot-aware, and never start kiosk/enforcement/services/tsnet before unlock** (the BFU lockout incidents below). Before the first unlock CE storage can't be read, so `CallPolicyStore` reads `boot_call_policy` from device-protected storage: pure `BootCallPolicy.kt` (`BootCallPolicyTest`), strict versioned JSON with only mode, calls on/off, country code and the allowed numbers (no names, tokens, PIN hash - DE is readable before authentication); missing/corrupt/other version → `UnknownFailClosed`. Every unlocked `refresh` rewrites it (`commit()`) when it differs from the last string *really* committed (a failed commit is retried; the prefs' in-memory map can't be trusted after one), checks the copy decides like CE (`bootCopyFaithful`) and reports `callState.bootPolicy` (`ok`/`write_failed`/`unreadable`); numbers no caller could match are left out rather than making the copy unreadable. The decisions are the pure `refreshPlan` (`CallPolicyRefreshTest`). A DE copy that saw managed (or unknown) calls is a second witness: a CE that lost `calls_managed_last` (reset/wiped preferences) fails closed and gets the flag restored - only an explicit `managed: false` unmanages; `resetPreferences` also keeps `calls_managed_last`/`last_call_rules`. The emergency-call record (callback window) lives in DE prefs `call_boot_state`. `Application.onCreate` while locked does only the call policy + `BootClock` and defers `LauncherPreferences`/`initRest` (`ensureUnlockedInit`) to `ACTION_USER_UNLOCKED` (registered receiver) or - first, usually - `KidAppComponentFactory` (manifest `appComponentFactory`, fully qualified because of the `.debug` suffix, extends androidx's `CoreComponentFactory`), which runs it before creating any component not in `DirectBootComponents`: such a component existing proves CE is unlocked even while `isUserUnlocked()` is still false. **A new direct-boot-aware component must be added to `DirectBootComponents`** (`DirectBootComponentsTest` compares it with the manifest). Whether Telecom binds our services before unlock, and whether the call log is readable then, are device checks in `02-calls.md` ("Direct boot").
- **Known gaps (device checks / follow-ups)**: direct boot is untested on a device (see above); a PSAP callback before the first unlock is rejected unless our in-call service recorded the emergency call (the call log is not read while locked); whether VIEW `tel:` reaches our activity or the system keypad, whether the system keypad's MMI codes are stopped, and whether the role APIs work on the Jelly Star are all on the device checklist in `02-calls.md`. Element X / Element Call VoIP and other self-managed calling apps bypass Telecom screening entirely. Since design 17 an allowed messaging app's calls ring over the PIN lock (unscreened, see below), and a self-managed call no longer holds the lock open.

## Hardening (handy step 4, design `docs/design/04-hardening.md`, at the monorepo root)

- **User restrictions from server switches** (`server/Hardening.kt`, pure, `HardeningTest`; DTO `dto/HardeningPolicy.kt` = `PolicyResponse.hardening`): `DISALLOW_FACTORY_RESET`, `_ADD_USER`, `_MODIFY_ACCOUNTS`, `_CONFIG_VPN`, `_USB_FILE_TRANSFER`, `_DEBUGGING_FEATURES`, `_SAFE_BOOT`, `_CONFIG_LOCATION` (+ `setLocationEnabled(true)` first) and `_AIRPLANE_MODE` (step 5). `hardeningPlan` sets each as the server says while managed (`hardeningManaged`: the enforced policy has an allowlist, or calls are managed); a missing object or field means that switch's default (all on, **safe boot and airplane mode off**), unmanaged/never-managed clears all. **Not lifted by the offline override or the pause** - only an explicit server value or unmanaging (second exception to the standing rule). `AppEnforcer.applyHardening` runs last in `apply()`, after the always-on VPN. `LastEnforcedPlan` carries the switches. Never call `AppEnforcer.apply(context, null)` for an override any more - pass the enforced policy (`currentPolicyDecision().policy`), or the hardening would be cleared.
- **adb**: with `disallow_debugging_features` on (the default) adb is gone the moment the first managed policy applies - no `adb install -r` fix-forward, no logcat, no `cmd role add-role-holder`. Grant `ROLE_CALL_REDIRECTION` and `ROLE_CALL_SCREENING` before enrolling, or switch "Block USB debugging" off in the phone's Advanced › Restrictions (the device row exists before enrollment) for device work. A launcher that crash-loops before it can sync then needs a recovery-mode wipe. ## Time rules, screen time, lifts, location policy (handy step 6, design `docs/design/06-time-rules.md`, at the monorepo root)

- **Model** (pure, `timerules/TimeRules.kt`, `TimeRulesTest`): `PolicyResponse.timePolicy` = named rules (`kind` school/bedtime/custom, `callsAllowed`, `exemptApps`, `days` = 7 windows Monday first; `start>end` ends next day, `start==end` = 24 h), `dailyBudgetMinutes` (7, null = unlimited) and the parent's `lifts`. ## Push, battery and Play (handy step 7, design `docs/design/07-battery-fcm-play.md`, at the monorepo root; FCM removed in design 19)

## FCM removed, SSE hardening (design 19, `docs/design/19-remove-fcm.md`, at the monorepo root)

- **SSE only**: `push/FcmSupport.kt`, `KidFcmService.kt` and `PushTransport.kt` are gone (transport decision, token upkeep, `SseReason`, FID/hash helpers, `fcm_push_v1`); `PushState` keeps only `sseConnected` (memory). ## VoIP calls over the PIN lock (design 17, `docs/design/17-voip-calls-over-lock.md`, at the monorepo root)

- **What rings**: an allowed app's ringing CALL notification with a full-screen intent - the contacts' messaging apps while calls are managed and on (Element X, Signal/Molly; never the SMS app), the known messengers while calls are unmanaged, none while calls are off or unknown; unsuspended (pure `voipCandidates` on `CallPolicyStore.effectiveState()`). - **Reading** (`badges/VoipCallReader`, in `BadgeListenerService`): category, channel, flags and whether an FSI exists; it keeps the ring's FSI, CallStyle decline and answer actions (17b: `pickAnswerIntent`) and the call service notification's content intent - **never the ring's content intent as such, never a title or text** (`VoipCallGuardTest`).

## Parent PIN hardening (design 24, `docs/design/24-parent-pin-hardening.md`, at the monorepo root)

- **One gate** (`server/ParentPin.kt`): the time lock's "Enter unlock code" (`override`), the PIN lock's "Parent code" (`pin_lock`), the Settings gate (`settings`), "Pause all restrictions" (`pause`) and "Install from Play" (`install_mode`) all call `ParentPin.check(context, entry, pin)` - background thread only (PBKDF2). Since design 24b the parent PIN is checked through its vault (`PinVault`, below) and `PinHash.verify(` exists only in `PinLockRuntime` (the kid's PIN); `OfflineOverride.activate`, `RestrictionsPause.start` and `PlayRuntime.startInstallMode` are called only from `ParentPin.kt` - the window starts inside `check`, after its `unlocked` event is committed (`ParentPinCallersTest`). Every pre-check reads `ParentPin.status` (configured - one rule, `PinHash.usable` included -, lockout left, tries left, next lockout): a dialog opened after 4 wrong tries anywhere warns "One more wrong try locks it for ...". One lock; `check` nests only design 24b's short locks (the relock marker's in `WindowRelock.opened`, the policy cache's in the vault's migration), neither of which ever takes `ParentPin`'s.
- **Lockout** (`ParentPinLockout.kt`, pure, `ParentPinLockoutTest`): 5 wrong tries lock every entry for 15 min, then 30 min, 1/2/4/8/16 h, cap 24 h (level 1-8). A correct PIN clears the tries but keeps the level; the level drops one step per 24 h without a wrong try (`decay` window); a new PIN from the server (another fingerprint) resets everything, a running lockout included. Within a boot both windows follow `backoffRemainingMs`; across a reboot `refreshParentLockout` re-anchors them by the wall clock (a clock set back gives the full duration, never more). The try **and** its `wrong`/`lockout` event are committed before PBKDF2; a match goes back to the pre-attempt state with no failures and swaps the event for `unlocked`. Under 6 characters: `TooShort`, not counted.
- **Store** (`ParentPinStore.kt`, `ParentPinStoreTest` against a fake prefs map): CE prefs `parent_pin_state`, every write one `commit()` of everything (`version`, `failures`, `lo_*`, `dc_*`, `pin_fp`, `events_v1`; the level is never stored - `levelNow` reads it from the decay window). The first load migrates the old `offline_override_failed_attempts`/`_locked_until` (still declared in `LauncherPreferences$Config` only for that; a running lockout keeps running, at most 15 min). An unreadable state (type clash, out of range, missing key) becomes a committed 15-minute level-1 lockout - never a dead end; a corrupt queue is dropped; a failed commit writes the previous state back and answers `Unavailable` ("Couldn't check the code" / "storage is full").
- **Dialogs** (`ui/ParentPinDialog.kt`; the PIN lock's own `dialog_pin_parent_code`): every result in the dialog's error line, never a toast (they don't show while a budget sets `DISALLOW_CREATE_WINDOWS`). No PIN or a running lockout opens the dialog in that state with OK disabled; after a lockout OK stays disabled (Cancel and reopen). Texts: the time left (`lockoutText`, "1 h 45 min", nb "1 t 45 min") plus the way out (a new parent PIN), and on the last try the next lockout. The Settings gate drops an Ok from an ended session (`session`, bumped in `onStop`).
- **Events** (`ParentPinEvents.kt`, `dto/ParentPinEvent`): `unlocked` (with `until_ms` for override/pause/install mode), `wrong` (`failures`) and `lockout` (`level`, `until_ms`), never PIN material; at most 100 queued, `wrong` dropped first. Uploaded only after the status report in `performMdmSync` (`POST /api/devices/pin-events`): a snapshot, and after a 2xx only the sent ids leave; dropped on any other 4xx except 401/404/408/429, kept on those, 5xx and no answer (an old server's 404: they wait). Enrollment clears the queue (not the lockout). Capability `parent_pin_events_v1`. The legacy `offline_override_used` status flag stays for older servers.

## Security review, launcher wave (2026-10-11, `docs/review/security-review-2026-10-10.md`, at the monorepo root)

- **The bearer stays home** (L8, `server/ServerAuth.kt`, `ServerAuthTest`): `bearerInterceptor` adds `Authorization` only to requests for the server's own origin (scheme, host, port - `sameOrigin`); `createMdmApi` and `createMusicServer` both use it, so an absolute `@Url` elsewhere never gets the device token. - **The Tailscale key is deleted after the first connect** (M12, `server/TailnetKey.kt`, `TailnetKeyTest`): tsnet reads `AuthKey` only to create the node (its state dir then holds the identity), so once `connect` returns an address `TsnetClient.forgetKeyOnceJoined` removes `tailscale_auth_key` and sets `tsnet_node_joined` in one `commit()`; later starts come up with an empty key from the stored state (`tailnetConnect`: key -> up with it, joined -> up with "", neither -> nothing). ## The battery in the status report (design 35 §2.5, `docs/design/35-parent-notifications.md`, at the monorepo root)

- **Wire** (design 35 step 1, in the server's commit): `StatusReportRequest.battery: BatteryReport? = null` with
  `BatteryReport(level, charging, low)` (every field always sent; `null` is left out, so `time_status_report.json` /
  `TimeStateZoneTest`, which build their own request, are unchanged). The server stores the level and charging for
  the PWA's "Battery 14 %, charging" line and raises the parent's "Battery low" event from `low` (latched; re-armed on
  battery, not charging, above Android's level); a level outside 0..100 drops the reading, never the report.
- **The reading** (step 3, `server/BatteryStatus.kt`): every report sets `battery = BatteryStatus.report(context)` -
  the sticky `ACTION_BATTERY_CHANGED` (`ContextCompat.registerReceiver(context, null, ..)`, as `SelfUpdate`'s ECBM read) through the pure `BatteryReport.of(level, scale,
  status, plugged, low)`: level = round(level x 100 / scale) clamped 0..100, charging = plugged != 0 or status
  CHARGING/FULL, low = `EXTRA_BATTERY_LOW`; `null` (left out) without a sticky intent, with the level -1 or a scale
  <= 0, or on any exception. Capability `battery_v1` (`BATTERY_CAPABILITY`, in `STATUS_CAPABILITIES`).
- **The trigger**: `Application.initRest` calls `BatteryStatus.watch(this)` - one runtime receiver
  (`RECEIVER_NOT_EXPORTED`; the system's broadcasts still reach it) for `ACTION_BATTERY_LOW` and `ACTION_BATTERY_OKAY`
  that calls `SyncRunner.request(app, "battery")`, so the report with `low=true` lands within seconds (OKAY: the
  re-arm). The request and the registration are each caught. While the process isn't running (killed, or before the
  first unlock) the edge is lost and the next report carries the sticky state.
- **After an emergency call connects** (`calls/EmergencyConnects.kt`, one per `KidInCallService`): every connected
  state of a platform-confirmed emergency call (active, active again after hold, disconnected after connecting) goes
  through `connected(call, connectTimeMillis, now) { CallPrefs.recordEmergencyConnected(this, it) }`, which commits
  the record with **one instant per call** (the call's `connectTimeMillis`, else its `creationTimeMillis` - both
  Telecom's, stable across a restart of our process mid-call -, else the first sighting; kept per `Call` object,
  identity map, dropped in `onCallRemoved`) and then asks for **one** sync per call
  (`SyncRunner.request(this, "emergency_call")`, called directly - Telecom's callbacks are on the main looper, and a
  post could be dropped by `onDestroy`'s `removeCallbacksAndMessages` - and caught) - so the report with
  `last_emergency_call_at` reaches the parent within seconds. `CallPrefs` keeps the instant
  (`mdm.calls.emergency_connected_at_ms`, DE prefs `call_boot_state`); the pure rules beside `callbackWindowUntil`
  (`CallRules.kt`): `emergencyRecord` - the callback window runs from **this** record, the hang-up's last, so a
  50-minute call still leaves an hour - and `reportedEmergencyAt` - the stored instant, a record from an older build
  its window's start. Before the stable instant the report moved from the connect to the disconnect time, which the
  server announces as a second emergency call. **Never before the first unlock** (`CallPolicyStore.userUnlocked`
  false: the anchor isn't direct-boot-aware): no request, the call isn't marked, so its next connected state after
  the unlock asks; else the anchor's start sync after the unlock carries the call from the DE record.
- Tests: `BatteryReportTest` (`of`: rounding, clamp, the charging rule, every null case; the report with and without
  `battery`; the receiver's registration, actions and catches by source), `SyncScheduleTest` (`battery_v1`),
  `EmergencyConnectsTest` (one sync and one instant per call over its states, the creation-time fallback, a second
  call, never before the unlock and at the next state after it, `emergencyRecord`/`reportedEmergencyAt`, the
  service's wiring and the request's catch by source; `BatteryReportTest` counts `report()`'s catch too). Emulator check: `docs/testing/emulator.md` §6n.

## Building without tsnet.aar

`libs/tsnet.aar` only exists where the Go + NDK toolchain ran (CI, x86_64). When it's missing, `app/build.gradle.kts` compiles `app/src/tsnetStub/java/tsembed/` into the **debug** variant instead - same API as the gomobile binding, every connect fails - so `./gradlew assembleDebug testDebugUnitTest` works on any machine; Gradle logs a warning when the stub is used. A **release** build never gets the stub, whatever the flags (security review L13): `checkReleaseHasTsnet` (a dependency of `preReleaseBuild`) fails it without the aar, and the stub isn't in the release source set anyway. CI also passes `-PrequireTsnet=true`, which fails any build without the aar. To build a release locally without Go (an APK that is never for a phone), pack the stub's classes into a throwaway `libs/tsnet.aar` (gitignored). If `mobile/tsembed`'s exported API changes, update the stub to match.

**Dependency verification** (security review L9): `gradle/verification-metadata.xml` holds the SHA-256 of every artifact the build resolves (CI's x86_64 aapt2 included, added by hand), the wrapper pins its distribution, and CI validates the wrapper jars - see the root `CLAUDE.md` "Build and test" for adding a dependency; `BuildChainTest` checks the wiring.

## Release builds (palchrb fork)

Production phones run the **release** build, package `me.vibb.launcher` (debug keeps the `.debug` suffix; only one of the two can be device owner on a phone). `app/build.gradle.kts` signs release builds when a keystore is configured: env vars `ANDROID_RELEASE_KEYSTORE_FILE`/`_PASSWORD`/`ANDROID_RELEASE_KEY_ALIAS`/`ANDROID_RELEASE_KEY_PASSWORD` (falls back to the store password), or the Gradle properties `handy.release.storeFile`/`storePassword`/`keyAlias`/`keyPassword` in `~/.gradle/gradle.properties` - never in the repo. Without one, `assembleRelease` still produces `app-release-unsigned.apk`; `-PrequireReleaseSigning=true` turns that into a build failure (release CI uses it). The release build type is not debuggable (no `run-as`). `-PversionCode`/`-PversionName` override the literals in `defaultConfig`; release CI derives them from the tag (`vMAJOR.MINOR.PATCH` -> `MAJOR*1_000_000 + MINOR*1_000 + PATCH`), so never bump the literals for a release. A release launcher can't be downgraded (`INSTALL_FAILED_VERSION_DOWNGRADE`, and `adb install -r -d` needs a debuggable app), so a broken release is fixed forward under a higher tag; a mistyped high tag burns versionCodes for good. R8 only shrinks (`-dontobfuscate -dontoptimize`); `proguard-rules.pro` also keeps the gomobile (`go.**`, `tsembed.**`) and pcap4j packet classes, and line numbers. Losing the release key means no more silent self-updates and re-provisioning every phone - keep it offline and backed up.

## Non-obvious gotchas (hit for real, more than once in some cases)

- **A second real boot-lockout incident on the GrapheneOS Pixel (2026-08-14), recovered again only via hardware-recovery-mode wipe - root cause not confirmed, but a real, well-supported theory plus mitigations are now in place.** Confirmed *not* a repeat of the original keyguard-suppression bug below: kiosk mode was visibly, correctly engaged for hours with `AppEnforcer`'s fail-closed lock-task-features verification succeeding repeatedly before the reboot, which that fix would have caught if it were failing. Leading theory instead: `TsnetClient.connect()` runs tsnet's embedded Go/cgo runtime, a real native-crash surface a plain Kotlin try/catch cannot protect against - a hard abort (e.g. GrapheneOS's `hardened_malloc` catching a memory-safety violation that stock Android's allocator might silently tolerate) bypasses the JVM's exception handling entirely and kills the process at the signal level. This app has no fallback Home app once Device-Owner-pinned, so a connect attempt that crashes on every launch would boot-loop the device with no way to reach a working launcher again - and this exact mechanism (tsnet's Go runtime SIGABRT-crashing the process) already happened once before for a different, since-fixed trigger (`no safe place found to store log state`, see the tsnet section below), so it's a real precedent, not pure speculation. Fits the device-specific pattern too (`hardened_malloc` is GrapheneOS-exclusive - never seen on the Moto G Play) and the "worked fine for hours, died at reboot" pattern (crash risk concentrated in tsnet's cold-start connection sequence, not steady-state operation). One real tension against this theory, noted honestly: a launcher self-update crashing/restarting the process has been observed to transiently fall back to a stock/system launcher that self-recovers, not a permanent hang - if tsnet were crash-looping identically, that same fallback-and-recover pattern might be expected instead of a hard lockout requiring a wipe. Not resolved either way without a live crash dump this app has no way to capture pre-decrypt. **Mitigations shipped regardless of whether this exact theory is confirmed**: (1) `TsnetClient.connectFromPreferences` no longer fires from `Application.onCreate()` (the earliest possible point in the process's life, racing the very first UI paint after unlock) - it's triggered from `HomeActivity`'s first `onResume()` instead, after the launcher has actually rendered. (2) `TsnetClient.connectFromPreferences` now wraps every attempt in a persisted crash-loop guard - a preference flag set synchronously right before the risky call and cleared right after; if a launch finds it still `true` from last time (proof the previous attempt never returned), that counts toward a streak, and after 2 such detections within a 15-minute window the next attempt is skipped entirely for that launch rather than retried straight into the same crash, letting the rest of the app boot normally without tailnet connectivity that cycle. Both are also worth checking for any *other* code path this app might add that touches tsnet or another native/cgo dependency in the future - the same class of risk applies wherever a hard native crash could happen before the launcher has had a chance to render at all.

  **Follow-up diagnostic session (2026-08-14 evening) - root cause still not confirmed, but a real live cycle was fully observed for the first time and came back completely clean.** Controlled testing first isolated the trigger precisely: Device Owner granted via adb *without* enrolling (no policy ever fetched, kiosk never engages) rebooted clean every time: switching only kiosk pinning on (via enrollment) is what makes the freeze reproducible, confirming it's specific to actively-pinned lock-task state, not Device Owner mode generally, general app bugs, or this physical unit's hardware (all separately ruled out by this same test). With that isolated, a live `adb logcat` stream was started *before* an actual reboot (capturing right up to the USB disconnect) and adb access was re-established immediately after (see the adb-authorization gotcha below) - between the two, the entire cycle was observed directly for the first time instead of only being reconstructed after the fact from a dead phone: a clean, ordinary-looking shutdown (simultaneous HAL/vendor daemon teardown - Wificond, audioserver, GNSS, Weaver, USB HAL - the normal signature of a voluntary reboot, not a crash), zero FATAL exceptions/native tombstones anywhere in the capture, the device reaching the lock screen correctly, and - after unlocking - `HomeActivity` resolving and kiosk re-pinning cleanly with zero errors, all on the build carrying every mitigation above (versionCode 108). In short: this specific test simply didn't reproduce the freeze at all, so the tsnet-crash theory above is neither confirmed nor ruled out by this session - treat it as still open. What this session *did* conclusively rule out: `HomeActivity` briefly being unresolvable (`cmd package resolve-activity` returning nothing, `am start` reporting `Activity class ... does not exist`) immediately post-reboot is not itself a symptom of anything wrong - see the dedicated gotcha entry on this below, added directly because of how alarming it looked mid-investigation before being understood.

- **`cmd package resolve-activity`/`am start` reporting `Activity class {.../HomeActivity} does not exist` immediately after a reboot, with `com.android.settings/.FallbackHome` shown as the focused app instead, is expected pre-first-unlock behavior for this app - not a crash, not corruption, not a bug to chase.** Only the call components are direct-boot-aware (task 15, see "Calls & SMS"); everything else - including `HomeActivity` - is not resolvable by PackageManager until the user's credential-encrypted (CE) storage unlocks, which requires a real first-unlock this boot cycle; `FallbackHome` (which *is* direct-boot-aware) is Android's own built-in placeholder for exactly this "the real Home app isn't ready yet" state, and is almost certainly also what's briefly, normally visible during any ordinary launcher self-update or process restart (see the "stock launcher flashes then reloads" observation in the entry above - same mechanism). Confirmed live (2026-08-14): `dumpsys device_policy` genuinely does not expose the `lockTaskFeatures` bitmask anywhere in its text output despite lock-task pinning being fully active (don't rely on it for that - `dumpsys activity activities | grep -A10 LockTaskController` shows `mLockTaskModeState`/`mLockTaskPackages` instead, though not the features bitmask either); `cmd package resolve-activity -n <component>` is the cleanest direct way to check whether a specific component is currently resolvable. The moment the device is actually unlocked, `HomeActivity` resolves and starts normally with zero errors - this whole state is a normal, timing-dependent, self-resolving part of every reboot, not evidence of anything broken.
- **adb showing `unauthorized` even though the phone displays "connected for debugging" (no fresh authorization prompt appearing at all) is not necessarily proof of a pre-decrypt/BFU state** - a claim made earlier in this investigation with more confidence than was warranted. Confirmed live (2026-08-14) that this can also just be a stuck/stale key-trust state specific to one host computer while the device is fully unlocked and normal (it worked fine from a different computer at the time). Troubleshooting order that actually resolved it, cheapest first: revoke USB debugging authorizations on the phone itself and replug (Settings > Developer options); if that doesn't prompt a fresh dialog, regenerate this host's adb keypair entirely (`adb kill-server`, move `~/.android/adbkey`/`adbkey.pub` aside, `adb start-server` regenerates them) - a genuinely new, never-before-seen public key must trigger a fresh prompt if the phone can show dialogs at all, which cleanly rules out any stale-trust explanation; if it *still* won't prompt, suspect the physical connection itself (cable/port/hub) before anything software-side, especially if it's known to work on another machine.
- **`PackageManager` query methods silently exclude apps hidden via `dpm.setApplicationHidden()` unless you pass `MATCH_UNINSTALLED_PACKAGES`.** This bit `AppEnforcer.controllablePackages()`'s `getInstalledApplications()` call *and*, separately, `MdmSyncWorker.collectInstalledApps()`'s `getApplicationInfo()` call one level deeper - fixing only the first still left unchecked apps permanently unable to reappear as checkboxes on the admin site. If a future "an app that got hidden can't be found again" bug shows up anywhere, check *every* PackageManager call in that code path for this flag, not just the first one you find.
- **A real boot-loop incident happened**: an earlier fix used a completely unfiltered `pm.getInstalledApplications(0)` for the suspend/enforcement loop, which included core OS/system packages - a restrictive allowlist suspended essential system components and crashed the phone into a boot loop, recovered via `adb reboot recovery`. Under-inclusion (missing an edge-case app) is an acceptable tradeoff; over-inclusion touching core OS packages is not, ever. `controllablePackages()` originally guarded against this with a hand-maintained `SAFE_SYSTEM_PACKAGES` allowlist of known-safe system-app package names (GrapheneOS's own `Auditor`/`Info` apps, AOSP dialer/contacts/settings/camera, ...) - this worked for the GrapheneOS test device but left almost nothing controllable on a GMS/OEM device (a real Moto G Play test enrollment showed only 4 restrictable apps - Tailscale plus three coincidental package-name matches - since Chrome/Play Store/Gmail/YouTube/Maps/the manufacturer's own apps all use different package names not in the list). **Replaced with a device-agnostic launcher-intent check**: a system app is included if it has a home-screen launcher icon (`queryIntentActivities` for `ACTION_MAIN`/`CATEGORY_LAUNCHER`), which is the actual definition of "an app a kid could tap open" - headless system components (SystemUI, telephony internals, resource overlays) don't expose a launcher activity at all, so they're naturally excluded without needing to enumerate every OEM's package names by hand. This query needs no manifest `<queries>` declaration - it's one of Android's documented automatic-visibility exemptions (the standard "list all launchable apps" idiom every launcher uses), and Device Owner apps are exempt from package-visibility restrictions entirely regardless.
- **Reading `WifiManager.isWifiEnabled`/calling `setWifiEnabled` needs `ACCESS_WIFI_STATE`/`CHANGE_WIFI_STATE` declared in the manifest even for Device Owner** - Device Owner exempts the app from the API 29+ restriction on *who* can toggle WiFi, but that's a separate concern from the base permission needing to be declared at all. Missing this crashed the old `QuickControlsActivity` (now `KidSettingsActivity`) with `SecurityException` the instant WiFi was included in a device's `quickControlsMask`, since `isWifiEnabled()` was called unguarded in `onCreate()`. Both `QuickControls.isWifiEnabled`/`setWifiEnabled` now also have defensive try/catch matching the rest of the file, as a second line of defense.
- **`LOCK_TASK_FEATURE_KEYGUARD` does nothing if the phone's own OS-level screen lock is "None"/swipe** - it only re-enables *whatever lock method is already configured*, it doesn't provide one of its own. Since handy step 10 "None" is the intended state (handy's own PIN lock replaces it, see above); the bit stays forced for its emergency-call exemption and for phones that still have an Android PIN.
- **`LOCK_TASK_FEATURE_NOTIFICATIONS` does not bring back Quick Settings tiles** - confirmed on real hardware (GrapheneOS/Pixel 4a): with only this feature enabled, the notification shade pulls down and shows notifications, but there are zero QS tiles (no WiFi/Bluetooth/etc. tile row at all), and no combination of the other feature bits changes that. So Quick Settings tiles are apparently just unreachable during Lock Task mode on this platform, full stop - there's no bit that restores them, and the docs' implication that this feature covers "the expandable notification shade" broadly is misleading in practice. Any WiFi/Bluetooth toggling a kid does while pinned is happening through the Settings app (if allowlisted), not Quick Settings.

## WiFi/Bluetooth restriction levels removed (2026-08-11)

The admin-configurable "open/restricted/disabled" WiFi/Bluetooth policy (server's `device_policy.wifi_mode`/`bluetooth_mode`, this app's `PolicyResponse.wifiMode`/`bluetoothMode`) is gone entirely - confirmed in practice not worth the UI complexity. `AppEnforcer.applyRadioRestrictions()` is now `clearRadioRestrictions()`: unconditionally clears the four `UserManager` restrictions that feature used to set (`DISALLOW_CHANGE_WIFI_STATE`, `DISALLOW_ADD_WIFI_CONFIG`, `DISALLOW_BLUETOOTH`, `DISALLOW_CONFIG_BLUETOOTH`), every `apply()` cycle same as before, rather than deleting the enforcement outright - a device that already had "restricted"/"disabled" saved from before this change needs those actively lifted, not just abandoned in whatever state they were last set to. `PolicyResponse` no longer has `wifiMode`/`bluetoothMode` fields at all; safe against an old server response since they're gone on both ends together, not a live compatibility concern. The kid-facing Quick Controls swipe-left WiFi/Bluetooth on/off toggles are a completely separate, unaffected feature.
- **A VPN app's own managed-config restriction only binds that app's own UI - not its own Quick Settings tile, and not any other OS surface.** Confirmed via live testing: Tailscale's `ForceEnabled` managed-config key (pushed via `setApplicationRestrictions`, see `AppEnforcer.applyVpnRestrictions`) successfully disables the in-app disconnect control, but Tailscale's own QS tile (published outside Lock Task mode, i.e. whenever the full shade is reachable) ignores it entirely and can still disconnect the VPN - apparently a separate code path in Tailscale's own app that doesn't check the same flag its main UI does. This generalizes: don't assume a third-party app's MDM/managed-config cooperation covers every surface it exposes, including its own tiles. The real fix for "this must stay connected, full stop" is `DevicePolicyManager.setAlwaysOnVpnPackage(admin, pkg, lockdownEnabled = true)`, enforced by the OS's connectivity stack directly and independent of the app's cooperation - now applied alongside `ForceEnabled` in `applyVpnRestrictions`, not instead of it.
- **The general lesson from the above**: since *any* third-party app can publish its own Quick Settings tile that ignores our restrictions, Quick Settings itself isn't a safe surface to rely on for anything kid-facing, even outside the VPN case specifically. Rather than chase this app-by-app, the launcher has its own swipe-left-from-home kid Settings screen (`ui/kidsettings/KidSettingsActivity` since handy step 8, formerly "Quick Controls", `QuickControlsActivity`) - a small, admin-curated set of toggles (WiFi, Bluetooth, brightness) built entirely on direct, silent Device-Owner APIs (`server/QuickControls.kt`), never Android's native QS tiles or `Settings.Panel.*` intents. This is the intended way for a kid to reach these controls; Quick Settings access itself is assumed permanently unsafe to expose while restrictions matter. Each of the WiFi/Bluetooth rows also has a "Manage networks"/"Manage devices" link (enabled only while that radio is on) into `WifiNetworksActivity`/`BluetoothDevicesActivity` - real scan/connect/forget screens, still built entirely on `QuickControls.kt`'s Device-Owner APIs, for the same reason.
- **`WifiManager`'s scan/connect/configured-network APIs (`startScan`, `getScanResults`, `getConfiguredNetworks`, `addNetworkPrivileged`) all hard-require the phone's system-wide Location toggle to be on**, confirmed live via `WifiService`'s own `SecurityException("Location mode is disabled for the device")` - thrown regardless of any app permission held, including `NEARBY_WIFI_DEVICES` with `neverForLocation` (that flag only covers the runtime-permission side, not this separate, unconditional platform check). `WifiNetworksActivity` works around this by silently flipping Location on for just that screen's lifetime via `DevicePolicyManager.setLocationEnabled` (Device-Owner-only, no Settings/dialog) and restoring whatever it was on exit - not a permanent change to the phone's Location setting. If a future "can't see any networks" report shows up, check this first before assuming a code bug.
- **There is no public `WifiManager.connect(int, ActionListener)` or `BluetoothDevice.isConnected()`/`connect()`/`disconnect()`** despite being documented in AOSP source - they're `@SystemApi`/hidden and simply aren't present in the public SDK jar this app compiles against (confirmed via `javap` against the real `android-36` platform jar, not assumed from docs). WiFi connection uses the public `enableNetwork(id, true)` instead, whose success only means the OS *accepted* the connect attempt, not that it actually associated - `WifiNetworksActivity` polls `scanWifiNetworks` afterwards and checks real connected state, since a wrong password shows up as a silent retry loop rather than a clean failure. The Bluetooth methods have no public replacement at all, so `QuickControls.kt` reflects into them (same pattern as `removeBond`), with the same fail-soft-on-any-OS-build handling as everywhere else in that file.
- **A `Handler`/other `Context`-dependent field initialized directly in a Kotlin property initializer (e.g. `private val handler = Handler(mainLooper)`) crashes on `Activity` construction** - property initializers run in the constructor, before `attachBaseContext`, so `Activity.mainLooper` (a `Context` method) throws `NullPointerException` on the still-null base context. Use the static `Looper.getMainLooper()` instead (no `Context` needed at all), or defer initialization into `onCreate()`.
- **`BLUETOOTH_SCAN` and `NEARBY_WIFI_DEVICES` both need `android:usesPermissionFlags="neverForLocation"`** in the manifest, or Android additionally requires the phone's Location toggle for scan results to come back at all (Bluetooth) or for the permission itself to be meaningfully granted (WiFi) - on top of, and separate from, the `setLocationEnabled` gotcha above for WiFi specifically.
- **`setAlwaysOnVpnPackage(..., lockdownEnabled = true)` for Tailscale without an exit node configured breaks all network connectivity, not just non-tailnet traffic** - confirmed live, and it's Tailscale's own documented behavior (github.com/tailscale/tailscale#12925, #1568), not something on our end to fix. Tailscale is a split-tunnel VPN: it only routes tailnet-destined traffic through its interface, not general internet traffic, unless an exit node is set. Lockdown forces *all* traffic through the VPN interface regardless of that - so with no exit node, Tailscale's tunnel has nowhere to send ordinary internet packets and they're just dropped. `applyVpnRestrictions` now only engages lockdown when `tailscaleExitNodeId` is also non-blank; `ForceEnabled` (the app-level restriction) still applies either way, since it doesn't have this failure mode. Don't ever let an admin-facing "require this VPN" toggle enable OS-level lockdown independent of exit-node state again - it's a guaranteed footgun, not a maybe.
- **`adb shell dpm set-device-owner <pkg>/.RelativeReceiver`** resolves the relative component name against the wrong base when `applicationIdSuffix` is set (debug builds: installed package `me.vibb.launcher.debug` vs. Kotlin namespace `com.kidslauncher.mdm`) - always pass the fully-qualified receiver class name. The real class is also nested under the `server` sub-package, not the top-level namespace - `MdmDeviceAdminReceiver.kt` declares `package com.kidslauncher.mdm.server`, so the only command that actually works on a debug build is:
  ```
  adb shell dpm set-device-owner me.vibb.launcher.debug/com.kidslauncher.mdm.server.MdmDeviceAdminReceiver
  ```
  A short/relative form (even one that gets the `applicationIdSuffix` part right) fails with `IllegalArgumentException: Not active admin` since it resolves to a nonexistent class - confirmed live re-provisioning the GrapheneOS Pixel after a hardware-recovery-mode wipe.
- **Reading private SharedPreferences via `adb shell run-as <debuggable-pkg> cat /data/data/<pkg>/shared_prefs/<pkg>_preferences.xml`** works without root on debug builds - useful for verifying persisted state directly instead of guessing from behavior. Note the file is named after the *installed package name*, not the Kotlin namespace.
- **`dumpsys activity activities` (search "LockTaskController") and `dumpsys statusbar` (`mDisabled1`/`mDisabled2`)** are ground truth for whether kiosk mode is actually engaged right now - more reliable than trusting the cached `kiosk_enabled` preference, which only reflects what the last `AppEnforcer.apply()` call computed and can be stale.
- **Kotlin top-level `private` is file-scoped, not package-scoped** - use `internal` to share a helper (e.g. `controllablePackages`) across files in the same package. This applies to `private` on an object/class member too (scoped to that type, not the file) - `QuickControls.selfGrantPermission` had to become `internal`, not stay `private`, for `LocateCommands.kt` to reuse it.
- **`DevicePolicyManager.setPermissionGrantState` re-issuing an already-granted permission retriggers GrapheneOS/Android's "your organization allows this app to access X" transparency notification every single call**, not just the first grant - so calling a self-grant helper unconditionally on every 2-minute sync produces a recurring notification the user can never actually dismiss for good. Always check `ContextCompat.checkSelfPermission` first and skip the grant call if already granted (see `QuickControls.selfGrantPermission`).
- **Android's location-in-use indicator fires on *any* `LocationManager` query that returns a fix - including the passive `getLastKnownLocation()` fallback, not just an active `getCurrentLocation()` fetch.** First throttled just the active fetch (10 minutes then; since step 6 the parent's location policy decides, see `locationAction` - only a `ring`/`locate` command forces it sooner), but the indicator kept appearing on every sync anyway - the passive fallback path was still being reached, and still touching `LocationManager`, on every throttled-skip cycle. Fixed by having the app keep its own cached copy of the last fix obtained (`cached_location_json` preference, `LocateCommands.loadCachedFix`/`saveCachedFix`) - a skipped cycle now returns that directly with zero `LocationManager` calls at all, so the indicator only appears on a due/forced cycle, not every sync. If a future "indicator/permission-usage still showing up too often" bug shows up anywhere in this app, check *every* path that could reach the relevant manager, not just the obvious one - same lesson as the `MATCH_UNINSTALLED_PACKAGES` gotcha above.
- **`LocationManager.getLastKnownLocation()` is purely passive** - it only returns a cached fix from whatever last requested one for any reason, and returns `null` forever if nothing ever has. It is not a "get me a location" call. For an actual on-demand fix, use `LocationManager.getCurrentLocation()` (API 30+, callback-based - bridge into a `suspend` function with `suspendCancellableCoroutine` + a `withTimeoutOrNull` wrapper) and only fall back to the cached value on timeout. `LocateCommands.currentLocation` does this; don't revert to a bare `getLastKnownLocation` call for this feature.
- **`AppInstallReceiver`'s manifest entry declared no `<intent-filter>`, and `AppInstaller.installSilently` targeted it via an *implicit* action intent (`Intent(APP_INSTALL_ACTION).setPackage(context.packageName)`) rather than an explicit component - so the `PackageInstaller.Session.commit()` result broadcast had nothing to resolve against and was silently dropped, every single time, for this app's entire history.** This is the actual, original cause of the self-update loop below - not the `apply()`-vs-`commit()` timing issue (real, and worth fixing, but not what was actually happening here): `recordInstalled`/`recordFailed` never fired even once, on any build, because the receiver was never reachable at all. No exception, no log line, nothing - the broadcast just vanished. Fixed by having `AppInstaller` target `AppInstallReceiver` explicitly (`Intent(context, AppInstallReceiver::class.java)`), which doesn't depend on any manifest intent-filter. **The general lesson**: a `PendingIntent.getBroadcast` built from an implicit action + `setPackage()`, aimed at a manifest receiver with no matching `<intent-filter>`, fails completely silently on modern Android - no crash, no log, the broadcast just never arrives. For any app-internal-only receiver (never meant to be triggered by anything outside your own `PendingIntent`), target it explicitly by component instead of relying on implicit action resolution; don't assume "it's registered in the manifest" means "it's reachable."
- **The kapt-generated `LauncherPreferences` setters all write via `SharedPreferences.Editor.apply()` (async, fire-and-forget), which is a real hazard for any write that races an imminent process death** - fixed for `TrackedAppUpdateState.save` and `LocateCommands`'s two location-cache writes (`saveCachedFix`/`saveLastActiveFetchAt`), all of which now bypass the generated setter and write directly via `PreferenceManager.getDefaultSharedPreferences(context).edit().put...(key, ...).commit()` (synchronous). Worth keeping even though the intent-filter bug above turned out to be the real cause of the self-update loop specifically - this is still a real hazard for anything written right before a self-update-triggered process kill.
- **Sideloading over a device that's already running the self-update system produces exactly one extra self-reinstall cycle, and this is expected, not a regression** (now that the intent-filter bug above is fixed and `recordInstalled` can actually fire) - `TrackedAppUpdateState` only ever gets populated by `AppInstallReceiver` reacting to a real self-triggered install; an `adb install -r` never touches it. So a sideloaded build always starts from "no record of ever installing anything," sees whatever the server currently advertises as the latest release as "new," and reinstalls itself once via its own mechanism - which is what finally lets `recordInstalled` populate and stabilizes it from then on. The tell for diagnosing this specific case (vs. a real bug) is checking the device's actual `tracked_app_update_state` preference (`adb shell run-as <pkg> cat .../shared_prefs/<pkg>_preferences.xml`) - if the key is entirely absent, no self-update has ever successfully completed on this device. **Also watch for `INSTALL_FAILED_VERSION_DOWNGRADE` in `adb logcat` around a self-update attempt** (`PackageInstallerSession` tag) - if the server's cached tracked-app release was fetched (via "Check now" or the hourly poll) *before* a just-pushed CI build finished uploading to the rolling `pre-release` tag, it caches a stale, older asset; Android correctly refuses to "downgrade" over a newer sideloaded build, and since the failure happens at session verification (before `AppInstaller`'s receiver would even be invoked), nothing gets recorded either - it'll keep retrying the same doomed download until "Check now" is clicked again *after* the real build is actually live on GitHub.
- **A foreground service must call `Service.startForeground()` immediately in `onCreate()`, unconditionally, before any other setup logic** - as of API 34, `Context.startForegroundService()` requires the matching `startForeground()` call to land promptly or the OS throws `ForegroundServiceDidNotStartInTimeException` and kills the app. `CommandListenerService` (the anchor service, see "Push, battery and Play") calls `startForeground()` as literally the first line of `onCreate()`, before checking whether the device is even enrolled yet.

## Established discipline

**The update fence's release code is never removed** (handy step 11): a phone that updated into a build carries that build's fence record, and every later build must still be able to release it - keep `UpdateFencePlan.kt`'s prefs file, keys, v1 parse and the release path, and only ever add keys.

**Never install a locally-built APK on a kid's phone.** Production installs come from GitHub Releases built by the root `.github/workflows/launcher.yml` (it runs with `working-directory: launcher`; `launcher-build` runs only when `launcher/`, the workflow or the build-tsnet action changed, and `launcher-ci` - always run - is the check to require): pushes and PRs only build and test (debug APK as a workflow artifact, unsigned release, lint, unit tests - no secrets, nothing published). A tag `launcher-vX.Y.Z` on a commit that is on `master`/`main` runs `launcher-release-build` (versionName `X.Y.Z`, versionCode `X*1_000_000 + Y*1_000 + Z`, the same formula as the old repo's `vX.Y.Z` tags) (unsigned release APK, no secrets), then `launcher-release-sign` (in the protected GitHub Environment `release`, deployment rule: tags `launcher-v*`, which holds `ANDROID_RELEASE_KEYSTORE_B64`/`_PASSWORD`/`ANDROID_RELEASE_KEY_ALIAS`; no checkout, no Gradle - zipalign + apksigner only; fails unless the cert SHA-256 equals the repo variable `RELEASE_CERT_SHA256` and the APK isn't debuggable; the keystore is deleted in an `always()` step), then `launcher-release-publish` (a normal GitHub Release with the stable asset name `kids-launcher-mdm.apk` + `.sha256`, so `releases/latest/download/kids-launcher-mdm.apk` is a permanent URL for the provisioning QR and the server's self-update row - server releases share the repo but are never marked latest). `launcher-vX.Y.Z-rc.N` tags go through the same jobs but publish a **prerelease that never becomes `latest`** (versionCode = the final release's code minus 1, so it installs over the previous release and the final installs over it). tsnet, anet and gomobile are pinned in `mobile/go.mod`/`go.sum` (`GOMOBILE_VERSION` at the top of the workflow must match); the tsnet build lives in the composite action `../.github/actions/build-tsnet` (root of the monorepo). Third-party actions are pinned by SHA; never add `pull_request_target`. Upstream's rolling `pre-release` debug release and its `ANDROID_DEBUG_KEYSTORE` secret are not used in this fork. Before every `adb install`, `apksigner verify --print-certs` the downloaded APK against `RELEASE_CERT_SHA256`.

## Architecture change in progress (2026-08-07): on-device DNS filtering + embedded tsnet

**The DoT-to-Pi Private DNS approach described in the section below is being replaced.** Confirmed live it hit a hard Android limitation: `setGlobalPrivateDnsModeSpecifiedHost`'s strict-mode bootstrap resolution structurally cannot resolve a Tailscale MagicDNS (`*.ts.net`) hostname (Android's private-DNS validation uses the network's own DHCP/underlying DNS for that one lookup, which can never know about `*.ts.net`) - this caused intermittent but real DNS breakage, confirmed via `NetworkMonitor: Strict mode hostname resolution ... UnknownHostException` and reproduced live via `curl: Could not resolve host` for the app's own server calls. Fixing that properly would need a real public domain + ACME DNS-01 automation on the Pi - real ongoing infrastructure for what should be a simple feature.

**New direction**: ad/content blocking moves fully on-device via the launcher's own `VpnService` (DNS66/RethinkDNS-style local packet filtering - not yet built, see `kid-phone-server`'s CLAUDE.md Phase C/D), and the standalone Tailscale app is being replaced by embedding Tailscale's `tsnet` library directly into the launcher via `gomobile bind`, so the launcher's own `VpnService` can be the device's only VPN (Android only allows one) while still reaching the server over the tailnet.

**Embedding tsnet - two real gobind limitations hit and worked around, confirmed via CI + `javap` on the actual built `.aar`, not guessed:**
- Go 1.24+ requires build tools (`gomobile`/`gobind`) to be declared via a `tool` directive in the *target* module's own `go.mod`, not just `go install`'d globally on the build machine - see the `tool` directive in `mobile/go.mod` (committed, with every other module version pinned in `go.sum`).
- `gobind` cannot bind `tsnet.Server` directly - several of its methods (`Loopback` in particular) return more values than gobind's Java bridge supports (zero-or-one value plus an optional error, no more). Fixed with `mobile/tsembed`, a thin wrapper exposing only a gobind-compatible surface (`Up`/`StartProxy`/`ProxyCredential`/`Close`), calling tsnet's richer API internally in plain Go. This turned out to be the *right* design anyway, not just a workaround: `Loopback()`'s local SOCKS5 proxy is tsnet's own documented mechanism for embedding into a non-Go program, so `TsnetClient.kt` talks to it via `java.net.Proxy`/`java.net.Authenticator` (confirmed via tsnet's own docs: the proxy always expects username `"tsnet"`, with the per-session `proxyCred` as password) rather than needing any Go network type bridged into Java at all.

**Current state**: CI builds `tsnet.aar` successfully (arm64-only) and it links into the app; `TsnetClient.kt` and `MdmApi.createMdmApi` are wired so sync traffic routes through the embedded tailnet whenever a Tailscale auth key is configured (Settings entry, `mdm.tailscale_auth_key` - a parent-generated Tailscale reusable pre-auth key, entered once). **Confirmed live and working on both test phones (2026-08-07)** - policy sync succeeds over the embedded tailnet with the standalone Tailscale app not required for this path. Getting there required three real bugs found via live logcat, not guessed:
- **`panic: no safe place found to store log state`** - `tsnet.Server.Start` calls `logpolicy.LogsDir()` internally (separate from `Server.Dir`), which searches `TS_LOGS_DIR`, platform defaults, `os.UserCacheDir()`, cwd, then a temp dir, and panics if none work. All fail on Android (no platform default, no `$HOME` for `UserCacheDir`, unwritable cwd) - this crashed the whole app process in a loop (`SIGABRT`, `CommandListenerService`'s restart-on-crash kept re-triggering it every ~30s). Fixed in `mobile/tsembed/tsembed.go`'s `New()` by setting `TS_LOGS_DIR` to a subdir of the already-writable `stateDir` before constructing the server.
- **`TsnetClient.connect()` cached its `Client` on the first call per process and never rebuilt it** - so changing the auth key in Settings had no effect until a full app restart, since the Go-side `tsnet.Server.AuthKey` field is only set at construction. Fixed by tracking the `(hostname, authKey, stateDir)` the current client was built with and rebuilding when they change (see `TsnetClient.kt`).
- **`netlinkrib: permission denied` during the actual tailnet-join/route-setup step reappeared intermittently even after the earlier interface-enumeration fix** (`netmon.RegisterInterfaceGetter` + `github.com/wlynxg/anet`) - turned out to only manifest transiently on some cold starts; a retry (new sync cycle / process restart) got past it cleanly both times it was hit live. Not fully root-caused past "some other net.Interfaces()-calling code path than the one already patched" - watch for a repeat before treating this as fully resolved.
- Also confirmed: an invalid/stale auth key produces a clean `tsnet.Up: backend: invalid key: API key does not exist` from Tailscale's control server - don't misdiagnose that as a code bug. Hand-typing a ~57-character `tskey-auth-...` key on-device is genuinely error-prone; copying it from the Tailscale admin console opened in the phone's own browser (rather than retyping from another device) avoids transcription mistakes entirely. A QR-code/interactive-login flow (surfacing `tsnet`'s browser login URL instead of requiring a static pre-auth key) was raised as a real future improvement, not yet built.

The `VpnService`-based local DNS filter itself (the actual replacement for DoT-to-Pi blocking, Phase C) is built but not yet live-tested. **Phase D shipped 2026-08-08, live-verified on the Pixel**: `KidVpnService.start()`/`TsnetClient.connectFromPreferences()` are both now called unconditionally from `Application.onCreate()` (each fails soft if not ready yet - no VPN consent granted, no auth key configured - and self-heals: `KidVpnService` via Android's own always-on-VPN service management once consent is granted, `TsnetClient` via `MdmSyncWorker`'s retry-until-connected call every sync cycle). `applyPrivateDnsLock` is simplified to unconditionally lock Opportunistic mode (never a specific host - see "Current status (2026-08-06)" below for the retired hostname-locking behavior this replaced) + `DISALLOW_CONFIG_PRIVATE_DNS`, on every `apply()`, not gated on any policy field. All Tailscale-app-specific code is deleted: the `TAILSCALE_PACKAGE` constant/suspend-exemption, the `ForceEnabled`/`ExitNodeID` managed-config push, and the client-side `PolicyResponse` fields (`requireTailscale`, `tailscaleExitNodeId`, `forcePrivateDnsToPi`) are all gone.

**`AppEnforcer.applyVpnRestrictions` calls `setAlwaysOnVpnPackage` pointed at the launcher's own package with lockdown OFF - a real live bug caught on the very first test, not a hypothetical.** The initial version enabled lockdown, reasoning that `KidVpnService` never capturing general traffic (only its one fake-DNS-server route, by design - see that class's doc comment) meant there was no split-tunnel gap for lockdown to strand anything in. That reasoning was wrong: `dumpsys connectivity` showed that once this VPN becomes the system default network, lockdown forces *every app's* traffic onto it regardless of what routes it declares - and since `KidVpnService` deliberately has no general/default route, general internet connectivity broke device-wide immediately (confirmed via the VPN network's captured routes: only the DNS-server address plus an explicit `::/0 unreachable`). This is the identical failure mode to the old Tailscale-without-an-exit-node bug (`github.com/tailscale/tailscale#12925`) that already motivated gating lockdown on an exit node elsewhere in this file - except here there's no equivalent "configure something broader" fix to gate on, since narrow routing is `KidVpnService`'s permanent design, not a transient unconfigured state. Lockdown must stay off for this VPN, full stop. Without it, Android's always-on designation still auto-restarts the service and still blocks a kid from disabling it via Settings; the only cost is DNS briefly going unfiltered through the OS's normal path if the service is ever down - an acceptable gap next to bricking the device.

Also found and fixed on the same test pass: **`CommandListenerService`'s SSE `OkHttpClient` was never wired to `TsnetClient`'s SOCKS5 proxy at all**, and was cached via `by lazy` (the same staleness class of bug already fixed once in `TsnetClient.connect()` itself). It only ever worked before because the standalone Tailscale app provided OS-level MagicDNS/routing for the server's tailnet-only hostname - once `KidVpnService` became the device's sole VPN, that stopped being available, and the command stream failed to connect indefinitely ("Command stream connection failed, reconnecting" looping). Fixed by building a fresh, proxy-aware client on every `connect()`/reconnect attempt, mirroring `createMdmApi`.

**Phase E (server-side, retiring `dns_engine.rs`'s live DNS listener) and the `require_tailscale`/`tailscale_exit_node_id`/`dns_filter_settings.enabled` cleanup are both done** - see `kid-phone-server`'s own CLAUDE.md for the Phase E writeup. In their place: `device_policy.vpn_filter_enabled` (default on), a real per-device admin toggle for `KidVpnService` itself, surfaced as the "Web filter" switch on the phone's Web Filter page in the PWA (`/devices/{id}/filter`, design 31 step 5) and threaded through `PolicyResponse.vpnFilterEnabled` to `AppEnforcer.applyVpnRestrictions`, which starts/stops the service and sets/clears the always-on-VPN designation to match. The on-device "pause all restrictions" kill-switch and the offline-override PIN both force this off too while active (not just the admin toggle) - confirmed live this needed fixing once already: an earlier version deliberately excluded `vpnFilterEnabled` from that "fully open" treatment, reasoning an access-restriction escape hatch shouldn't override a parent's separate content-filtering choice - wrong in practice, since the whole point of those overrides is a guaranteed working, unblocked device when something's wrong (which can include the VPN/filter itself).

**A real ANR was caught and fixed getting the toggle working**: `SettingsFragmentLauncher`'s "pause all restrictions" listener has always called `AppEnforcer.apply()` directly inside a main-thread `view.post{}` block - previously cheap enough (DevicePolicyManager Binder calls) not to matter, but once `applyVpnRestrictions` started (re)starting `KidVpnService`, whose `onCreate()` does a synchronous blocklist-file read (`DnsFilterEngine.loadFromDisk`), this froze the UI thread for several seconds (confirmed live: `Davey! duration=3876ms`, 230 skipped frames) and got the process killed. Fixed by having the posted block hand off to a background coroutine instead of running `apply()`/`reevaluateLockReasonFromCache()` itself - matches every other `AppEnforcer.apply()` caller in the codebase, which were already off the main thread.

**Confirmed live and fully working on both test phones (Pixel 4a 5G, Moto G Play) as of 2026-08-08**: ad-blocking, policy sync, the new per-device filter toggle (both the server checkbox and the local pause-restrictions switch), and the blocked-domain log at `/dns/log` all verified end to end. Not yet built (deliberately deferred, tracked as a backlog task): the QR-code/interactive-login flow for the tsnet auth key mentioned above. Also not yet cleaned up: the server's `com.tailscale.ipn` tracked-app row still silently auto-updates the now-unused standalone Tailscale app - harmless, minor, low priority.

## Sideload blocking + instant suspend-on-install (2026-08-08)

**`UserManager.DISALLOW_INSTALL_APPS` is the wrong tool for "block new app installs but let already-installed apps keep updating" - its own AOSP javadoc says it "also prevents device owners and profile owners installing apps."** Confirmed by reading the actual source (`frameworks/base/core/java/android/os/UserManager.java`), not assumed - this restriction is a blanket block with no carve-out for the device owner's own installs, so it would have broken this app's own `AppInstaller.kt`/`PackageInstaller`-based tracked-app pushes too. The Android-intended tool for "curated list of installable apps, but keep auto-updating approved ones" is Android Enterprise's Managed Google Play app allowlist - not usable here, since it needs real Google Play Services + Play EMM API enrollment, doesn't exist on GrapheneOS at all, and conflicts with this project's deliberate avoid-Google-infrastructure design.

**What's actually built instead, in `AppEnforcer.kt`:**
- `applySideloadRestriction` sets `DISALLOW_INSTALL_UNKNOWN_SOURCES` + `DISALLOW_INSTALL_UNKNOWN_SOURCES_GLOBALLY`, lifted while an offline override or the pause-restrictions kill-switch is active (see the standing rule below - the first version of this didn't, confirmed live as a real gap, fixed same-day) - blocks installing an APK downloaded via an allowlisted browser (or any other non-store source), while leaving the device's own app store (Play Store / GrapheneOS's, where present) completely untouched for both fresh installs and updates, and not touching this app's own privileged installs either - "unknown sources" restrictions only gate the user-facing install-permission flow neither of those paths goes through.
- `enforceOnNewPackage` reacts to a single newly-installed package **immediately** (suspends/hides it if not on the current allowlist) rather than waiting for the next full `apply()` cycle, which could be up to the 5-minute periodic-sync backstop away. Wired to `Application.kt`'s `LauncherApps.Callback.onPackageAdded` - an existing, already-registered callback that fires the instant Android finishes any install, on-device, with zero network round-trip, regardless of whether the app came from a store or (for anything installed before the sideload restriction above was ever applied) a sideloaded APK. Dispatched onto a background coroutine from the callback, not run inline - `onPackageAdded` fires on the main thread by default, and this does `DevicePolicyManager` Binder calls, which is exactly the class of mistake that caused the ANR described above. Already respects the same overrides independently (checks them itself before acting).

Together: an app store install of something not on the allowlist would still need the admin to explicitly add it before it stays usable (same as it always did), but now becomes unusable within moments of installing rather than surviving until the next sync; a sideloaded APK can't be installed at all once the restriction is in place. Neither is a true "you literally cannot install this" guarantee before the fact for the store-install case - that guarantee doesn't exist without Managed Google Play - but it closes the practical gap to something close to instant.

**Standing rule, going forward: every restriction added to `AppEnforcer` must be liftable via the offline-override PIN / pause-restrictions kill-switch, unless explicitly told otherwise for that specific case.** The call rules (see "Calls & SMS") are such an explicit exception: the override and pause never open calls or SMS. The hardening switches (see "Hardening (handy step 4)") are the second one: only the server lifts them. `applyPrivateDnsLock` predates this rule and is the other deliberate exception on record (still unconditional - see its own doc comment for why); don't treat it as a precedent for a *new* restriction without checking first. The underlying reasoning, confirmed live twice now (once for the VPN filter toggle, once for this sideload restriction): the whole point of those overrides is a guaranteed, fully-unblocked device when something's wrong, and a parent should never find a restriction they can't reach through their own offline PIN.

## A custom DNS server with a parent-chosen backup (design 36 steps 1-2, `docs/design/36-custom-dns.md`, at the monorepo root)

- **What it does**: with Settings › Web Filter › "Custom server" the VPN forwards every query **the phone's lists let
  through** (FCM/Spotify exemptions and `BlockedEventLog` unchanged - the lists always block first) to the parent's
  server - DoH or DoT, by name or IP - and, only while that server as a whole is unhealthy, to the parent's backup.
  A failing backup drops the query as a failing Cloudflare does (no third tier); never plain DNS, never unfiltered.
  Every connection is a `protect()`ed socket on the phone's current network, **never through tsnet** (a home-network
  server works on the home Wi-Fi, the backup answers elsewhere). Without a custom server nothing changed:
  `DnsFilterEngine.resolveProvider` is today's DoT to Cloudflare/Quad9 (now through `resolveDoT`, same timeouts).
- **Policy and pref** (step 1's wire): `PolicyResponse.dnsUpstream` is raw `JsonElement?` read field by field by the
  pure `server/CustomUpstream.kt` `customUpstreamFrom` (kind `doh` with an `https://` URL OkHttp parses, or `dot` with
  a host and a port 1-65535, a numeric `rev`, a backup passing the same check - anything else is `null` = the provider;
  `PolicyResponseCompatTest`). `storeAcceptedPolicy` writes `dns_upstream_provider` and `dns_upstream_custom`
  (`customUpstreamPref`: the raw JSON when valid, else removed) in the policy's one `commit()`; a decode failure or a
  rejected policy never touches either; not in `LastEnforcedPlan`. Then `DnsFilterEngine.setCustomUpstream` (memory,
  `@Volatile`; `loadFromDisk` reads the pref at VPN start, so a reboot offline keeps the last accepted servers) tells
  the running VPN (`onCustomChanged`). `CustomUpstreamPrefTest` pins the one writer.
- **`server/CustomDns.kt`** (glue, one per config while the VPN is up; `KidVpnService.syncCustom` builds a new one for
  new servers - fresh state, fresh client - and `close()`s the old): routes a query, runs the canary and the
  bootstrap look-ups, relays. The backup's answer is relayed as is; the backup's outcomes never touch the state.
- **The rule** (pure `server/UpstreamChooser.kt`, state `ChooserState` in one `AtomicReference` changed by CAS): an
  attempt at the primary is an `Answer` (relayed - NXDOMAIN and `0.0.0.0` included), a `Transport` failure (no
  address, connect, TLS, HTTP, a stream closed or silent before the request was written - a period starts: backup for
  60 s doubling to 15 min, `gen` up so a burst counts once) or `Odd` (REFUSED, SERVFAIL, silence after the request was
  written). `Odd` asks the canary (`. IN NS` to the primary, 2 s, one in flight, verdict kept 60 s): a healthy canary
  makes the name's own outcome stand - **REFUSED is the phone's NODATA (`blockedResponse`), SERVFAIL/silence a
  SERVFAIL, never the backup for that name** -; a failed one is a transport failure (`refused` for a REFUSED canary,
  AdGuard Home's answer to a client id it doesn't allow). A query that gives up waiting for another's canary leaves
  the state alone and answers as from a healthy server. One ~4.8 s deadline per query (`QUERY_DEADLINE_MS`: primary
  2.5 s, canary 1-2 s, backup the rest, 1.3-2.5 s) keeps a failed canary's query inside the stub's first try. In a period one query per back-off probes the primary
  (`probing`), the rest go to the backup. `reset` (a network reset or new servers) tries the primary at once.
  Battery: one probe per back-off, one canary per 60 s at most.
- **Transport** (`server/UpstreamTransport.kt`): `resolveDoT(query, addresses, host, port, budget, protect)` - at most
  two addresses, IPv4 first, one budget (1.5 s connect, 2.5 s in all for the parent's servers), the next address only
  while nothing was written; a name gets SNI + endpoint identification, an IP no SNI and the default hostname
  verifier on the IP after the handshake. DoH: `buildDohClient` - **one OkHttpClient per `CustomDns`, from a fresh
  `OkHttpClient.Builder()` (never `newBuilder()` of the API/SSE clients, which carry tsnet's SOCKS proxy)**,
  `Proxy.NO_PROXY`, `ProtectedSocketFactory` (sockets protected before they connect), `BootstrapDns` as its `Dns`,
  1.5 s connect / 2.5 s call, no redirects, no cache, no cookies, system CAs; a per-call `EventListener` (`CallMarks`)
  splits a timeout at the written request. POST `application/dns-message`, ID 0 out, the query's ID back in; a
  response that isn't 200 + `application/dns-message` (parameters ignored) + <= 65535 bytes + parsable is `http`.
  Pool evicted on a network reset and on close.
- **Bootstrap** (`server/BootstrapDns.kt`): an IP literal is itself (`ipLiteral` parses it into bytes - never
  `InetAddress.getByName`, which would resolve a malformed one through our own VPN), `cloudflare-dns.com` is
  `1.1.1.1`; a name is A then AAAA through the bootstrap resolvers (`bootstrapResolvers`: the backup if it is an IP,
  the primary if it is, then Cloudflare `1.1.1.1` DoT; the look-up - never a query - falls through to the next on a
  transport failure or silence, and a step that failed for A is skipped for AAAA, so a home-IP primary away from home
  still lets a backup by name be found), never the system resolver and never through the lists or the chooser, 1 s
  connect (DoH too, per call from its `Budget`), 2 s in all. `BootstrapCache` (memory): the CNAME chain's final name,
  TTL clamped 5 min-24 h, stale served while one refresh runs and kept when it fails, one look-up per name at a time,
  a failed look-up (stale or with nothing cached) retried after 30 s or a network reset. Both
  names are looked up when a config loads. A primary with no address yet sends that query to the backup (no failure);
  nothing at all after its look-up is a `bootstrap` period (not stepped again inside a period). A backup with no address drops the query.
- **Network reset**: `KidVpnService` registers `registerBestMatchingNetworkCallback` (INTERNET + NOT_VPN; the VPN is
  its own default network) and resets on the pure `networkChanged` (another network, or one that gained VALIDATED -
  a captive portal logged in); unregistered in `stopSelfCleanly`. Never set underlying networks
  (`VpnMeteredInvariantTest`); lockdown stays off.
- **Status**: `StatusReportRequest.dnsUpstream` = `KidVpnService.dnsUpstreamReport()` - only while the VPN runs with a
  custom server: `{rev, in_use: custom|backup, since_ms (wall clock, from elapsed time), reason (backup only):
  bootstrap|connect|tls|http|refused|timeout}`, never an address (`upstreamReport`; contract
  `dns_upstream_status.json`, byte-identical with `../server/testdata/`, `DnsUpstreamStatusTest`,
  `UpstreamChooserTest`). Capability `dns_custom_v1` in `STATUS_CAPABILITIES`.
- **Secrets**: both targets may hold an AdGuard Home client id. `CustomUpstream`/`UpstreamTarget` `toString`s are
  redacted; log lines name modes, kinds, reasons, counts and exception classes only (never `e.message`, which OkHttp
  fills with the URL) - `CustomUpstreamPrefTest` scans the log calls; the policy decode failure and a corrupt cache are
  logged by exception class only (`PolicyGate`: a `JsonDecodingException` quotes the input).
- Tests: `UpstreamChooserTest` (every transition, the burst, the back-off cap, the canary verdicts, reset, the outcome
  mapping, `networkChanged`, the status field against the contract), `CustomDnsTest` (the glue with a fake transport:
  backup DoT/DoH, its failure leaving the state, REFUSED/silence from a healthy server, the canary reused and its
  waiter, reset, the bootstrap glue and its fall-through), `CustomDnsGuardsTest` (the lists first, the DoH client's
  protected sockets and no proxy, no status field once the VPN is off),
  `BootstrapResolverTest`, `DohMessageTest`, `CustomUpstreamPrefTest`, `PolicyResponseCompatTest`,
  `DnsUpstreamStatusTest`.
- **Not device-tested**: a real DoH/DoT server through the protected sockets (emulator check `docs/testing/emulator.md`
  §6m), a LAN server on the home Wi-Fi then away, a network that blocks 853, the canary against AdGuard Home's REFUSED
  for a removed client id, Wi-Fi/mobile resets on the Jelly Star. Step 3 (DoH on 443 when 853 is blocked, a disk
  cache for the bootstrap) is not built.

## MY_PACKAGE_REPLACED (2026-08-15)

**This app had no `MY_PACKAGE_REPLACED` handling at all (found 2026-08-15), so any in-place update - the app's own silent self-update, or a plain `adb install -r` - left `CommandListenerService` (and every background service it owns) dead until the next physical unlock.** Confirmed live: reinstalling over the running app killed the process as expected, but nothing relaunched it - `HomeActivity` doesn't resolve and no service restarts while the device sits at its own ordinary lock screen, since this app isn't direct-boot-aware and Android doesn't eagerly relaunch a killed pinned-Home-app process behind the keyguard just because it exists. This is a real, meaningful reachability gap for a device whose whole point is being reachable: a self-update landing while the phone is locked in a pocket would silently drop command-push, sync, notifications until someone next unlocks it. Fixed with `server/PackageReplacedReceiver.kt`, a new manifest receiver (`exported="false"` is safe here despite the implicit-action filter, since `MY_PACKAGE_REPLACED` is a protected broadcast only the OS can send) that calls `CommandListenerService.start()`/`KidVpnService.start()` on receipt - Android cold-starts the app specifically to deliver this broadcast, even while locked, as long as it's not a pre-first-unlock boot (which it structurally can't be here - the OS couldn't have just replaced the APK otherwise). Deliberately does **not** touch `TsnetClient` from this receiver - see `Application.onCreate`'s own doc comment on why tsnet only ever starts from `HomeActivity`'s first `onResume()`, given its real native-crash history on this project; tailnet/kid-phone-server reachability still waits for the next actual unlock after an update, only the tsnet-independent pieces come back immediately. **Confirmed live (2026-08-15/16), twice**: `adb install -r` over the running, locked app cold-started the process specifically for `PackageReplacedReceiver` within seconds each time, with `CommandListenerService` back up before any physical unlock.

## Current status (2026-08-08, `v0.15.0`/versionCode 100)

Everything below "Historical" in this section predates and is superseded by this line - kept for the incident-history detail, not as a description of the current app. Current state: on-device DNS filtering + embedded tsnet fully replaced the old DoT-to-Pi approach (Phase A-E, see above); the Apps tab was reworked this session into a global catalog with real per-device install scoping (`device_tracked_apps` on the server), including auto-allowlisting a selected app and silently uninstalling one that's deselected; a real concurrency bug in `performMdmSync` (three independent trigger points racing on the same shared cache file, found via live `adb logcat`, not guessed) is fixed with a `syncMutex`; background installs/updates now show a progress notification; and kiosk mode now defaults on for a newly enrolled device (server-side change, `kid-phone-server`'s `create_device`) rather than starting wide open. Confirmed live on both test phones (Pixel 4a 5G GrapheneOS, Moto G Play).

**Historical - superseded by Phase D (2026-08-08), kept for context on why the design looks the way it does**: `AppEnforcer.applyPrivateDnsLock` used to lock Android's system Private DNS to the server's own hostname via `DevicePolicyManager.setGlobalPrivateDnsModeSpecifiedHost` + `UserManager.DISALLOW_CONFIG_PRIVATE_DNS`, whenever `PolicyResponse.forcePrivateDnsToPi` was true (mirroring the server's global DNS/Filters on/off toggle). Built to fix a real live-testing finding: plain port-53 DNS interception (the original DNS/Filters design) turned out to have too many independent bypasses to rely on alone - exit-node routing not actually being engaged, Android's own Private DNS or a browser's DNS-over-HTTPS routing around port 53 entirely, and Tailscale's own MagicDNS override intercepting queries first. Deliberately failed closed if the server became unreachable (confirmed acceptable - the existing offline-override PIN / Settings kill-switch already provide full-offline recovery, and there's no unblocked-internet fallback for a kid to land in). This whole approach (hostname-specific Private DNS pointed at the Pi) is gone as of Phase D - see the on-device-filtering migration section above for what replaced it.

**Also historical, same reason as above**: `setGlobalPrivateDnsModeSpecifiedHost` (unlike `setGlobalPrivateDnsModeOpportunistic`, which the current code uses) returns an `Int` status, not `void` - this mattered a lot when the code called it, since a first live test showed `DISALLOW_CONFIG_PRIVATE_DNS` correctly applied ("blocked by admin" in Settings) but `private_dns_mode` (checked directly via `adb shell settings get global private_dns_mode`) still reading `opportunistic`, not `hostname` - Android actively tests connectivity to the specified host before accepting "specified host" mode, and silently keeps whatever mode was already set if that test fails. Not relevant to the current Opportunistic-only code, but worth remembering if a specific-host lock is ever reintroduced for something else.

**One known hole, deliberately not addressed yet**: a browser's own independent DNS-over-HTTPS (e.g. Chrome's "Use secure DNS") can't be blocked by any of the above, since a VPN/DNS-level lock can't distinguish "this HTTPS packet is a DNS query" from any other HTTPS traffic without breaking TLS. Chrome specifically supports an Android Enterprise managed-config key (`DnsOverHttpsMode`) that could lock this via `setApplicationRestrictions`, but this wasn't built - the primary browser in use (Vanadium, GrapheneOS's own) already had this off and isn't Play-Store/Enterprise-managed at all, so there's no equivalent lock available for it anyway.

**`v0.8.0`: the periodic backstop sync moved from a WorkManager `OneTimeWorkRequest` chain to a timer inside `CommandListenerService` itself** (since handy step 7 a while-idle `BackstopAlarm` instead - the Handler timer only ran because the 15 s SSE keepalive kept waking the phone). Confirmed live on both real devices: overnight, with screens off, neither phone self-updated on its own even though a new release had been sitting on the server for hours - both needed a manual "Sync now" to unstick. Most likely cause: Android's Doze/battery-optimization deferring the underlying JobScheduler dispatch that WorkManager relies on, and WorkManager isn't inherently exempt from that. `CommandListenerService` already pays the cost of an always-on foreground service (which *is* exempt from Doze, by design) to hold its SSE connection open, so it now drives the periodic sync directly off its own `Handler` timer too, instead of running a second, less-reliable scheduling mechanism alongside it. `MdmSyncWorker` is no longer a `CoroutineWorker` - the file now just holds `performMdmSync()` and its helpers; the `androidx.work` dependency was removed entirely. Not yet re-confirmed live whether this actually fixes the overnight-idle gap - the theory is sound (foreground services really are Doze-exempt) but the original WorkManager behavior was never root-caused with certainty, so watch for a repeat before treating this as fully closed.

**A second real device is now enrolled**: a Motorola Moto G Play 2024 on Tracfone/a prepaid MVNO (`adb shell dpm set-device-owner` used directly, since QR provisioning doesn't work on GMS devices - see above), package `com.kidslauncher.mdm.debug`, currently at `v0.7.9`. This surfaced two real gaps the GrapheneOS test phone never exposed:

1. **`AppEnforcer.controllablePackages()`'s old hand-maintained `SAFE_SYSTEM_PACKAGES` allowlist left almost nothing restrictable on this device** (only 4 apps showed up - Tailscale plus three coincidental package-name matches), since Chrome/Play Store/Gmail/YouTube/Maps/the manufacturer's own apps all use package names the GrapheneOS-oriented list never anticipated. Fixed in `v0.7.8` by switching to a launcher-intent check (see the gotcha entry above) - confirmed live, the real app list now shows up correctly.

2. **Resolved**: a Tracfone-branded carrier preload app (`com.tracfone.preload.accountservices`, "Device Pulse" in its UI - didn't show up under any name/package search containing "pulse" or "motorola", only found by checking `dumpsys activity activities` for the actual foreground activity) stayed reachable even when correctly excluded from the allowlist. Root-caused as two compounding factors, both now understood:
   - It's a genuinely platform-protected `/product`-partition privileged app - `dpm.setPackagesSuspended`/`setApplicationHidden` both fail for it *without throwing* (the former returns the subset of packages it couldn't act on; the latter returns a plain boolean), confirmed via the new `v0.7.9` logging (`AppEnforcer` tag: `"Platform refused to suspend/hide com.tracfone.preload.accountservices"`, reproduced on every sync). This is an Android/OEM platform limitation, not a bug - some privileged carrier/account-services apps simply cannot be suspended or hidden by any Device Owner policy.
   - The earlier "falls back to Motorola's stock launcher" symptom was very likely a side effect of the self-update reinstall loop from the same session (see the `AppInstallReceiver` gotcha above) - `startLockTask()` is only called from `HomeActivity.reconcileKioskMode()` on `onResume()`, and every self-update reinstall kills and restarts the whole process, leaving a real gap where lock-task wasn't engaged until `HomeActivity` resumed again. With that loop fixed, confirmed live: `mLockTaskModeState=LOCKED` holds continuously, the Tracfone app still shows up in the launcher's own app list (since it can't be hidden) but **tapping it is correctly blocked by lock-task pinning** - true containment doesn't depend on suspend/hide succeeding for every app, since lock-task enforcement has no privilege exceptions. Net effect: a platform-protected app staying visible-but-unopenable is expected, acceptable behavior, not a gap to close further.
