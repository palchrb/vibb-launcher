# Launcher notes: the Vibb music bridge, courier, media surfaces

Moved from launcher/CLAUDE.md on 2026-11-01.

## Vibb music: the bridge, the courier, own files (design 21 step 3, `docs/design/21-vibb-music-phase1.md` §2/§3 and 21b §5, at the monorepo root)

The launcher is the music app's (`me.vibb.music[.debug]`, `music/` in the monorepo) only way to the server. All of it is in `music/`:
- **`MusicBridgeService`**: the AIDL `me/vibb/bridge/IMusicBridge.aidl` (byte-identical with `music/`, `MusicPlanTest`; the names both apps spell are in `bridge_contract.json`, byte-identical in both apps' test resources), exported behind the launcher's own signature permission `${applicationId}.permission.MUSIC_BRIDGE`, every call checked against the caller's package and signer (`callerAllowed`; since security review S-L8 the music app is trusted - grants, managed config, nudge, budget exemption, bridge - only with the launcher's own signer, `MusicTrust`, and a release launcher trusts only `me.vibb.music`, never `.debug`). A bound service, not a ContentProvider: the launcher's own update only disconnects the player. Files go out as read-only pfds; the Storytel login (`GET /api/devices/music/storytel`) is fetched when the music app's generation isn't the policy's and answered through the callback, in memory only.
- **`MusicSync`** (in `performMdmSync` after the wallpapers, only with a music app installed, never failing a sync): only the managed config for the music app (`dpm.setApplicationRestrictions`: `v`, `managed`, `launcher_package`, `language`, `mobile_data`, `library_version`, `storytel_generation`, `volume_cap_pct` (the cap in force, 0 = none: a Sonos room is outside `STREAM_MUSIC`; pushed by `VolumeCap.refresh` from every `apply()` edge when the cap in force changed, and once per process; design 26a §5.3), and since design 30 `stream_mobile_data`, `download_mobile_data` and `storage_limit_gb` (GB, 0 = no limit), with `mobile_data` kept as both switches for an older music app - **Boolean, Int and String only**: a device owner's restrictions are dropped whole for any other type, a Long included) and its nudge. The fetch (library, changed listings with a version index, covers) runs after the sync in **`MusicCourier`**, never inside the sync lock. A `me.vibb.music.action.BRIDGE_CHANGED` nudge shares the launcher's identity (the music app checks it). It goes out when the managed config changed, and when the music app was updated in place (`onPackageChanged` -> `musicNudgeOnChange`: a catalog install, Play or adb), so the new app reports at once; the music app also nudges itself on `MY_PACKAGE_REPLACED`. Server calls go through the `MusicServer` interface only (design 22 L1 swaps the transport there). No music app installed: everything kept for it is deleted.
  - **The policy's `music` object** (`musicPolicy`, design 30 §1.3): `mobile_data` is still required; `stream_mobile_data`/`download_mobile_data` - a JSON Boolean is used, absent (an older server) falls back to `mobile_data`, anything else refuses the whole object (keep what is there); `storage_limit_gb` - absent = 2 (`DEFAULT_STORAGE_LIMIT_GB`), `null` = no limit, an integer 1..1000, anything else 2 (lenient, so it never refuses the object; qa-30-s2-code L1). A refused object keeps what is there everywhere: the managed config, no courier run, no Storytel answer, own files and `later` pictures on Wi-Fi only, and **the volume cap** - `VolumeCap` keeps the last cap read (`policyCapPct`, CE prefs `volume_cap`). `MusicSync.cachedMusicPolicy()` is the cached policy's music object, read.
- **`MusicFileDownloads`**: the parent's own audio files, one ahead of the handover (noBackupFilesDir/music_files), after the catalog's APKs (`AppDownloads.busy()`), with design 13's pure rules (`resumeAction`, `downloadGate`; Wi-Fi only unless the policy's **downloads** switch - the pure `ownFileGate(caps, MusicSync.cachedMusicPolicy(), ...)`, design 30) in `OwnFileFetch`, which asks the gate again every 1 MB of the copy (over tsnet a stream survives a move to mobile data). Two hash failures skip a file for a day. The music app copies a file, checks it and `releaseFile`s it; its `reportState` names the files it holds, which replace the handed-over marks and delete a ready copy it already has.
- **Updates**: a music app APK waits while the last `setNowPlaying` says "playing" (`MusicNowPlaying.deferInstall`, `AppDownloads`' `DEFER` outcome skips only that record for the run; "playing" is refreshed by every report, dropped when the player's process dies and ignored after 6 h without one); a pause asks for a download run when an install waits.
- **Status**: `music_state` = the music app's last report (known keys, `sonos_rooms` included: the Sonos speakers it knows, for the parent's room scope, design 26a §5.5; `audio_bytes`/`extra_bytes` since design 30 step 3a, whose presence tells the PWA the music app reads both mobile-data switches) + package, version code and `bridge` ("bound"/"unbound"); capability `music_v1`. `setNowPlaying` (CE prefs + art file, Home's snapshot) and `setForeground` (`MusicForeground`) are read by step 4 below.
- **Storytel** (design 26b, `docs/design/26b-storytel.md`): no launcher code - a Storytel entry's listing rides the courier unchanged (`libraryHead`/`listingsToFetch` pass every non-`own` entry's `items`; `MusicPlanTest` pins it with the library snapshot's Storytel entry), a book's cover is an ordinary `wantArt` hash fetched by the same `syncArt`, and the sealed login keeps phase 1's `getStorytelLogin` path; the server's gate (the phone's Storytel switch and a stored login) decides whether the entries come at all.
- **Spotify** (design 26c, `docs/design/26c-spotify.md` §6, at the monorepo root): a Spotify entry's listing rides the courier unchanged like any other (`MusicPlanTest` pins the library snapshot's entries 6 and 7, list and context mode); the launcher adds three things:
  - **The token courier** (`getSpotifyToken(callback)`, appended to `IMusicBridge.aidl` with the new `ISpotifyTokenCallback.aidl`, both byte-identical with `music/`; `check()` first like every bridge method): `POST /api/devices/music/spotify/token` through `MusicServer.spotifyToken()` (the device bearer, over tsnet) on IO within `SPOTIFY_TOKEN_TIMEOUT_MS` (10 s); the pure `SpotifyTokenCourier.spotifyTokenAnswer(httpStatus, body)` maps the answer to the callback's `status` (`bridge_contract.json` `spotify_token`: `ok`, `off`, `reauthorize`, `busy`, `unreachable`, `key`, `launcher`), the token only with `ok`, `expiresInMs` (the token's life, or `busy`'s wait), `account` (`"<id>:<generation>"`). An `ok` that isn't whole is `launcher`, as is no server set up, a transport failure or the timeout; an unknown status from a newer server passes through. **No cache, no store, no log of the body or the token** (the log lines name the exception class only; `SpotifyTokenAnswer`'s `toString` is redacted): the music app caches, one source of expiry. An older music app never calls it; an older launcher drops the oneway call and the music app times out to "trenger internett".
  - **The gated DNS exemption** (§6.2): the pure top-level `classifyDomain(blocked, domain, spotify)` (what `DnsFilterEngine.classify` runs) returns "not blocked" for FCM's hosts always and for Spotify's - a domain equal to or under a suffix, or exactly an exact host (`isSpotifyHost`) - only with `spotify`, **both before the suffix walk** (so a blocked parent such as `akamaized.net` never blocks the exact CDN host under it). The flag is `DnsFilterEngine.setSpotify(musicSpotify(policy.music))`, set **per phone** by every fresh sync before `refreshIfNeeded` (`MdmSyncWorker`) and from the cached policy when the VPN loads its list (`loadFromDisk`) - never read per packet from the policy. `musicSpotify` reads the key on its own and leniently (absent, not a boolean or no `music` object = false; a bad `spotify` never refuses the music object, a bad other field never lifts the exemption). The server drops the same hosts from that phone's delivered list and moves its `dns_filter_version` on bind and unbind. The host list (`SPOTIFY_HOST_SUFFIXES`, `SPOTIFY_EXACT_HOSTS`) is checked against `app/src/test/resources/spotify_hosts.json` (`SpotifyHostsTest`), which is byte-identical with the server's and the music app's (`MusicPlanTest`) - **provisional** until the user's DNS capture lands as one commit of the list, the constants and the comment (the three copies, the six constants on the three sides - these two among them - and their "provisional" doc comments; 26c "Release").
  - **The WebView provider is never restricted** (§6.3) - **on every phone**, Spotify or not, at every `apply()`: the music app's web player is the system WebView, so `computeEnforcementPlan`'s `neverRestrict` takes `webViewProvider` (`AppEnforcer.webViewProviderPackage()`: `WebView.getCurrentWebViewPackage()` at each `apply()`, off main); no allowlist, time rule or lock suspends or hides it (a suspended provider breaks every WebView, the launcher's own included). `controllablePackages` already skips it (a system package without a launcher icon); this is the guard. `EnforcementPlanTest` pins it.
  - **The diagnostic log** (2026-11-01, Device › Advanced's "Turn On Diagnostic Log for 15 Minutes"): the policy's `music.spotify_diag_until` (epoch seconds while it runs, else `null`) is read leniently by `spotifyDiagUntil` (a positive integer up to `Int.MAX_VALUE`, anything else 0 - never a refusal of the music object) into `MusicPolicy.spotifyDiagUntilS`, and `restrictionsFor` hands it to the music app as the managed config's `spotify_diag_until` (an Int, 0 = off; `bridge_contract.json`'s `restrictions`, byte-identical with `music/`), written like every restriction when it differs - the server's nudge brings the sync, so the music app's `VibbSpotify` log starts within seconds and stops by its own clock.
  - `music_state.spotify` (the music app's account word) passes through `musicState` like the other keys; `PolicyResponse.music` stays raw JSON (its doc names `spotify` and both readers, `musicPolicy` and `musicSpotify`). Tests: `SpotifyTokenCourierTest`, `SpotifyHostsTest`, `DnsFilterEngineTest` (the gated exemption and, by a source scan, where the flag is set), `EnforcementPlanTest`, `PolicyResponseCompatTest`, `MusicPlanTest` (the three AIDL files, the whole 13-method sequence with `getSpotifyToken` last, `spotify_token` against its constants, the host list's three copies, `musicSpotify`, and the diagnostic log's `spotifyDiagUntil` and `spotify_diag_until` restriction; `PolicyResponseCompatTest` its policy key too).

## Vibb music: episode pictures (design 27, `docs/design/27-music-episode-art.md`, at the monorepo root)

- **`wantArt(now, later)`** (appended to `IMusicBridge.aidl`, oneway; an older launcher ignores it): the music app's want set - `now` (streaming's: the playing item ±5, the queue's next 50, the playing Spotify entry's look-ahead; at most 500) and `later` (kept episodes' and Nytt's pictures, the other Spotify entries' look-ahead, and on Wi-Fi every picture of every ticked entry - the addendum of 2026-10-19), 64-hex only, at most 1000 in a call (`wantArtLists`; caps in `bridge_contract.json` `want_art`: one oneway Binder call's size, ~136 bytes a hash, ~136 KB - not a cap on the pictures: the music app names only what it lacks, so the next call names the next ones). `MusicBridgeService` stores both lists at once in `filesDir/music/want_art.json` (`MusicStore.setWantArt`), fetches the `now` pictures at once (`MusicCourier.fetchNowArt`: `nowArtToFetch`, the first `ART_PER_RUN`, beside any courier run - the playing episode's picture never waits for the next sync or behind a long Wi-Fi run) and runs the courier only when something is fetchable now (`MusicCourier.artFetchable`, QA M6).
- **The gates** (pure `artGates`/`artGatesOn`, the user's rule of 2026-10-19: pictures count as streaming): `now` where streaming is allowed - online (INTERNET + a physical transport), never roaming, unmetered or with the policy's `stream_mobile_data` (an older policy's `mobile_data`, `musicPolicy`); `later` only online and unmetered, whatever the downloads switch (qa-art-asap-code M1: the bulk is Wi-Fi only, so a want set stored on Wi-Fi fetches nothing of it after a switch to mobile data; kept episodes' pictures then wait for Wi-Fi too, the playing ones come with `now`). No readable music object: no streaming switch.
- **`MusicCourier.syncArt`** after `syncCovers`: through the cover route (`server.cover`, at most 1 MB, hash-checked), `now` first, in rounds of `ART_PER_RUN` (100) for as long as more are fetchable on this network (`fetchArtPaced`: each round reads the want set, the files and the network again, so a metered network ends the `later` part; a round that stores nothing ends it; the music app is nudged after each round, copies them and names the next) - `artToFetch` with `artToFetchOn`'s gates. At most `ART_ROUNDS_PER_RUN` (3) rounds a run: with more left (`PacedArt.more`) the courier runs again (`runAgain`), so a new library, changed listings and the own files never wait behind thousands of pictures (qa-art-asap-code M2). `ArtInFlight` keeps the `now` fetch and the courier from GETting one picture twice at once (L5). A picture is ~40-70 KB: a 1000-item feed is ~50 MB, ten rounds over four runs. An HTTP error or a wrong hash counts (`art_failures.json`; two wait a day), a network error doesn't. New art nudges (`BRIDGE_CHANGED`). Covers dir: `artToDelete` keeps the library's `covers` and the want set, so the launcher holds a picture only until the music app copied it - and on a metered network every file younger than `ART_HOLD_MS` (3 days, `artHeld`), so the bulk fetched on Wi-Fi isn't lost before the music app's next Wi-Fi sync copies it (L6). No library: the want set goes too (`clearWantArt`).
- Tests: `MusicPlanTest` (lists and caps, the gate table, `artToFetch`, the immediate `now` fetch, the paced rounds and the run's three, the in-flight set, `artToDelete` with a 1000-hash set and `artHeld`, the keep rule in `syncCovers`, the bridge methods - 13 since design 26c's `getSpotifyToken`).

## Vibb music: media surfaces and time (design 21 step 4, `docs/design/21-vibb-music-phase1.md` §3, at the monorepo root)

Pure rules in `music/MusicMediaPlan.kt` (`MusicMediaPlanTest`), `music/MusicWindow.kt` (`MusicWindowTest`, design 28), `ui/home/MusicCard.kt` (`MusicCardTest`) and `lock/LockMedia.kt` (`LockMediaTest`, `LockMediaGuardTest`, `LockMediaLayoutTest`); the glue is in `music/`.
- **Sessions** (`MusicSessions`): the music app's platform media session through `getActiveSessions(BadgeListenerService)` and its change listener, watched only while Home or the lock shows a surface. **No notification-listener access = no media surfaces** (no card, no media view; the snapshot isn't shown either). A suspended or uninstalled music app shows nothing (`shownSession`); play, next and previous look the app up again at the tap (a pause always goes), and `Application`'s `onPackagesSuspended`/`Unsuspended` re-render the surfaces (`packagesChanged`). The music app itself refuses to play while suspended.
- **The listening window** (design 28, `docs/design/28-music-card-session.md`, at the monorepo root): both surfaces show only while the session plays (`sessionPlay` PLAYING: also buffering, skipping) or for `MUSIC_LINGER_MS` (10 min) after the later of the end of play and a fresh headset - pure `musicShownUntil` (end exclusive) / `windowedSession` / `lockTileSession` (the lock's tile with its end) / `musicRecheckInMs` (`(end - now)` at least 1 ms). Stamps (`MusicListening`, `elapsedRealtime` + `BOOT_COUNT` read once per process, CE prefs `music_bridge` keys `listen_played_*`/`listen_headset_*`, loaded lazily under its lock): the end of play from the bridge (`MusicNowPlaying.store` and `playerGone` call `observePlay` before their `changed()`; `playedStampAfter`: only after a stamp valid in this boot and younger than 60 s - a stale `playing_at` opens nothing) - so a launcher restart inside the window keeps it and a reboot never shows one; a fresh headset from `registerAudioDeviceCallback` (`MusicListening.init`, from `MusicMedia.init` right after `MusicCalls.init`; wired, USB headset, A2DP, LE headset/speaker sinks - not SCO, ASHA hearing aids, LE broadcast; the devices at registration are the baseline, nothing in the 2 min after the boot or the registration counts, the same `type/address` back within 60 s isn't fresh). Listeners hear only an end of play or a fresh headset, never the 15 s playing stamp.
- **Home "Spilles nå"** (`MusicHomeCard`, `view_home_music_card.xml`, mockup HomeCard.dc.html v12): between the contacts row (or the call card) and the grid while the session plays, and inside the listening window while it is paused - else, inside the window, from the last `setNowPlaying` snapshot shown paused (back at once after a restart inside the window); outside the window nothing - a paused session never falls back to the snapshot (`musicCard(listening, bootCount)`, `MusicCardModel.hideAtElapsedMs`). Live: the button is the session's play/pause, a tap sends its `sessionActivity` (`ALLOW_IF_VISIBLE`); snapshot: both open the player (`me.vibb.music.ui.MainActivity`) with `EXTRA_RESUME` (names in `bridge_contract.json`) - after a headset, "put the buds on, press play". Active only between Home's onStart and onStop with its content shown (never LOCKED), listening to the sessions, the bridge and `MusicListening`; ticks 1/s only while playing, else one `expiry` recheck at the window's end; `resumeContent` renders it again (the recheck's delay stops in deep sleep).
- **PIN lock media view** (since design 25 the glance page's music tile - see "The lock's glance page" below): `MusicLockPanel` binds the full tile (step 4's, `lock_media_*` ids) and the compact one (`lock_media_compact_*`) on the glance page while a session is live and inside the listening window - design 28: playing, or paused within the window; one private `shown()` (the pure `lockTileSession`) for `lookUp` and `render`, and `lookUp` posts the `expiry` recheck that refits the page without the tile; never the snapshot, whose play would open the player. Since 25b-G (user decision 2026-10-12) the keypad stage has no music row - it stays plain. The glance panel decides which tile shows. It weakens nothing: only the session's play/pause/previous/next - never the music app, its session activity, a setting or a notification (`LockMediaGuardTest` scans the glue).
- **Screen time** ("listening never counts", the user's decision): `screenTimeCounts(musicListening)` - the player in front (its `setForeground`: top resumed, never in multi-window) **while it plays** (the last `setNowPlaying`, `MusicNowPlaying.playing`) doesn't count; browsing it with nothing playing does, and so does a PiP video over it. `MusicForeground` is cleared at every screen-off (its own receiver, `MusicMedia.init`) and when the token dies; it and the playing flag re-run `ScreenTimeTracker.update` on every change.
- **Time rules**: the budget lock adds `MUSIC_PACKAGES` to its usable apps (`decideTimeLock(musicApps)`; the allowlist still applies) - music plays on after the budget; a rule keeps only its own exempt apps. Before `apply()` suspends a music package its playing session is paused (`pauseBeforeSuspend`; without listener access the music app pauses itself on `MY_PACKAGE_SUSPENDED`; on a Sonos room the session's pause stays a Pause, and the music app's own `MY_PACKAGE_SUSPENDED` handling stops the speaker, design 26a §6.1).
- **Volume cap** (`VolumeCap`): the policy's `music.volume_cap_pct` (Off/90/80/70/60) while `hardeningManaged` and without the override or the pause (`capPctInForce`), refreshed by every `apply()` and read from the cache at process start; `STREAM_MUSIC` above `volumeCapIndex` (floor of max x pct, at least 1 - never mute) is set back on `VOLUME_CHANGED_ACTION`, on every output coming or going and whenever a player starts or moves to another output (`registerAudioPlaybackCallback`: each output keeps its own index), again after 1.5 s. Never `DISALLOW_ADJUST_VOLUME`. A Sonos room is outside `STREAM_MUSIC`: the music app clamps its own sets to the `volume_cap_pct` restriction (`MusicSync` above).
- **Calls** (`MusicCalls`, from `MusicMedia.init`; pure `musicCallActive`/`callHoldStep` in `MusicMediaPlan.kt`, `MusicMediaPlanTest`; design 26a §6.7): a call = a VoIP ring or call (`VoipCalls.phase`), our dialer's (`OngoingCalls`) or a system call (`managedCallActive`, never `MODE_IN_COMMUNICATION` alone), re-read on each of their changes and every audio-mode change. A call beginning while the music app has a session - playing or not (`CALL_HOLD` means "a call began", emulator round 2026-10-14 N3: the web player is often paused by Chromium before this look, and a play tapped during a call must start nothing) - sends it the custom action `CALL_HOLD`, that call ending sends `CALL_RELEASE` (only after a HOLD; names in `bridge_contract.json`, unchanged); the player decides the rest (a call that begins while nothing plays is no pause of its; it pauses what plays as its own pause, the sleep timer runs on, starts nothing during the call, plays again only what it paused) - local and Sonos playback alike. The session's playing state is read only for the log line. Needs notification-listener access (the session); without it the music app's audio-mode backstop covers a system call. `VoipCalls`, `OngoingCalls` and `VoipCallPlan` are only listened to.
- **Badge**: `badgeCounts` skips notifications with `EXTRA_MEDIA_SESSION` (a paused player's is neither ongoing nor unread; `badges/isMediaNotification` looks only at that key's presence - the listener itself still reads no extras), so the music tile shows the "N nye i Musikk" notification's `number`; `MusicSync` grants the music app `POST_NOTIFICATIONS` while a policy exists (`notificationGrantState`) - since design 52 through the list `MUSIC_RUNTIME_GRANTS` (`MusicMediaPlan.kt`, `MusicMediaPlanTest`), looped by `grantRuntimePermissions`: `POST_NOTIFICATIONS` with `notificationGrantState` (without a policy DEFAULT, the phone's choice) and `BLUETOOTH_CONNECT` with `bluetoothGrantState` (the "Spill av på" sheet's paired headphones; without a policy **DENIED** - DEFAULT would keep the grant). Each is set only when `getPermissionGrantState` differs, so nothing is granted twice; the kid sees no dialog.
- Not device-tested: design 21's "Step 4 implementation status".
