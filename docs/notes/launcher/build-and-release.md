# Launcher notes: build and release

Moved from launcher/CLAUDE.md on 2026-11-27 ("Established discipline"'s release pipeline, "Building without tsnet.aar" and "Release builds" in full; the core keeps the rules); the core file's 'Where the rest is' lists every note.

## Established discipline: the release pipeline

**Never install a locally-built APK on a kid's phone.** Production installs come from GitHub Releases built by the root `.github/workflows/launcher.yml` (it runs with `working-directory: launcher`; `launcher-build` runs only when `launcher/`, the workflow or the build-tsnet action changed, and `launcher-ci` - always run - is the check to require): pushes and PRs only build and test (debug APK as a workflow artifact, unsigned release, lint, unit tests - no secrets, nothing published). A tag `launcher-vX.Y.Z` on a commit that is on `master`/`main` runs `launcher-release-build` (versionName `X.Y.Z`, versionCode `X*10_000_000 + Y*10_000 + Z*10 + 9` by `scripts/release-version.sh` - see "Release builds") (unsigned release APK, no secrets), then `launcher-release-sign` (in the protected GitHub Environment `release`, deployment rule: tags `launcher-v*`, which holds `ANDROID_RELEASE_KEYSTORE_B64`/`_PASSWORD`/`ANDROID_RELEASE_KEY_ALIAS`; no checkout, no Gradle - zipalign + apksigner only; fails unless the cert SHA-256 equals the repo variable `RELEASE_CERT_SHA256` and the APK isn't debuggable; the keystore is deleted in an `always()` step), then `launcher-release-publish` (a normal GitHub Release with the stable asset name `kids-launcher-mdm.apk` + `.sha256`, so `releases/latest/download/kids-launcher-mdm.apk` is a permanent URL for the provisioning QR and the server's self-update row - server releases share the repo but are never marked latest). `launcher-vX.Y.Z-rc.N` tags go through the same jobs but publish a **prerelease that never becomes `latest`** (versionCode = the final release's code with the RC number 1..8 for its last digit 9, so each RC installs over the one before and the final over them all). tsnet, anet and gomobile are pinned in `mobile/go.mod`/`go.sum` (`GOMOBILE_VERSION` at the top of the workflow must match); the tsnet build lives in the composite action `../.github/actions/build-tsnet` (root of the monorepo). Third-party actions are pinned by SHA; never add `pull_request_target`. Before every `adb install`, `apksigner verify --print-certs` the downloaded APK against `RELEASE_CERT_SHA256`.

## Building without tsnet.aar

`libs/tsnet.aar` only exists where the Go + NDK toolchain ran (CI, x86_64). When it's missing, `app/build.gradle.kts` compiles `app/src/tsnetStub/java/tsembed/` into the **debug** variant instead - same API as the gomobile binding, every connect fails - so `./gradlew assembleDebug testDebugUnitTest` works on any machine; Gradle logs a warning when the stub is used. A **release** build never gets the stub, whatever the flags (security review L13): `checkReleaseHasTsnet` (a dependency of `preReleaseBuild`) fails it without the aar, and the stub isn't in the release source set anyway. CI also passes `-PrequireTsnet=true`, which fails any build without the aar. To build a release locally without Go (an APK that is never for a phone), pack the stub's classes into a throwaway `libs/tsnet.aar` (gitignored). If `mobile/tsembed`'s exported API changes, update the stub to match.

**Dependency verification** (security review L9): `gradle/verification-metadata.xml` holds the SHA-256 of every artifact the build resolves (CI's x86_64 aapt2 included, added by hand), the wrapper pins its distribution, and CI validates the wrapper jars - see the root `CLAUDE.md` "Build and test" for adding a dependency; `BuildChainTest` checks the wiring.

## Release builds

Production phones run the **release** build, package `me.vibb.launcher` (debug keeps the `.debug` suffix; only one of the two can be device owner on a phone). `app/build.gradle.kts` signs release builds when a keystore is configured: env vars `ANDROID_RELEASE_KEYSTORE_FILE`/`_PASSWORD`/`ANDROID_RELEASE_KEY_ALIAS`/`ANDROID_RELEASE_KEY_PASSWORD` (falls back to the store password), or the Gradle properties `handy.release.storeFile`/`storePassword`/`keyAlias`/`keyPassword` in `~/.gradle/gradle.properties` - never in the repo. Without one, `assembleRelease` still produces `app-release-unsigned.apk`; `-PrequireReleaseSigning=true` turns that into a build failure (release CI uses it). The release build type is not debuggable (no `run-as`). `-PversionCode`/`-PversionName` override the literals in `defaultConfig`; release CI derives them from the tag with `../scripts/release-version.sh` (`launcher-vMAJOR.MINOR.PATCH[-rc.N]` -> `MAJOR*10_000_000 + MINOR*10_000 + PATCH*10 + N`, N = the RC number 1..8 and 9 for the release, so every build has its own code and an RC installs over the RC before it by Android's own rule; MAJOR <= 199, MINOR and PATCH <= 999), so never bump the literals for a release. The first tag under the rule is `launcher-v0.36.0-rc.4` (360004) and the script refuses a lower one; the versionCode alone decides whether a build is ahead (`launcherUpdateStep`, `pendingApkCheck`, Install Now's settle), and `launcherTagVersionCode` (and the server's `install_now::launcher_tag_version_code`) read a tag's code - the shared `../contracts/core/launcher_tag_codes.json` (`SelfUpdatePlanTest`) pins both. A release launcher can't be downgraded (`INSTALL_FAILED_VERSION_DOWNGRADE`, and `adb install -r -d` needs a debuggable app), so a broken release is fixed forward under a higher tag; a mistyped high tag burns versionCodes for good. R8 only shrinks (`-dontobfuscate -dontoptimize`); `proguard-rules.pro` also keeps the gomobile (`go.**`, `tsembed.**`) and pcap4j packet classes, and line numbers. Losing the release key means no more silent self-updates and re-provisioning every phone - keep it offline and backed up.
