## Hardening (handy step 4, design `docs/design/04-hardening.md`, at the monorepo root)

- **User restrictions from server switches** (`server/Hardening.kt`, pure, `HardeningTest`; DTO `dto/HardeningPolicy.kt` = `PolicyResponse.hardening`): `DISALLOW_FACTORY_RESET`, `_ADD_USER`, `_MODIFY_ACCOUNTS`, `_CONFIG_VPN`, `_USB_FILE_TRANSFER`, `_DEBUGGING_FEATURES`, `_SAFE_BOOT`, `_CONFIG_LOCATION` (+ `setLocationEnabled(true)` first) and `_AIRPLANE_MODE` (step 5). `hardeningPlan` sets each as the server says while managed (`hardeningManaged`: the enforced policy has an allowlist, or calls are managed); a missing object or field means that switch's default (all on, **safe boot and airplane mode off**), unmanaged/never-managed clears all. **Not lifted by the offline override or the pause** - only an explicit server value or unmanaging (second exception to the standing rule). Since security review S-L11 `withFilterVpnLock` also sets `_CONFIG_VPN` while the Web filter is on without that (a filter-only phone; the parent's explicit switch off wins), and that part goes with the filter: lifted by the override and the pause. Also since then (S-L5) `DISALLOW_BLUETOOTH_SHARING` while managed, lifted by the override and the pause (`bluetoothSharingRestricted`). `AppEnforcer.applyHardening` runs last in `apply()`, after the always-on VPN. `LastEnforcedPlan` carries the switches. Never call `AppEnforcer.apply(context, null)` for an override any more - pass the enforced policy (`currentPolicyDecision().policy`), or the hardening would be cleared.
- **adb**: with `disallow_debugging_features` on (the default) adb is gone the moment the first managed policy applies - no `adb install -r` fix-forward, no logcat, no `cmd role add-role-holder`. Grant `ROLE_CALL_REDIRECTION` and `ROLE_CALL_SCREENING` before enrolling, or switch "Block USB debugging" off in the phone's Advanced › Restrictions (the device row exists before enrollment) for device work. A launcher that crash-loops before it can sync then needs a recovery-mode wipe. Safe mode repairs nothing (restrictions, suspension, blocked adb and factory reset persist there); `disallow_safe_boot` defaults off only until it is checked on the Jelly Star. Deploy order: server first, set the switches and a PIN, then the launcher (a launcher on a pre-0023 server applies the defaults) - runbook in `04-hardening.md`.
- **Schedule enforced by suspension**: `KidModeEnforcer.lockReasonNow(policy, overrideActive, now)` is the one rule for the lock (sync, offline re-checks, `apply`). While it isn't NONE, `computeEnforcementPlan(scheduleLocked = true)` suspends - but doesn't hide (`EnforcementPlan.hide` is only the apps not allowed at all; hiding drops alarms/jobs/widgets) - every controllable app but ours, the system dialer, the keyboards (`inputMethods`, always in `neverRestrict` - since design 24b only the enabled ones that are system or allowlisted) and the alarm apps (`alarmApps`, `sparedAlarmApps`: every system clock and a verified Fossify Clock - since bug 2026-11-02 always, no longer only while it holds the next alarm; spared by the lock only), whatever the allowlist, and kiosk pins only our package (plus an allowlisted system dialer while calls are unmanaged, and since bug 2026-11-02 the allowed alarm apps: an unpinned clock's ringing screen, a task of its own, was refused by lock task - the alarm rang during a school rule with no way to Stop it; the kid can now reach the clock app - alarms, timer, stopwatch - during a rule through Recents or a notification, as with the kiosk off, accepted; without the block bit the clock's task can also open unsuspended non-launchable system screens - Google Clock's Bedtime to Digital Wellbeing, "Help & feedback" (GMS Help, a WebView of help articles), the ringtone and document/photo pickers - while its links to launchable apps (Settings, Assistant, Spotify/YouTube Music, a browser, Play) are refused, those being suspended; all of it was reachable with the kiosk off already. **Device check (code QA L4/L5)**: Google Clock's Help & feedback and Bedtime during a rule; `AppEnforcer` logs "Alarm apps (spared by a rule, pinned while allowed): [...]" when the set changes - read it on the Jelly Star and the emulator, nothing but clock apps may be in it); LockActivity always shows "Emergency call" (112 via Telecom, CALL_PHONE self-granted, fallback the system dialer); the call restrictions are unchanged (allowed and emergency calls work: phone book, in-call UI and screening are ours). `shouldSuspendNewPackage` suspends new installs during the lock. `reevaluateLockReasonFromCache(context)` re-runs `apply` in the background when the lock changes; since step 6 the re-checks come from one boundary alarm and screen events, not a minute timer (see "Time rules" below). `AppEnforcer.lastEnforcedLockKey` makes a re-check re-apply until the lock is really enforced; switched-off hardening is cleared at the start of `apply()`. `AppEnforcer.apply` is `@Synchronized` - never call it on the main thread (every caller - the pause's start, the relock, the sync - runs it off main).
- **Backup to Google stays off** (Google account on the phone, runbook `docs/setup/google-account.md` at the monorepo root): `server/BackupService.kt` with the pure `backupServiceAction` (`Hardening.kt`, `HardeningTest`). Early in every `apply()` (right after `clearHardening`) while `hardeningManaged`, it reads `dpm.isBackupServiceEnabled(admin)` and, if on, calls `setBackupServiceEnabled(admin, false)` - AOSP switches the service off at `set-device-owner` and only the device owner can switch it on. There is **no action that switches it on**, no server switch, the override/pause don't lift it and unmanaging leaves it as it is; never on the main thread (it refuses), every exception caught and logged. `BackupServiceInvariantsTest` scans every non-test source set: each mention of the setter must be a plain call whose last argument is the literal `false` (no variable, named argument, method reference or reflection). Status `backup_service_enabled` (`BackupService.reportedState`; null = not device owner/unreadable, then left out of the JSON).
- **Never call `setUserControlDisabledPackages`** (launcher round 7 §2, `docs/design/r7-launcher-small-items.md`; the round's battery-state report was removed on 2026-10-20): a package on that list can't be suspended, hidden or uninstalled by the device owner either (AOSP `SuspendPackageHelper` "protected package", `setApplicationHiddenSettingAsUser`, `DeletePackageHelper`; qa-l7-b-code finding 1), so time rules, the budget, the camera lock and the update fence would fail open for those apps. `BackupServiceInvariantsTest` scans the production sources for it.
- **Device checks** are in `04-hardening.md` (restrictions in Settings, VPN with `DISALLOW_CONFIG_VPN`, location lock vs `WifiNetworksActivity`, suspension at the schedule edges incl. inside an app and from Recents, calls at bedtime).

## Emulator fixes: kiosk app block, emergency dialer, role hand-back (handy step 9 part B, design `docs/design/09-sms-and-fixes.md`, at the monorepo root)

Part A (SMS allowlist via the SMS role) is **postponed (user, 2026-10-05)**: SMS stays on/off only, as in step 2.
- **Kiosk app block** (B4): `PolicyResponse.blockActivityStart` (server switch, default on; the server masks bit 64 out of `lock_task_features`, so it only ever comes from this key) adds `LOCK_TASK_FEATURE_BLOCK_ACTIVITY_START_IN_TASK` (`lockTaskFeatures()` in `server/LockTaskHelpers.kt`): while kiosk is on every activity start of a non-pinned package becomes BlockedAppActivity - explicit intents into Play, Google sign-in/payment sheets, Settings. That path has **no emergency exemption**, so `AppEnforcer.resolveLockTaskHelpers` resolves system helpers from intents on every apply (emergency dialer, Telecom via `ACTION_CALL`, permission controller via `REQUEST_PERMISSIONS`/the role request, `ACTION_CHOOSER` = intentresolver, `ACTION_OPEN_DOCUMENT`, `ACTION_PICK_IMAGES`, the `SMS_CB_RECEIVED` receiver, since 16d the recents provider) and pure `lockTaskHelpers` keeps FLAG_SYSTEM ones minus Settings, the camera, the system dialer (its pinning stays under the call rules) and Play core; the plan pins them only with the bit, also during a time-rule lock (`LockTaskHelpersTest`). `LastEnforcedPlan` carries the switch. The platform refusing to suspend the Play Store (verifier on GMS) is recorded (`PlayRuntime.storeSuspendable`) and reported as `playStoreSuspendable`.
- **Emergency** (QA 09 #1): `LockActivity` and the phone book's 112 tile fall back, when Telecom refuses, to `EmergencyDialer.open` - an explicit intent (`android.intent.action.DIAL_EMERGENCY`, then `com.android.phone.EmergencyDialer.DIAL`) to the resolved **system** component (`chooseEmergencyDialer`), which must be lock-task permitted. Never `ACTION_DIAL` to the default dialer (not pinned while calls are managed or a rule blocks calls).
- **Role hand-back without a kill** (B2, QA 09 #6/#11): before the dialer role changes (and whenever calls are managed) every role-grantable permission our manifest requests (`ownPermissionsToFix`, `server/OwnPermissions.kt`) is granted by policy via `QuickControls.fixOwnPermission`, decided on `getPermissionGrantState` - `selfGrantPermission` skips anything `checkSelfPermission` reports granted, including role-owned grants that a hand-back revokes (killing HOME/kiosk/call path). `DISALLOW_CONFIG_DEFAULT_APPS` is re-set in the same pass; after a TAKE/RELEASE with kiosk on, Home is brought to front. `KEYGUARD_DISABLE_SECURE_CAMERA` is ORed in while managed (`keyguardDisabledFeatures`, only our bit cleared) - useless without a screen-lock PIN; runbook: camera gesture off before enrolling (`docs/testing/emulator.md`); since 2026-10-06 the PIN lock suspends the allowed camera apps while LOCKED (`CameraLock`).
- **Role changes reach the server** (B1): `AppEnforcer.signalRoleChange` requests a sync when the dialer/redirection role state differs from `CallPrefs.rolesSignalled` (written by `CallStateReport.build` and by the request itself - once per change, no loop while offline; pure `roleReportNeeded`). The server shows "waiting" for at most 5 minutes.
- **Call log** (B3): `canReadCallLog(granted, unlocked)` gates `CallSystem` and `MissedCallsRepo` - no SecurityException per sync on unmanaged phones.
- **Element X** Message button: `matrix:u/<mxid without @>?action=chat` (`elementChatUri`, MSC2312 - Element X has no matrix.to filter), fallback `element://user/<mxid>` (`MessageIntent.uris`, tried in order by `ContactSheet.openMessage`; since design 15 a learned DM room's `elementx://open/…` comes first), all explicit to Element X. No call button (no call intent).
- **Fix round (qa-09-code.md)**: with the block on, the plan always pins the **system dialer** (its in-call UI - emergency, unmanaged calls - would otherwise be blocked; residual: its keypad's MMI/USSD codes bypass Telecom, as before step 9); `EmergencyDialer.open` only targets `isLockTaskPermitted` system handlers that resolve, falling through (`emergencyTargets`); Home comes forward only when the dialer role really changed and no call is on (`bringHomeAfterRoleChange`); after a hand-back we caused, our fixed permissions go back to DEFAULT (`shouldResetOwnPermissions`, pref `own_permissions_fixed`) and `canReadCallLog` also needs managed calls; ResolverActivity is a helper (`HelperKind.RESOLVER`), `firstHelper` skips forbidden matches, the set is logged; a missing `block_activity_start` = **off** (older server: no kill switch; emergency wins); Matrix IDs follow the spec grammar and are percent-encoded (`uriEncode`); `apply(fromSync = true)` doesn't request another sync.

## Sideload blocking + instant suspend-on-install (2026-08-08)

**`UserManager.DISALLOW_INSTALL_APPS` is the wrong tool for "block new app installs but let already-installed apps keep updating" - its own AOSP javadoc says it "also prevents device owners and profile owners installing apps."** Confirmed by reading the actual source (`frameworks/base/core/java/android/os/UserManager.java`), not assumed - this restriction is a blanket block with no carve-out for the device owner's own installs, so it would have broken this app's own `AppInstaller.kt`/`PackageInstaller`-based tracked-app pushes too. The Android-intended tool for "curated list of installable apps, but keep auto-updating approved ones" is Android Enterprise's Managed Google Play app allowlist - not usable here, since it needs real Google Play Services + Play EMM API enrollment, doesn't exist on GrapheneOS at all, and conflicts with this project's deliberate avoid-Google-infrastructure design.

**What's actually built instead, in `AppEnforcer.kt`:**
- `applySideloadRestriction` sets `DISALLOW_INSTALL_UNKNOWN_SOURCES` + `DISALLOW_INSTALL_UNKNOWN_SOURCES_GLOBALLY`, lifted while an offline override or the pause-restrictions kill-switch is active (see the standing rule below - the first version of this didn't, confirmed live as a real gap, fixed same-day) - blocks installing an APK downloaded via an allowlisted browser (or any other non-store source), while leaving the device's own app store (Play Store / GrapheneOS's, where present) completely untouched for both fresh installs and updates, and not touching this app's own privileged installs either - "unknown sources" restrictions only gate the user-facing install-permission flow neither of those paths goes through.
- `enforceOnNewPackage` reacts to a single newly-installed package **immediately** (suspends/hides it if not on the current allowlist) rather than waiting for the next full `apply()` cycle, which could be up to the 5-minute periodic-sync backstop away. Wired to `Application.kt`'s `LauncherApps.Callback.onPackageAdded` - an existing, already-registered callback that fires the instant Android finishes any install, on-device, with zero network round-trip, regardless of whether the app came from a store or (for anything installed before the sideload restriction above was ever applied) a sideloaded APK. Dispatched onto a background coroutine from the callback, not run inline - `onPackageAdded` fires on the main thread by default, and this does `DevicePolicyManager` Binder calls, which is exactly the class of mistake that caused the ANR described above. Already respects the same overrides independently (checks them itself before acting).

Together: an app store install of something not on the allowlist would still need the admin to explicitly add it before it stays usable (same as it always did), but now becomes unusable within moments of installing rather than surviving until the next sync; a sideloaded APK can't be installed at all once the restriction is in place. Neither is a true "you literally cannot install this" guarantee before the fact for the store-install case - that guarantee doesn't exist without Managed Google Play - but it closes the practical gap to something close to instant.
