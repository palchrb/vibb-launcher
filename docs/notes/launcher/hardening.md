# Launcher notes: hardening, emulator fixes, sideload blocking

Moved from launcher/CLAUDE.md on 2026-11-01.

## Hardening (handy step 4, design `docs/design/04-hardening.md`, at the monorepo root)

- **User restrictions from server switches** (`server/Hardening.kt`, pure, `HardeningTest`; DTO `dto/HardeningPolicy.kt` = `PolicyResponse.hardening`): `DISALLOW_FACTORY_RESET`, `_ADD_USER`, `_MODIFY_ACCOUNTS`, `_CONFIG_VPN`, `_USB_FILE_TRANSFER`, `_DEBUGGING_FEATURES`, `_SAFE_BOOT`, `_CONFIG_LOCATION` (+ `setLocationEnabled(true)` first) and `_AIRPLANE_MODE` (step 5). `hardeningPlan` sets each as the server says while managed (`hardeningManaged`: the enforced policy has an allowlist, or calls are managed); a missing object or field means that switch's default (all on, **safe boot and airplane mode off**), unmanaged/never-managed clears all. **Not lifted by the offline override or the pause** - only an explicit server value or unmanaging (second exception to the standing rule). Since security review S-L11 `withFilterVpnLock` also sets `_CONFIG_VPN` while the Web filter is on without that (a filter-only phone; the parent's explicit switch off wins), and that part goes with the filter: lifted by the override and the pause. Also since then (S-L5) `DISALLOW_BLUETOOTH_SHARING` while managed, lifted by the override and the pause (`bluetoothSharingRestricted`). `AppEnforcer.applyHardening` runs last in `apply()`, after the always-on VPN. `LastEnforcedPlan` carries the switches. Never call `AppEnforcer.apply(context, null)` for an override any more - pass the enforced policy (`currentPolicyDecision().policy`), or the hardening would be cleared.
- **adb**: with `disallow_debugging_features` on (the default) adb is gone the moment the first managed policy applies - no `adb install -r` fix-forward, no logcat, no `cmd role add-role-holder`. Grant `ROLE_CALL_REDIRECTION` and `ROLE_CALL_SCREENING` before enrolling, or switch "Block USB debugging" off in the phone's Advanced › Restrictions (the device row exists before enrollment) for device work. A launcher that crash-loops before it can sync then needs a recovery-mode wipe. Safe mode repairs nothing (restrictions, suspension, blocked adb and factory reset persist there); `disallow_safe_boot` defaults off only until it is checked on the Jelly Star. Deploy order: server first, set the switches and a PIN, then the launcher (a launcher on a pre-0023 server applies the defaults) - runbook in `04-hardening.md`.
- **Schedule enforced by suspension**: `KidModeEnforcer.lockReasonNow(policy, overrideActive, now)` is the one rule for the lock (sync, offline re-checks, `apply`). While it isn't NONE, `computeEnforcementPlan(scheduleLocked = true)` suspends - but doesn't hide (`EnforcementPlan.hide` is only the apps not allowed at all; hiding drops alarms/jobs/widgets) - every controllable app but ours, the system dialer, the keyboards (`inputMethods`, always in `neverRestrict` - since design 24b only the enabled ones that are system or allowlisted) and the alarm apps (`alarmApps`, `sparedAlarmApps`: every system clock and a verified Fossify Clock - since bug 2026-11-02 always, no longer only while it holds the next alarm; spared by the lock only), whatever the allowlist, and kiosk pins only our package (plus an allowlisted system dialer while calls are unmanaged, and since bug 2026-11-02 the allowed alarm apps: an unpinned clock's ringing screen, a task of its own, was refused by lock task - the alarm rang during a school rule with no way to Stop it; the kid can now reach the clock app - alarms, timer, stopwatch - during a rule through Recents or a notification, as with the kiosk off, accepted; without the block bit the clock's task can also open unsuspended non-launchable system screens - Google Clock's Bedtime to Digital Wellbeing, "Help & feedback" (GMS Help, a WebView of help articles), the ringtone and document/photo pickers - while its links to launchable apps (Settings, Assistant, Spotify/YouTube Music, a browser, Play) are refused, those being suspended; all of it was reachable with the kiosk off already. **Device check (code QA L4/L5)**: Google Clock's Help & feedback and Bedtime during a rule; `AppEnforcer` logs "Alarm apps (spared by a rule, pinned while allowed): [...]" when the set changes - read it on the Jelly Star and the emulator, nothing but clock apps may be in it); LockActivity always shows "Emergency call" (112 via Telecom, CALL_PHONE self-granted, fallback the system dialer); the call restrictions are unchanged (allowed and emergency calls work: phone book, in-call UI and screening are ours). `shouldSuspendNewPackage` suspends new installs during the lock. `reevaluateLockReasonFromCache(context)` re-runs `apply` in the background when the lock changes; since step 6 the re-checks come from one boundary alarm and screen events, not a minute timer (see "Time rules" below). `AppEnforcer.lastEnforcedLockKey` makes a re-check re-apply until the lock is really enforced; switched-off hardening is cleared at the start of `apply()`. `AppEnforcer.apply` is `@Synchronized` - never call it on the main thread (every caller - the pause's start, the relock, the sync - runs it off main).
- **Backup to Google stays off** (Google account on the phone, runbook `docs/setup/google-account.md` at the monorepo root): `server/BackupService.kt` with the pure `backupServiceAction` (`Hardening.kt`, `HardeningTest`). Early in every `apply()` (right after `clearHardening`) while `hardeningManaged`, it reads `dpm.isBackupServiceEnabled(admin)` and, if on, calls `setBackupServiceEnabled(admin, false)` - AOSP switches the service off at `set-device-owner` and only the device owner can switch it on. There is **no action that switches it on**, no server switch, the override/pause don't lift it and unmanaging leaves it as it is; never on the main thread (it refuses), every exception caught and logged. `BackupServiceInvariantsTest` scans every non-test source set: each mention of the setter must be a plain call whose last argument is the literal `false` (no variable, named argument, method reference or reflection). Status `backup_service_enabled` (`BackupService.reportedState`; null = not device owner/unreadable, then left out of the JSON).
- **No screen content for AI** (design 126 A4, 2026-11-22): three launcher-only entries in `HardeningRestriction`, like
  `SET_WALLPAPER` (no server switch, always on while `hardeningManaged`, cleared unmanaged; the override, the pause and
  "Åpne for oppsett" never lift them): `CONTENT_CAPTURE` (`DISALLOW_CONTENT_CAPTURE`), `CONTENT_SUGGESTIONS`
  (`DISALLOW_CONTENT_SUGGESTIONS`) and `ASSIST_CONTENT` (`DISALLOW_ASSIST_CONTENT`, API 35: `minSdk = 35` on the entry,
  the pure `hardeningKeyApplies(restriction, sdk)`; `AppEnforcer`'s `userManagerKey()` answers `null` below it, so
  Android 14 neither sets nor clears it). They stop Android System Intelligence (Overview's text and image actions,
  Circle to Search, "ask about this screen") and the assistant's screenshot and app content - for Gemini or Google
  holding the role; Vibb's own assistant (design 98) reads nothing anyway. Possible cost on 15+: Play Protect's
  on-device scam detection runs over content capture and may stop too (the gate reads `dumpsys content_capture`,
  design 126 §1.4, §10).
- **User certificates** (2026-11-25): `CONFIG_CREDENTIALS` (`DISALLOW_CONFIG_CREDENTIALS`), a server switch
  (`hardening.disallow_config_credentials`, server migration 0178, Advanced › Restrictions' "Blokker sertifikater"), on
  by default; a missing field blocks. While set, Settings › Encryption & credentials can't install or remove a
  certificate and Android's own trusted ones can't be switched off. Its cost: a Wi-Fi network whose own CA must be
  installed (some school or work networks; EAP with "Use system certificates" and a domain still works) - the parent
  turns the switch off, which is a choice, never a warning. Like every hardening switch the pause, the setup hold and
  the Parent PIN don't lift it, so a certificate during setup also needs the switch. Vibb One trusts no user
  certificate either way (design 76). The device owner's own `installCaCert` isn't gated by it.
- **The provisioning baseline** (2026-11-25, `server/ProvisioningBaseline.kt`): a phone set up from the QR is locked
  down before it has talked to the server - `PROVISIONING_BASELINE` (no USB debugging, no new users, no safe mode, no
  user certificates) and the sideload restriction, set at once by `PolicyComplianceActivity` and
  `onProfileProvisioningComplete` (both call `ProvisioningBaseline.arm` first, extras or none), and kept by
  `hardeningPlan(managed = false, baseline = true)` while the flag (device-protected `provisioning_baseline.xml`) is
  armed and no policy was ever applied (`provisioningBaselineHolds` over `everManaged`). From the first policy the
  server's switches alone decide; a phone the server later unmanages clears everything as before. Factory reset is
  only blocked from the first policy, so a phone that never reaches its server can still be reset from Settings;
  Android's own lock is never touched. adb's `dpm set-device-owner` runs neither entry, so the dev emulator's adb
  provisioning keeps adb. A QR-provisioned phone whose enrolment failed has no adb until it connects: Koble til with a
  new code from the PWA is the way on. The cost, accepted by the owner: before the first policy, a launcher that
  misbehaves (crash loop, a broken setup) has no adb and no safe mode to fix it with - only a factory reset from Settings
  or recovery remains.
- **Never call `setUserControlDisabledPackages`** (launcher round 7 §2, `docs/design/r7-launcher-small-items.md`; the round's battery-state report was removed on 2026-10-20): a package on that list can't be suspended, hidden or uninstalled by the device owner either (AOSP `SuspendPackageHelper` "protected package", `setApplicationHiddenSettingAsUser`, `DeletePackageHelper`; qa-l7-b-code finding 1), so time rules, the budget, the camera lock and the update fence would fail open for those apps. `BackupServiceInvariantsTest` scans the production sources for it.
- **Device checks** are in `04-hardening.md` (restrictions in Settings, VPN with `DISALLOW_CONFIG_VPN`, location lock vs `WifiNetworksActivity`, suspension at the schedule edges incl. inside an app and from Recents, calls at bedtime).

## Emulator fixes: kiosk app block, emergency dialer, role hand-back (handy step 9 part B, design `docs/design/09-sms-and-fixes.md`, at the monorepo root)

Part A (SMS allowlist via the SMS role) is **postponed (user, 2026-10-05)**: SMS stays on/off only, as in step 2.
- **Kiosk app block** (B4): `PolicyResponse.blockActivityStart` (server switch, default on; the server masks bit 64 out of `lock_task_features`, so it only ever comes from this key) adds `LOCK_TASK_FEATURE_BLOCK_ACTIVITY_START_IN_TASK` (`lockTaskFeatures()` in `server/LockTaskHelpers.kt`): while kiosk is on every activity start of a non-pinned package becomes BlockedAppActivity - explicit intents into Play, Google sign-in/payment sheets, Settings. That path has **no emergency exemption**, so `AppEnforcer.resolveLockTaskHelpers` resolves system helpers from intents on every apply (emergency dialer, Telecom via `ACTION_CALL`, permission controller via `REQUEST_PERMISSIONS`/the role request, `ACTION_CHOOSER` = intentresolver, `ACTION_OPEN_DOCUMENT`, `ACTION_PICK_IMAGES`, the `SMS_CB_RECEIVED` receiver, since 16d the recents provider) and pure `lockTaskHelpers` keeps FLAG_SYSTEM ones minus Settings, the camera, the system dialer (its pinning stays under the call rules) and Play core; the plan pins them only with the bit, also during a time-rule lock (`LockTaskHelpersTest`). `LastEnforcedPlan` carries the switch. The platform refusing to suspend the Play Store (verifier on GMS) is recorded (`PlayRuntime.storeSuspendable`) and reported as `playStoreSuspendable`.
- **The kiosk's end: the block and the stored switch go before the list** (2026-11-10, `docs/testing/emulator.md` §6af; `LockTaskChrome.writeLockTask`'s unpin, pure `unpinFeatures` in `server/LockTaskHelpers.kt`, `LockTaskHelpersTest`): a pause's start (Settings behind the Parent PIN, or the PWA's `start_pause`) left 1 of 10 emulator starts on Android's "App is not available". `setLockTaskPackages(admin, [])` takes Home's task out of lock task, clears it and restarts Home inside the same call, while the end of lock-task mode is only posted and the features are reset after the packages - checked before that, Home's start met LOCKED, the block bit and an empty list, became BlockedAppActivity, and that screen's start locked the phone to its own task (its OK ended it; the Home key did nothing). So the unpin writes three things in this order: the platform's features without the block bit (`liftAppBlock`; nothing when the bit isn't set), the stored `kioskEnabled` off, then the empty list; a failed emptying puts the switch and the features back. The switch goes first because the restarted Home resumes while the call still runs: with the switch still on, `reconcileKioskMode()` asked for lock task with nothing allow-listed - Android's screen-pinning request during a pause (seen once). With it off first, a living Home hears the change and stops lock task itself when it gets there before the emptying (nothing is cleared then, Settings stays in front); either order is safe. The pin is unchanged: the plan's features, verified, then the packages, then the switch - so the block is back whenever the kiosk is. Never empty the list with the block bit set, and never leave the switch on across the emptying.
- **The kiosk ends from its root** (design 141, `docs/design/141-kiosk-ends-from-root.md`; `lock/HomeRootStop.kt`, pure rules in `lock/LockTaskRoot.kt`, `LockTaskRootTest`, the order scanned in `HomeFrontTest`): design 139's gate found the emptying leaves lock task on when a `BlockedAppActivity` task was left under the kiosk (a start of a package neither pinned nor suspended, left with the Home key): its task is `LAUNCHABLE_PRIV` (`lockTaskMode="always"`), which `setLockTaskPackages` never removes, so lock task stayed LOCKED with it alone - every start refused, Home's own `stopLockTask` from a new, unlocked task "Invalid uid", stuck until a reboot. So the unpin now has a third step between the switch and the list: `HomeRootStop.stop` - only while `lockTaskModeState` is LOCKED (PINNED is screen pinning, never the kiosk's) and Vibb's chrome isn't - calls the registered Home's `stopLockTask()` from the pass's own thread (a plain binder call with the token; no latch on main: the main thread takes `LockTaskChrome`'s monitor itself). From the root AOSP's `clearLockedTask` clears every other locked task, the leftover included, takes Home out without clearing it and empties the locked list, so the emptying finds nothing (no Home restart, neither §6af race). Home registers in `onCreate` and unregisters in `onDestroy` only when not `isChangingConfigurations` (a relaunch keeps the record and its token). Home's stop runs once per kiosk-off spell (from a kiosk-on pass to the next) until it answers `ASKED` - Home's own stop at a resume counts too; later passes answer `ASKED_BEFORE`: from a task that is no longer the root a stop clears that task (`mLockTaskUid` is never reset), Home's and with it the setup flow's return (code QA M1). Answers (one log line each, tag `HomeRootStop`; `REFUSED`/`NO_HOME`/`ASKED_BEFORE` and the stuck line once per spell, `NOT_LOCKED` never): `NOT_LOCKED`, `LOCKED_CHROME`, `ASKED_BEFORE`, `NO_HOME`, `ASKED`, `REFUSED` (Home's task never locked), `FAILED`. Two follow-ups: **the stuck check** - 1 s after a pass that found LOCKED, lock task still LOCKED with the kiosk off, Vibb's chrome not LOCKED and no VoIP pin (`lockTaskStuck`) gets one retry per spell, `stopLockTask()` from our resumed activity (a launch in the window before the posted stop - the setup hold's flow, our in-call screen - joins lock task and becomes the new root; its stop ends it), then "Lock task still on after the kiosk's end (Home's stop: ..., retry: ...)" - log only (Q1), the parent's remedy is a restart; and **no Home in the process** with the screen on (`unpinStep`): the emptying is skipped, Home is brought (typed HOME, restarted in its root task - our package is still listed), its `reconcileKioskMode` stops lock task from the root and - only while that Home is awaited (`HomeRootStop.homeStopped()`) - asks for a chrome pass (`PinLockRuntime.requestChromePass`), which empties the list; a pass 3 s later empties it regardless (one bring per spell). With the screen off, or the lock undecided with a kid PIN, today's emptying (the residual). Every kiosk's end: Home stays as it is (no launch splash); a pause from Settings keeps Settings in front. Gate: `docs/testing/emulator.md` §6cf.
- **Emergency** (QA 09 #1): `LockActivity` and the phone book's 112 tile fall back, when Telecom refuses, to `EmergencyDialer.open` - an explicit intent (`android.intent.action.DIAL_EMERGENCY`, then `com.android.phone.EmergencyDialer.DIAL`) to the resolved **system** component (`chooseEmergencyDialer`), which must be lock-task permitted. Never `ACTION_DIAL` to the default dialer (not pinned while calls are managed or a rule blocks calls).
- **Role hand-back without a kill** (B2, QA 09 #6/#11): before the dialer role changes (and whenever calls are managed) every role-grantable permission our manifest requests (`ownPermissionsToFix`, `server/OwnPermissions.kt`) is granted by policy via `QuickControls.fixOwnPermission`, decided on `getPermissionGrantState` - `selfGrantPermission` skips anything `checkSelfPermission` reports granted, including role-owned grants that a hand-back revokes (killing HOME/kiosk/call path). `DISALLOW_CONFIG_DEFAULT_APPS` is re-set in the same pass; after a TAKE/RELEASE with kiosk on, Home is brought to front. `KEYGUARD_DISABLE_SECURE_CAMERA` is ORed in while managed (`keyguardDisabledFeatures`, only our bit cleared) - useless without a screen-lock PIN; runbook: camera gesture off before enrolling (`docs/testing/emulator.md`); since 2026-10-06 the PIN lock suspends the allowed camera apps while LOCKED (`CameraLock`).
- **Role changes reach the server** (B1): `AppEnforcer.signalRoleChange` requests a sync when the dialer/redirection role state differs from `CallPrefs.rolesSignalled` (written by `CallStateReport.build` and by the request itself - once per change, no loop while offline; pure `roleReportNeeded`). The server shows "waiting" for at most 5 minutes.
- **Call log** (B3): `canReadCallLog(granted, unlocked)` gates `CallSystem` and `MissedCallsRepo` - no SecurityException per sync on unmanaged phones.
- **Element X** Message button: `matrix:u/<mxid without @>?action=chat` (`elementChatUri`, MSC2312 - Element X has no matrix.to filter), fallback `element://user/<mxid>` (`MessageIntent.uris`, tried in order by `ContactSheet.openMessage`; since design 15 a learned DM room's links, `elementRoomUris`, come first), all explicit to Element X. No call button (no call intent).
- **Fix round (qa-09-code.md)**: with the block on, the plan always pins the **system dialer** (its in-call UI - emergency, unmanaged calls - would otherwise be blocked; residual: its keypad's MMI/USSD codes bypass Telecom, as before step 9); `EmergencyDialer.open` only targets `isLockTaskPermitted` system handlers that resolve, falling through (`emergencyTargets`); Home comes forward only when the dialer role really changed and no call is on (`bringHomeAfterRoleChange`); after a hand-back we caused, our fixed permissions go back to DEFAULT (`shouldResetOwnPermissions`, pref `own_permissions_fixed`) and `canReadCallLog` also needs managed calls; ResolverActivity is a helper (`HelperKind.RESOLVER`), `firstHelper` skips forbidden matches, the set is logged; a missing `block_activity_start` = **off** (emergency wins); Matrix IDs follow the spec grammar and are percent-encoded (`uriEncode`); `apply(fromSync = true)` doesn't request another sync.
- **The Credential Manager selector (passkeys-kiosk, 2026-11-20, `docs/testing/2026-11-20-passkeys-kiosk.md`)** is a kiosk-block helper (`HelperKind.CREDENTIAL_SELECTOR`): the package Android starts for a passkey or password request, read as AOSP's `IntentFactory` reads it (pure `credentialSelectorPackage`: `config_oemCredentialManagerDialogComponent` when set and enabled, else `config_credentialManagerDialogComponent`, each only when its package is an installed system app; when neither is usable - the Jelly Star's OEM placeholder without "/", an unreadable string - AOSP's `com.android.credentialmanager` if installed as a system app, `jelly-round-2`). The "Kiosk app block helpers" log line ends with both raw config values. On Android 14 that is `com.android.credentialmanager`, pinned with the block; on a phone with Google's `GoogleConfigOverlay` (the Play image on 16) it is Play services' `CredentialChooserActivity`, which `lockTaskHelpers` never pins, so a passkey there still ends in "App is not available" outside a pause - the options are in the test doc, the user decides.
- **The MediaStore provider (media-provider-helper, 2026-11-20)** is a kiosk-block helper (`HelperKind.MEDIA_PROVIDER`): the package of `MediaStore.AUTHORITY` (`resolveContentProvider`, system only - the MediaProvider module, `com.google.android.providers.media.module` on Google builds). An app's `createDeleteRequest`/`createTrashRequest`/`createWriteRequest` starts the provider's confirmation (`PermissionActivity`) in the app's task, also with Media management (then it finishes at once); not pinned, Immich's delete on the Jelly Star (Android 16) was "App is not available" for "Media picker". `ACTION_PICK_IMAGES` resolves to the separate `com.google.android.photopicker` (emulator capture 2026-10-23 too), so `PHOTO_PICKER` never pinned the module. Pinned with the block like the others, also during a time-rule lock; its other exported screens (the older picker, the picker's cloud-media settings, the clear-cache dialog) are in the enum's comment. The "Kiosk app block helpers" line shows `MEDIA_PROVIDER=...`.

## Sideload blocking + instant suspend-on-install (2026-08-08)

**`UserManager.DISALLOW_INSTALL_APPS` is the wrong tool for "block new app installs but let already-installed apps keep updating" - its own AOSP javadoc says it "also prevents device owners and profile owners installing apps."** Confirmed by reading the actual source (`frameworks/base/core/java/android/os/UserManager.java`), not assumed - this restriction is a blanket block with no carve-out for the device owner's own installs, so it would have broken this app's own `AppInstaller.kt`/`PackageInstaller`-based tracked-app pushes too. The Android-intended tool for "curated list of installable apps, but keep auto-updating approved ones" is Android Enterprise's Managed Google Play app allowlist - not usable here, since it needs real Google Play Services + Play EMM API enrollment, doesn't exist on GrapheneOS at all, and conflicts with this project's deliberate avoid-Google-infrastructure design.

**What's actually built instead, in `AppEnforcer.kt`:**
- `applySideloadRestriction` sets `DISALLOW_INSTALL_UNKNOWN_SOURCES` + `DISALLOW_INSTALL_UNKNOWN_SOURCES_GLOBALLY`, lifted while an offline override or the pause-restrictions kill-switch is active (see the standing rule below - the first version of this didn't, confirmed live as a real gap, fixed same-day) - blocks installing an APK downloaded via an allowlisted browser (or any other non-store source), while leaving the device's own app store (Play Store / GrapheneOS's, where present) completely untouched for both fresh installs and updates, and not touching this app's own privileged installs either - "unknown sources" restrictions only gate the user-facing install-permission flow neither of those paths goes through.
- `enforceOnNewPackage` reacts to a single newly-installed package **immediately** (suspends/hides it if not on the current allowlist) rather than waiting for the next full `apply()` cycle, which could be up to the 5-minute periodic-sync backstop away. Wired to `Application.kt`'s `LauncherApps.Callback.onPackageAdded` - an existing, already-registered callback that fires the instant Android finishes any install, on-device, with zero network round-trip, regardless of whether the app came from a store or (for anything installed before the sideload restriction above was ever applied) a sideloaded APK. Dispatched onto a background coroutine from the callback, not run inline - `onPackageAdded` fires on the main thread by default, and this does `DevicePolicyManager` Binder calls, which is exactly the class of mistake that caused the ANR described above. Already respects the same overrides independently (checks them itself before acting).

Together: an app store install of something not on the allowlist would still need the admin to explicitly add it before it stays usable (same as it always did), but now becomes unusable within moments of installing rather than surviving until the next sync; a sideloaded APK can't be installed at all once the restriction is in place. Neither is a true "you literally cannot install this" guarantee before the fact for the store-install case - that guarantee doesn't exist without Managed Google Play - but it closes the practical gap to something close to instant.

## Android 17: Settings can't be hidden or suspended (fix round `compat-fix-1`, 2026-11-16)

On Android 17 (API 37; seen on 37.0 and 37.2) `com.android.settings` hosts App lock and holds the app-op
`SYSTEM_EXEMPT_FROM_SUSPENSION` (with `android`, `com.android.providers.settings`, Telecom and other system-uid
packages): `setPackagesSuspended` returns it as not suspended ("Cannot suspend package ... has
OP_SYSTEM_EXEMPT_FROM_SUSPENSION set") and `setApplicationHidden` returns false ("ignoring ... as it's on policy-exempt
list"). Android 16's Google image (`jelly36`) already refuses the suspension for the same app-op but still hides it;
Android 14 (`compat34`) does both. Lock task still refuses to start it while the kiosk is on, and the kiosk is always
on while apps are managed (`kiosk_desired` isn't the parent's choice), so it stays shut; but it is visible to the
package manager. One side effect: with Settings never hidden, FallbackHome is always there before the first unlock, so
a boot the shutdown didn't arm (step M's case below the boot cover) can't hang on 17.

- **The lists follow the plan** (`server/PlatformRefusals.kt`, `PlatformRefusalsTest`): `AppFilter` (Home, the drawer,
  Kid Settings' hidden apps) leaves out every package the last plan wants hidden or suspended
  (`AppEnforcer.lastPlanSuspend`/`lastPlanHide`, `plannedOffLists`), whatever the platform did - general, not a
  Settings case. Before the first `apply` in a process the last plan stored stands in (`PlatformRefusals.storePlan`,
  every apply, QA M1: right after a reboot and after a process death in the pause). The PIN-gated Settings' top gear
  asks the plan too (QA L4). Home filters
  again after an `apply` whose sets changed (`HomeActivity.planListener`): a refused package sends no package callback.
  `dialogTarget` leaves such a package out too (`ResolvedDialog.plannedOff`), so the PIN-gated Settings' system-page
  rows (Background connection, Modify system settings, App access, fingerprint, media on the lock screen, the
  assistant's voice input) still say "pause first" instead of a page lock task would refuse. In the pause the plan
  releases Settings, so it is on Home and the rows open it, on every version.
- **No retry until a reboot or an OS update**: a refusal of a package that holds the app-op is recorded
  (`PlatformRefusals.refused`, prefs `platform_refusals`: the boot count and `Build.FINGERPRINT`) with one log line
  ("Android refuses to suspend ... not asked again until a reboot or an OS update"); `apply` skips that restricting call
  while the record matches this boot and build and the package still holds the app-op (`restrictCallDue`,
  `stillExempt`, QA L1). A release is always made, and any other refusal
  (the Play Store as verifier, a carrier app) is still retried at every pass as before.
- **What else changes on 17**: Flymodus's route window (design 98) finds Settings unhidden, so it neither unhides nor
  hides it again - it only pins it for the window; so does design 122's Bluetooth pairing window (`BtPairingWindow`,
  `kid-settings.md`), which pins Settings for the pairing dialog alone, at most 30 s. SystemUI's Settings links (`launcher-fix-1`'s sink) resolve to
  Settings' own activities, which win over the sink's priority -999, so the sink is never reached: under the kiosk (with
  the app-block bit) the start becomes Android's BlockedAppActivity, "App is not available - Settings is not available
  right now" with OK, back to where the kid was - no SystemUI crash (checked with `am start` of
  `APP_NOTIFICATION_SETTINGS` on 37.2, `docs/testing/emulator.md` §6as); in the pause they open Settings, as on 14-16.
  Snarveier (design 99) has no Settings link of its own; its notification's gear is the case above.

## SystemUI's Settings links while Settings is hidden (the gear bug, fix round `launcher-fix-1`, 2026-11-16)

`AppEnforcer.apply` hides `com.android.settings` while managed (`EnforcementPlan`'s `hide`; Settings can't be
suspended). SystemUI's `StatusBarNotificationActivityStarter` starts the notification long-press menu's gear ("More
settings", `android.settings.APP_NOTIFICATION_SETTINGS`), the shade's Manage (`NOTIFICATION_SETTINGS`) and History
(`NOTIFICATION_SETTINGS` + `NOTIFICATION_HISTORY`) through `TaskStackBuilder.startActivities`, which throws
`ActivityNotFoundException` when nothing resolves: SystemUI died and restarted, and Android's keyguard came up (the kiosk
stayed locked, Vibb One's process was untouched). Found on `jelly36` (`docs/testing/emulator.md` §6ar), the same on
Android 14.

**What reaches that path, per release** (read in AOSP's `android14-release` to `android17-release`, and
`android16-qpr2-release`: `NotificationGutsManager`, `StatusBarNotificationActivityStarter`, the 16+ `SettingsIntent`
with its `FooterViewModel`/`EmptyShadeViewModel` callers, and 14/15's `NotificationStackScrollLayoutController`):
`startNotificationGutsIntent` - the app's and a channel's notification page, conversations, bubbles, 16 QPR2+'s
`NOTIFICATION_BUNDLES`, the app-ops links (`APPLICATION_DETAILS_SETTINGS` and `MANAGE_APP_OVERLAY_PERMISSION`, both with a
`package:` URI; `MANAGE_APP_PERMISSIONS` goes to the permission controller, which has no launcher icon and is never
hidden), and the Notification Assistant's own feedback intent (not Settings's; nothing to catch); `startHistoryIntent`
(14, 15) and `startSettingsIntent` (16+) - Manage, History, and the empty shade's text, which on 16+ links to Modes
(`ZEN_MODE_SETTINGS`, or `AUTOMATIC_ZEN_RULE_SETTINGS` over `ZEN_MODE_SETTINGS` when one mode hides the notifications - a
time rule's own mode can). Every one of them is in the sink.

**The sink** `server/SettingsSinkActivity` (exported, no permission - SystemUI starts it; `Theme.NoDisplay`,
`noHistory`, `excludeFromRecents`, its own empty `taskAffinity`; a plain `Activity`, since an AppCompat one throws under
`Theme.NoDisplay`) answers `SettingsSink.ACTIONS` and, with a `package:` URI, `SettingsSink.PACKAGE_ACTIONS`, at
**priority -999**, category DEFAULT. It only finishes in `onCreate`: it opens nothing, reads nothing from the intent but
the action (logged only when it is one of ours) and validates nothing. While Settings is visible (the restrictions
pause, "Åpne for oppsett") Settings' own filters win and no chooser shows: priority 1 on every emulator image checked
(Android 14's AOSP image, 16's Pixel image, 17); -999 keeps a tie with any other handler unlikely. Android 14's Settings
has no `AUTOMATIC_ZEN_RULE_SETTINGS` filter, so there the sink answers it even in the pause (nothing on 14 sends it).
`SettingsSinkTest` pins both filters to the lists, the attributes (and the absent risky ones), a plain `Activity`, and a
body that reads only the action and finishes.

**Where the kid lands, and why it can't pass the PIN lock.** `TaskStackBuilder` starts the first intent with
`NEW_TASK | CLEAR_TASK | TASK_ON_HOME`, so after the sink the kid is on Home, not back in the app they were in (as with
a visible Settings, which also returns to Home). The empty affinity keeps `CLEAR_TASK` off Home's own task. While the PIN
lock is up, its lock-task features leave out NOTIFICATIONS and the status bar is disabled, so no shade can reach the sink
there - a later change that adds NOTIFICATIONS while LOCKED would make the gear a way from the PIN lock to Home, and must
be reviewed with that in mind.

**The other SystemUI paths don't crash** (checked on `jelly36` with Settings disabled and lock task off, §6ar): Quick
Settings tiles' long-press (Internet, Bluetooth, Airplane, Alarm), their dialogs (the Internet dialog's network,
Bluetooth's "Pair new device", Modes' Settings and a mode), the Quick Settings footer's gear, the clock and date, and
the volume panel's Settings go through SystemUI's `ActivityStarter`, which starts through the activity task manager and
only logs `result code=-91`; a notification's own tap (a `PendingIntent` to Settings, e.g. "Physical keyboards
configured") is the same. Under the kiosk none of these are reachable anyway: lock task keeps Quick Settings closed and
hides the volume dialog's settings button, on Home and on Android's keyguard. A new crashing path is one more action in
`SettingsSink` and the manifest.

**Checked on** Android 14 (`google_apis`, API 34) and 16 (`jelly36`, the Play image): the crash before, the sink after,
the pause. Android 17 (`google_apis`, API 37.2) only in part (§6ar): there the platform refuses to hide Settings at all
("Platform refused to hide com.android.settings"), so the gear and Manage reach Settings, which lock task blocks with
Android's "App is not available" - no crash, but not the quiet sink either; Settings' filters sit at priority 1 above the
sink there too. Whether Settings can be hidden on the Jelly Star's own Android 17 is owed.
