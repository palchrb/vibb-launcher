# Server notes: device API

Moved from server/CLAUDE.md on 2026-11-27 ("Device-facing API"); the core file's 'Where the rest is' lists every note.

## Device-facing API (plain JSON, no envelope)

Every route below is declared in `src/device_routes.rs` (`device_routes()`, design 22 S0), never in `main.rs`
(`tests::listeners::main_rs_has_no_device_route_literal`): both listeners build from it.

- `POST /api/devices/enroll` - `{enrollment_code}` → `{device_id, device_token}`; design 129 S1: with `chain` and `proof` (the phone's new Keystore key, attested for `SHA-256("vibb-enroll-v1" || 0x00 || code)`, at most 32 KiB) the answer adds `key: {key_id, state: "observed"}`; the same code with the same key in the code's life answers again with a new bearer (a lost answer: at most twice, each proof's ECDSA `r` new). Design 129b: every body carries `attempt` (16 bytes, Base64url) and a key, or `key_error`; a refused key or none is `409 {state: "waiting", reason, number, retry_after_s}` until the parent's exception (`POST /devices/{id}/key-exception`) lets that attempt enrol `key: {state: "exempt", reason}`; `426 update_app` without `attempt`, `503 server_setup`/`list_stale`, `429` within 10 s of a row's last try (`docs/notes/server/device-key.md`, "E1")
- `GET /api/devices/key`, `GET /api/devices/key/challenge`, `POST /api/devices/key {challenge, chain, proof}`, `POST /api/devices/key/conflict` (bearer or signature) - design 129 §5.2's registration: `{state, key_id?, spki_sha256?, rotate}`; a 32-byte challenge for 10 min; 200 `{key_id, state}` (idempotent on the key), 409 `exists`, 400 `{reason}`, 503 `list_stale`; 204 (409 `none` while no key is stored). Every device request may instead be signed (`Vibb-Signature`, `Vibb-Body-SHA256`; checked at the edge), every device answer carries `Vibb-Time`, and a refused signature is a 401 `Vibb-Auth: <reason>` - observe mode: the bearer keeps working (`docs/notes/server/device-key.md`; the shapes are `contracts/core/device_key.json`)
- `GET /api/devices/policy` (bearer) → allowlist, `time_policy` (effective rules + budget, global or the device's own, and active lifts) and `location_policy` (always; `{mode, interval_minutes, zones}` - design 64 step 2: the served interval, at least 30 min while the phone has zones and its watch holds fences, and the zones `[{id, latitude, longitude, radius_m}]` while Regularly, `[]` otherwise, never a name; `docs/notes/server/zones.md`), the frozen legacy schedule fields, `kiosk_desired`, `lock_task_features`, `override_pin_hash`/`override_pin_salt`, `pending_command`, `call_policy` (always, both channels' modes; contacts carry `photo`; `sms_groups` since design 80 D13, "Gruppemeldinger", always), `lock_glance` (always; `{apps: [{package, show_text}], sms}` - `sms` Meldinger's level `off`/`name`/`text` since design 82, `text` only while `sms_mode` is `managed`; an unreadable table sends `{"apps": [], "sms": "off"}`, never a 500), `hardening` (always, every switch explicit), `launcher_ui` (always; `lock_wake_on_notification` always in it since launcher round 7 §3, `lock_weather` since design 75 and `lock_notice_alert` (`off`/`buzz`/`sound`) since design 130 - design 82 W3's `lock_buzz_on_notification` before it -, pinned by `policy_json_keys_snapshot` and the launcher's `PolicyResponseCompatTest`), `block_activity_start` (always; never inside `lock_task_features`), `kid_lock` (always, null = no lock; `{pin_hash, pin_salt, pin_length, keyguard, pin_rev}`, design 59; `keyguard` always `"android"` since design 132), `screen_timeout_seconds`, `update_fence`, `notification_auto_cancel` (always), `music` (always the key; `null` when unreadable), `app_permissions` (always a list, design 68; a failing read is a 500), `calendar` (always; design 69: `{on_home, kid_adds, glance_next, lock_reminders, calendars, rules, feeds}` - `feeds` the calendar links `[{id, name, rev}]` since design 72 -, a read error is a 500; `docs/notes/server/calendar.md`), `server_tls` (design 76: always - `{}` watching, `{"enforce": true}` on, `{"enforce": false}` the parent's off; `docs/notes/server/connectivity.md`, "The phones' certificate check")
- `GET /api/devices/weather` and `/weather/now` (bearer) - the lock glance's weather and the card's nowcast line (design 75 §3.4: `off`/`no_position`/`unavailable`/`ok`, `none`/`ok`; 20 and 60 asks an hour per phone, `no-store`, gzip); the shapes are `contracts/core/weather.json`'s, shared with the launcher (no place name since 2026-11-04: MET is the only outside service the weather asks); `docs/notes/server/launcher-ui.md`, "Lock screen weather"
- `GET /api/devices/calendar/feeds/{uid}` (bearer) - a calendar link's set (design 72 §3; `{v: 1, id, rev, events}`), `ETag` = its rev, `If-None-Match` -> 304, gzip; 404 unless this phone has the link; the shape is `contracts/core/calendar_feeds.json`'s `feed`, shared with the launcher
- `POST /api/devices/command-result` (bearer) - `{command_id, success, message, requested_at?}` → 204 (implies the receipt; a wipe only when it was refused)
- `POST /api/devices/command-receipt` (bearer) - `{command_id, requested_at?}` → 204: the phone got the command and is about to run it (security review L12; the first receipt counts). `pending_command` is `{id, command, requested_at}` (+ `allow`, `release_tag` or `pin` on their own commands only; `pin` = `set_kid_pin`'s Child PIN, design 59): an id alone isn't unique across a restored backup or another server, so the phone keys "ran it already" on both and sends `requested_at` back; an answer that names another `requested_at` counts for nothing (QA of the launcher wave, Medium 1)
- `POST /api/devices/status` (bearer) - `{lock_reason, kiosk_engaged, installed_apps, app_version, app_version_code, offline_override_used, location, policy_state, restrictions_paused, capabilities, call_state, notification_listener_enabled, time_state, install_mode, play_window_active, play_store_suspendable, lock_state, screen_timeout_seconds, update_fence, notification_cancels, backup_service_enabled, battery_optimization_exempt, relock, unseen_boots, battery, write_settings_granted, extra_locations, zone_watch, calendar, server_tls, sms_state, setup}` (design 114: `setup` - the readings no other field carries and the setup hold's `hold_until_ms`/`hold_left_ms`, `setup_status::clean`, `contracts/core/setup_steps.json`'s `report`; design 77: `sms_state` - the SMS engine's role, mode, counts and hold pools, never a message, and since design 80 `own_learned` - the own number learned from a message -, and since design 82 `has_history` - the phone has threads to read, for Device › Apps' Meldinger row -, and since design 83 `sim_operators` and `mmsc_unlisted` - the SIMs' operators, whose `call_policy.mmsc_hosts` rows the policy then has, and a contact's pictures at an address that isn't on the SIM's row, `mmsc_hosts::intake` -, `sms::sanitize_state`, `contracts/core/sms_contract.json`'s `report`; design 76: `server_tls` - `{enforcing, seen?, outside}`, `server_tls::sanitize`, `contracts/core/server_tls_report.json`; installed apps may carry `installer`, `access` (design 68: the camera and special accesses the app declares, known keys and values only), and since 2026-10-25 `version_code`/`version_name` - the `app_updated` of every checked catalog app, `docs/notes/server/notifications.md` "App update notices"; design 64 step 2: `extra_locations` - queued fixes, every one stored before the zones are judged once - and `zone_watch` - `{fences, motion_sensor, location_on, background_location, mock_ignored}`, known keys only, plus `still`: the report's own fix is still current, stamped `resent_at`, and design 131's `wifi_disagreed` (0 when absent); every fix's `check` (`gnss`/`link`, a Wi-Fi provider's only, `device_locations.fix_check`); design 87: an installed app's `logo`, the SHA-256 of its drawn icon, and design 87b's `auto_tile` beside it, the SHA-256 of the tile it draws for Automatic) → 200 `{"wanted_logos": [hash, ...]}`, or 204 when it wants none (at most 40: the reported logos not stored, not refused in the last day, within the phone's budget and the caps; `app_logos::answer`)
- `POST /api/devices/app-logos/{hash}` (bearer) - design 87: a logo the answer asked for, raw `image/png`, at most 80 KiB -> 204 (stored, or on disk already); 400 a hash that isn't 64 lowercase hex or doesn't match the body, 415 not `image/png`, 413 too large, 409 no row of this phone names it or the budget or a cap is spent, 422 not a 128 x 128 PNG (not asked for again for a day); the shapes are `contracts/core/app_logos.json`, shared with the launcher
- `GET /api/devices/contact-photos/{hash}` (bearer) - a contact photo, only for this device's contacts
- `GET /api/devices/wallpapers/{hash}` (bearer) - a wallpaper image, only when ticked for this device
- `POST /api/devices/crashes` (bearer) - launcher crash reports (hash + short trace), see "Crash reports" -> 204
- `POST /api/devices/dns-events` (bearer) - blocked domains, stored only while the phone's log is on (default off) -> 204
- `POST /api/devices/pin-events` (bearer) - `{events: [{id, kind, entry, at_ms, until_ms, failures, level}]}`, the phone's parent-PIN uses, wrong tries and lockouts (design 24, see "Parent PIN") -> 204; 400 only for a body that isn't JSON or has no `events` array, 413 above 100 events
- `POST /api/devices/power` (bearer) - `{off?: {at_ms, boot_count, battery?, reboot?, reason?, location?: {lat, lng, accuracy_m?, at_ms, provider?}}, on?: {at_ms, boot_count, battery?, unlocked_at_ms?}}`, the phone's shutdown (with its last stored fix since 2026-10-25, stored as a fix and marked `shutdown_at`) and start (design 38, `docs/notes/server/notifications.md`) -> 204; 400 for neither part or not one, 413 above 2 KiB
- `POST /api/devices/time-request` (bearer) - `{id, asked_at_ms}` (`id` 16-64 lowercase hex), the kid's "Be om mer tid" (design r13, `docs/notes/server/notifications.md`, "Requests for more time") -> 200 `{"accepted":true}`, `{"accepted":false,"reason":"capped"}` (3 a day, the phone's own day - its reported zone, else Phone Setup's) or `{"accepted":false,"reason":"stale"}` (asked before today); 400 for a body that doesn't parse or a bad id, 413 above 1 KiB; the shapes are `contracts/core/time_request.json`, shared with the launcher
- `POST /api/devices/rule-pause` (bearer) - `{key, minutes, started_at_ms, rules: [{rule_id, until_ms}]}` (`key` 32 lowercase hex), the parent code's pause of the rule in force set offline on the phone's time-rule screen (design 98 §4.4, `handlers::rule_pause`) -> 200 `{"accepted":true,"lift_ids":[..]}` (`"over":true` for a pause already over, stored as an over row), or `{"accepted":false,"reason":"unknown_rule"}`; 400 for a body that fails a check (minutes outside `RULE_LIFT_MINUTES`, a start past the 5-min slack or older than 7 days, 1-8 rules, an end at the start or past start + minutes + slack), 413 above 2 KiB. One `time_lifts` row per rule (a design 93 copy's negative id is its rule's), `created_by` NULL and `phone_key` the key; a retry inserts nothing and never revives an ended row; the phone line `time_lift_phone`; no cap (the user, 2026-11-18): each stored pause is the inbox's `pin_used` line, pushed (security review 2026-11-17 M2; `docs/notes/server/time-rules.md`). The shapes are `contracts/core/rule_pause.json`, shared with the launcher; the policy's `rule_pause: true` says this server takes it
- `POST /api/devices/contact-request` (bearer) - `{id, name, number, matrix_id?, asked_at_ms}` (`id` 16-64 lowercase hex), the kid's contact request from the phone book (design 77 §14, `handlers::contact_requests`; `docs/notes/server/calls-and-contacts.md`, "The kid's contact request") -> 200 `{"accepted":true}` (a retried id too), or `{"accepted":false,"reason":"capped"|"invalid"|"known"}` (three a day in the phone's own day or five open; the name, number - never an emergency number - or Matrix ID refused; the number on the phone or asked for already); 400 for a body that doesn't parse or a bad id, 413 above 1 KiB; the shapes are `contracts/core/contact_request.json`, shared with the launcher; the answers come back as `call_policy.contact_requests`
- `POST /api/devices/contact-request/{id}/photo` (bearer) - the picture the kid gave an accepted request, raw `image/jpeg` or `image/png`, at most 64 KiB and 512 px a side (Calls & Contacts tidied (6), `contact_requests::upload_photo`) -> 204 stored as a parent's contact photo is (re-encoded, no metadata); 400 a bad id, 415 another type, 413 too large, 409 no live request of this phone with that id or one with a picture already, 422 not a picture or too many pixels; "Legg til…" gives it to a contact new to the family; the shapes are `contracts/core/contact_request.json`'s `photo`
- `POST /api/devices/sms-held` (bearer) - `{rows: [{id, at, kind, sender_class, sender, expires_at, state}]}` (at most 50, instants epoch ms), the phone's held and blocked SMS senders - who and when, never what (design 77 D16) -> 200 `{"accepted": n}` (`"capped": true` past 500 held rows a phone, or 500 blocked ones - each
its own bound); 400 `{refused, reason}` for the first row that fails a check (nothing stored), 413 above 16 KiB; forward-only states; the shapes are `contracts/core/sms_contract.json`, shared with the launcher (`sms.rs`; `docs/notes/server/calls-and-contacts.md`, "SMS in Vibb One, step 1")
- `POST /api/devices/setup/ticks` (bearer) - `{step}`, the setup flow's "Gjort" on a step the parent ticks (design 114
  §4.4, `setup_status::tick`) -> 204 (ticked now or before; a new tick writes the phone line `setup_tick_phone` and
  nudges), 400 `{"error": "not_a_parent_step"}` for anything else, 413 above 256 bytes; the shapes are
  `contracts/core/setup_steps.json`'s `tick`, shared with the launcher; the policy's `setup.ticked` carries the ticks
- `GET /api/devices/apps` / `GET /api/devices/apps/{id}/download` (bearer) - update check/download, both scoped to apps selected for this specific device (plus the launcher's own self-update, always included) - see the "global catalog" bullet above; the download is resumable (`Range`/`If-Match`, `X-Release-Tag`; "App downloads" below)
- `GET /api/devices/music/library` (ETag/304, gzip), `/music/entries/{id}/items` (ETag/304, gzip; design 21b), `/music/covers/{hash}`, `/music/files/{id}` (Range, `X-Content-SHA256`) (bearer) - the phone's music library, scoped to its ticks (design 21)
- `POST /api/devices/music/storytel/token` (bearer) - `{}` or `{"stale": "<generation>:<16 hex>"}` (read as bytes, at most 256) → always JSON with `status`, `no-store`: 200 `ok` `{jwt, expires_in_s, session}` (the server's own Storytel JWT, design 58 §2.2), 404 `off`, 409 `refused`/429 `busy` with `retry_after_s`, 502/500 `unreachable`, 503 `key`; 20 asks a rolling hour per phone; the shapes are `contracts/music/storytel_token_answers.json`, shared with both apps
