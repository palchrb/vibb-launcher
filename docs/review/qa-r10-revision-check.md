## New problems

- N1 Low-Medium: **`saveConfig`'s "null" is ambiguous.** §3.2 removes the PIN fields "for `kidLock == null`", but `guardTripped` calls `saveConfig(app, config, ...)` (`PinLockRuntime.kt:1222`) with `config == null` after an `Unreadable` at init (`:439-443`), and has no `kidLock`. The R10-11 promise (no deletion there) only holds if removal is an explicit mode. Fix: `saveConfig(mode = Write(real)|Remove|Keep, ...)`; `guardTripped` and every stand-in/redacted case pass `Keep`; `Remove` only from `configure` with `kidLock == null`; test `guardTripped` after an unreadable init. Say what `PinLockStore.config` returns for `Unreadable` (null at init is fine).
- N2 Medium: **the button is not shown at the first open after a total loss.** `ParentPin.status` reports `untilSync` only when the stored flag `REWRAP` is set (`ParentPin.kt:107`, `PinVault.kt:90`); `status()` never touches the key. The flag is set by the first failed `verify()` (`PinVault.kt:118-121`) or `accept`. After `key all` the status is still "configured", so §8 check 5 ("open: the dialog shows the button") fails and the parent sees no way out until one parent-code try has failed. Fix: evaluate `showReEnrol` again after every result in both dialogs (the `Unavailable(untilSync)` result then reveals the button) and change check 5 to "type any parent code once, then the button shows"; or probe the vault key when the dialog opens (one HMAC, off main).
- N3 Low: **clears outside `LOCK` resurrect a secret.** `resetPreferences` (§3.1 "still clears it") and any remove run outside `LOCK`; the migration's re-read-then-commit (with a first-time keygen inside the hold) can put `ks1:` back after the clear. Fix: removes go through `SealedPrefs.remove(...)` under `LOCK`; add it to the second-thread test.
- N4 Medium: **"another package's activity is refused" is false for lock-task packages and for our own task.**
  - Kiosk on: the lock-task list is the allowlist (`LockTaskHelpers.kt:185-190`) and the permitted keyboards are exactly system + allowlist (`EnforcementPlan.kt:249-250`). An allowlisted keyboard (HeliBoard, launcher/CLAUDE.md "Touch sounds") or app can start its own activity over the lock (its settings, clipboard or help links, a browser if allowlisted); only the re-front loop (0.5 s to 5 s) ends it.
  - Kiosk off: `PIN_LOCK_FEATURES_KIOSK_OFF` has no `BLOCK_ACTIVITY_START_IN_TASK` (`LockTaskHelpers.kt:195`, only with a VoIP call), so an activity our own field starts into the lock's task (the selection toolbar's PROCESS_TEXT/Share items) is not blocked; only IME-originated NEW_TASK starts hit the violation check.
  - The permit lists exist only while `allowlist != null` (`EnforcementPlan.kt:250`, `takeIf { appsManaged }`) and are `null` in a window, so on a calls-only phone any enabled keyboard is live. The note says "outside windows" without that condition.
  - Fix, strongest first: (c) our own 31-key pad (no IME, 24b §1.8 intact); or keep (a) and (1) disable selection, context menu, long-click and insertion callbacks on the field, (2) rewrite the argument to "system + allowlisted keyboards; their own activities can open over the lock for seconds", (3) add to check 5: HeliBoard allowlisted, kiosk on and off, tap every toolbar key (gear, clipboard, mic, emoji), long-press the field.
- N5 Medium: **the second dialog has no lock-task argument at all.** `ParentPinDialog` serves the time-rule screen (`LockActivity`, not lock-tasked with the kiosk off; protected only by suspension, and keyboards are `neverRestrict`), the Settings gate, pause and install mode. §5's "always in lock task while LOCKED" covers only `PinLockActivity`. Fix: show the button in the lock's dialog only, or add the separate argument. Also change "Neither half is kid-triggerable" to "not kid-controllable": a transient Keystore fault at boot can persist `REWRAP` and make the token `Unreadable` at once, so the button shows until it heals (harmless; say it).
- N6 Low: **main can still wait on `LOCK`.** R10-7's complaint was main waiting behind a background keygen. The keygen stays inside `LOCK` (migration, `edit`) and the note does not say a non-migrating `read` skips `LOCK` on a memo miss. Fix: "`read(migrate = false)` never takes `LOCK`"; first-time keygen only in `seal`.
- N7 Low: **`DeviceToken.set` runs on main today.** Settings' enrolment writes the token inside `withContext(Dispatchers.Main)` (`SettingsFragmentLauncher.kt:352-353`); a sealed, committed `set` (possible keygen) is Keystore work on main. Fix: `Enrollment.enroll` does the write on IO; the UI part only toasts.
- N8 Low: **`recreate()` in `set` can strand a window.** Run while a window is open with a kid-set Android credential, the orphaned reset token cannot be replaced (`resetTokenNeeded` needs `!secureNow`, `WindowRelockPlan.kt:127-128`): the relock reports "credential left" and the lock stays inactive (`ANDROID_CREDENTIAL`). Rare (two seal failures in a row). Fix: state it in §3.1, or `recreate()` only when the alias is missing or invalidated.
