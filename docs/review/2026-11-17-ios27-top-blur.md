# iOS 27: a grey blur that stays over the status bar after the PWA returns from the background

Research for PLAN's item "iOS 27: the grey blur over the status bar still comes back after the PWA has been out of
focus" (2026-11-17). Server 0.82.0 (design 109 A) is on the phone. Nothing in the repo was changed.

Labels used below: **[confirmed]** means read in a primary source (WebKit's source on `main`, a WebKit bug, an Apple
forum post by Apple staff, or a device-tested PR). **[inferred]** means my reading, not measured on a device. The WebKit
source is today's `main`; iOS 27.x ships a branch of it, so details can differ.

## 1. What the band is

- **[confirmed]** On iOS 26 and later every `UIScrollView`, including WKWebView's, has a UIKit "top edge effect" (the
  scroll pocket): a soft blur and dim at the top. WebKit turns it off itself (`-[WKWebView _updateHiddenScrollPocketEdges]`
  sets `[_scrollView _wk_topEdgeEffect].internallyHidden = [self _shouldHideTopScrollPocket]`). On iPhone, with the soft
  style, it hides the pocket only while a **top colour extension view** is visible
  (`_hasVisibleColorExtensionView:Top`). That view exists only when the page reports a **fixed container edge** at the
  top (our `.top-strip`) and the web view has an obscured top inset. (`Source/WebKit/UIProcess/API/Cocoa/WKWebView.mm`,
  `WKWebViewIOS.mm`)
- **[confirmed]** On iOS 27 a home-screen web app cannot draw under the status bar. The system colours that area to
  match the page (WebKit 317153, comment 2). Device-tested on iOS 27.2 (kuraneko1/dsh-mobile-maxxing#91): with
  `black-translucent` the blur stays whatever the page does; with `default` and a fixed box taller than 10 px with a
  background, the blur is gone. That is the setup we already ship (`head.html` `default`, `.top-strip` at 12 px).
- **[confirmed]** Apple's developer forum thread 845744 (Sep 2026) reports a **stale blur glass effect at the top of
  UITableView and WKWebView** after updating to iOS 27, in apps that add no blur code. The poster says the rendering
  state "leaks across the whole app process" and stays until a view controller is pushed or popped. An Apple Frameworks
  Engineer replied that "app adoption should not be necessary", which treats it as Apple's bug. A third poster reports
  the same blur at the top of every installed PWA on iOS 27.0, never on iOS 26. The only workaround posted is native:
  set `scrollView.topEdgeEffect.hidden = YES` again in `willMoveToWindow:`. A web page has no access to that.

## 2. The most likely mechanism

Given "only after the background, stays until killed, new in 27":

1. **[inferred, fits forum 845744]** When the app goes to the background and comes back (the scene detaches and
   reattaches, and the app-switcher snapshots are taken), iOS 27's UIKit brings the top edge effect back on its own,
   or renders it stale, even though WebKit's flag still says "hidden".
2. **[confirmed, source]** WebKit sets that flag only when its own inputs change. These are the fixed edges it receives
   from the web process (`-_updateFixedContainerEdges:` returns early when `_fixedContainerEdges == edges`), the
   extension view appearing or disappearing, the obscured insets, and the hide reasons. Setting the flag again to the
   same YES is most likely a no-op inside UIKit.
3. **[confirmed, source]** The web process recomputes the edges only when `m_needsFixedContainerEdgesUpdate` is set:
   - a main-frame load (`WebPage::didCommitLoad`);
   - a fixed or sticky renderer added or removed (`LocalFrameView::add/removeViewportConstrainedObject` →
     `didAddOrRemoveViewportConstrainedObjects`);
   - a change of the obscured insets;
   - a sticky node that starts sticking (`WebPage.cpp`, `WebPageCocoa.mm` `willCommitMainFrameData`,
     `LocalFrameView.cpp`).

   It does not recompute on a repaint or on a layout of an existing box. So design 104's colour nudge was never
   seen, and design 109's `left: -1px` alone was never seen either.
4. **[confirmed, source]** Design 109's clone does reach WKWebView. Replacing the strip removes and adds a fixed
   renderer, and the clone's `#0C0C15` differs from `#0C0C14`. But all that does is re-run WebKit's update with the
   same result, "hide = YES" (only the colour changes). The blur stayed on 0.82.0. That is consistent with point 1:
   **a same-value "hidden" does not cure the stale UIKit state. A real NO → YES transition may.**
5. **[confirmed, source]** A tab switch does not reset it. A new document with the same night strip sends the same
   edge, and WKWebView's `_fixedContainerEdges` is not reset by a load (only `WebPageProxy`'s internals are), so it
   returns early. Killing the app creates a new WKWebView, which is why only a kill helps. Design 109 §A.2 guessed
   this; the source confirms it.
6. **[confirmed, source]** On iPhone the top edge can be sampled again after the user has interacted or scrolled:
   `defaultTopContentInsetBackgroundCanChangeAfterScrolling()` is `currentUserInterfaceIdiomIsSmallScreen()`
   (`WebPreferencesDefaultValuesCocoa.mm`). So a page can take its top edge away and get it back within the same
   document. That is the lever for fix 1.

**The one page-side lever left:** make WebKit go from "top edge night" to "no top edge" and back. When the edge goes
away, `-[WKColorExtensionView fadeOut]` runs, `isHiddenOrFadingOut` is YES at once, and `internallyHidden` becomes
**NO**. When the edge returns, the view is revealed and `internallyHidden` becomes **YES** again. That is the same
kind of fresh "hidden" that the native forum workaround sets. **[inferred]** Whether this clears iOS 27's stale effect
is not known until it runs on the phone.

How to make "no top edge" reliably **[confirmed, source]**: `Page::updateFixedContainerEdges` keeps the old colour when
nothing is found, as long as the last strip element still has a visible renderer. So the old strip must leave the
render tree (removed or `display: none`). Changing its colour, size or `position` while it stays rendered keeps the old
edge.

## 3. Candidate fixes, ranked

All three are in `server/static/top-strip.js` and `server/static/style.css`, with the head's `?v=` bumped. Each is
small and reverts with one commit.

### Fix 1 (first choice): take the edge away and back, once, about 1 s after a real return

- **style.css**: a stand-in that paints exactly like the strip but is not fixed, so WebKit does not count it:
  `.top-strip-standin { position: absolute; z-index: 4000; top: 0; left: 0; right: 0; height: var(--top-strip);
  background: var(--night); pointer-events: none; }`. The app shell's document does not scroll, so an absolute box at
  top 0 sits exactly where the fixed strip is. On the four `doc-scroll` sign-in pages it scrolls with the page for the
  ~100 ms it exists.
- **top-strip.js** (still only when `navigator.standalone === true`):
  - Record `hiddenAt` on `visibilitychange` → hidden.
  - On → visible after at least 2 s hidden (and on `pageshow` with `persisted`), wait `EDGE_DELAY_MS` (1000), then:
    1. `stand = strip.cloneNode(false); stand.className = "top-strip-standin";`
       `strip.parentNode.replaceChild(stand, strip)`. The fixed renderer goes, so WebKit recomputes and reports no
       top edge, and the pocket's flag goes to NO.
    2. Two `requestAnimationFrame`s, so at least one commit carries "no edge", then `EDGE_GAP_MS` (0-100).
    3. Replace the stand-in with a plain `.top-strip` clone. The fixed renderer is back, the top edge is night again,
       and the flag goes to YES.
  - Cancel a pending toggle on hidden or `pagehide`. Skip it under `html.locked` and `html.veiled`: the veil rule
    `body > :not(.top-strip)` would hide the stand-in.
  - Keep a cap, as design 109 does, so the strip is never left out.
  - Drop design 109's clone/hold/theme-color and design 104's 0.3/1/3 s retries in this variant. They do nothing
    useful, and fewer moving parts make the result easier to read.
- **Visible cost [inferred]**: on each return, a flash of the system pocket in the status area for a few frames plus
  WKColorExtensionView's 0.1 s fade, even when nothing was wrong. The page itself does not change. Under the
  "visible-cost choices first" rule, this cost is the user's call.
- **Risk**: if Apple's build has the top-edge lock on for iPhone (it is off on `main`), the edge would not come back
  within the same document. The blur would then stay until the next tab switch, which loads a new document that is
  sampled while it parses. That is no worse than today and clears on the next tab tap.

### Fix 2 (no cost when things are fine): the same toggle, but only on page loads and refreshes in place

- The same stand-in and toggle function. Run it once after `load` on every page, and on `handy:swapped` (pull to
  refresh on Devices and a phone's summary, and the in-place reloads). Do nothing on a return.
- **Effect**: when the blur is stuck, any tab tap or pull-down clears it, instead of killing the app. The flash
  happens only while a new page appears anyway, which is much less noticeable.
- It does not prevent the blur, so it is a fallback if Fix 1 works but its flash on every return bothers the user.
  Fixes 1 and 2 can also be combined.

### Fix 3: Fix 1 with a longer gap (if Fix 1's fast toggle is coalesced)

- `EDGE_GAP_MS` = 300, and the toggle at 1 s and again at 3 s after the return.
- UIKit may merge a NO → YES flip that lands in the same Core Animation transaction. A longer gap makes sure UIKit
  sees "visible" before "hidden". The cost is a longer flash: about 0.3 s of pocket per toggle.

### Considered and rejected

- **`theme-color` re-set on `visibilitychange`**: `theme-color` is not what WKWebView uses for the pocket or the
  extension. It uses the fixed edge colour, else `underPageBackgroundColor` (`_updateTopScrollPocketCaptureColor`).
  Design 109 already changes it, with no effect.
- **Toggling `apple-mobile-web-app-status-bar-style` at runtime**: iOS reads it when the app is added, and
  `black-translucent` keeps the blur on iOS 27.2 (device-tested, dsh-mobile-maxxing#91).
- **Manifest `display`** (`fullscreen` / `minimal-ui`): it needs the app removed and added again, and does not touch
  the edge effect.
- **A 1 px scroll**: our document does not scroll (`main` does). A scroll of `main` is not a WebKit trigger.
- **`backdrop-filter`**: nothing in the top hit-test lineage has one. Only `.tab-bar` does, at the bottom, and it is
  not fixed.
- **Making the strip not fixed for good**: the band would then be the pocket all the time (WebKit 316008 / 317153,
  2026-11-10 note).

## 4. Testing on the iPhone with little effort

**Today, no release (diagnostics):** when the blur is stuck, try these in order and note which one clears it.

1. Tap another tab. By the source, this should *not* clear it. If it does, the model above is wrong somewhere.
2. Open a system sheet over the app, for example a page with a `<select>` or date picker, or a long-press on a link.
   If this clears it, it matches forum 845744 (a view-controller transition clears the stale effect), and Fixes 1-3
   are aimed at the right thing.
3. Pull down Control Centre and let it go.
4. Settings › Accessibility › Display & Text Size › Reduce Transparency, on and back. Watch whether the band turns
   solid. That would show it is the system material, not our paint.
5. Check the exact iOS version and update to the latest 27.x. Apple treats the stale effect as its own bug.

**Can each variant be tried without a server release?** Not with the current code, which has no switch.

- Static files are served from disk (`ServeDir::new("static")`, `/app/static` in the image). One could
  `docker cp` a changed `top-strip.js` into the running container, but no `Cache-Control` is set, so Safari's
  heuristic cache may keep the old copy. Watchtower's next image would also undo it. Not recommended.

**One small server release, then every variant from the phone:** `top-strip.js` reads a variant from
`localStorage` `handy-strip`, set by `?strip=<v>` on any page, on the pattern of `nav-timing.js`'s `?timing=1`. The
installed app has no address bar and has its own storage, so Settings › About (`templates/updates.html`, beside the
existing `/updates?timing=1#timing` row) gets one row group "Status bar test" with links `?strip=109` (today's
default), `?strip=a` (Fix 1), `?strip=b` (Fix 2), `?strip=c` (Fix 3) and `?strip=none` (no script: the control). The
row's value shows the active variant.

- After one release, the user picks a variant, kills the app once, and uses it for a day.
- To report, the user answers: did the blur come (yes/no); if yes, did it clear by itself about 1-3 s later (variants
  a/c), or on a tab tap (b); and was any flicker at the top visible on an ordinary return.
- Order to test: **a** first (most direct); if it flickers too much or does not help, **c**; then **b** as the
  low-cost fallback; **none** for a day if the results are unclear, to see whether the nudges matter at all.
- Tests: `jstest/top-strip.test.js` (the switch, the toggle's two DOM swaps, the cancel on hidden, the skip under
  `html.veiled`) and the `shell.rs` pins of the new rule and `?v=`.
