## Medium

### M1. `caldav_write`'s row is not gated by the kid's writes, so it can outlive the parent's switch-off

- **Where:** `server/src/integration_health.rs:336` (`FOR_DEVICE`: `h.key = 'caldav_write' AND h.scope = 'device:' || ?1`,
  with no join); the row is written by `calendar_kid_events.rs` `record_failure` and cleared only by
  `work_claimed`'s `Step::Wrote` (`calendar_kid_events.rs:2806`).
- **What:** every other scope maps through a live mapping row (§2.3: "a choice the parent made maps to no phone").
  `device:<id>` maps on its own. Scenario: the marked calendar answers 403 (`write_refused`, a stop), so the phone gets
  "Avtaler fra telefonen lagres ikke". The parent then unticks "the kid's events" for that phone, or unmarks the
  calendar. Nothing is written for the phone again, so no `Step::Wrote` clears the row. The orange row stays on the
  phone and in the Devices list count until `retention` drops it 30 days after the last failure. The Calendar page shows
  nothing wrong, so the parent has no way to clear it. The same happens to a transient run (`Down`) that ends because
  the writes were switched off.
- **Fix:** map `caldav_write` only while the phone still writes:
  `... AND EXISTS (SELECT 1 FROM device_calendar_feeds f JOIN calendar_sources s ON s.id = f.source_id WHERE
  f.device_id = ?1 AND f.kid_writes = 1 AND s.kind = 'caldav')`. Test it in `tests::attention`: a stop, then
  `kid_writes = 0`, and the row is gone.

### M2. A refused post's `too_big` is recorded as a CalDAV stop that only a write clears (builder deviation 3: rejected)

- **Where:** `server/src/calendar_kid_events.rs:1154` (`record_failure(.., "too_big")` in `post_inner`),
  `:1745` (`class_of`: `too_big` is `Stop`), `:1194` (the next accepted post clears `device_kid_events.error =
  'too_big'`), `:2519` (`stop = |e| e != "too_big"`: the write loop does not treat `too_big` as a stop).
- **What:** `too_big` comes only from the phone's own post being over the limit. That is the phone's set refused, not
  CalDAV, the same as `bad_set`, which §2.1 leaves unrecorded. The write loop keeps writing the stored set. Because the
  row is cleared only at the next `Step::Wrote`, it goes wrong both ways:
  - The kid's set goes over the limit, and the kid deletes events until the set is back to the one already stored and
    written. The next post is accepted and clears `error` at `:1194`, but the plan writes nothing. The Calendar page is
    clean while "Avtaler fra telefonen lagres ikke" stays (and M1's 30 days apply).
  - A write still waiting from the older set succeeds after the refused post. That clears the row while the phone's
    newest set is still refused.
- **Fix:** keep it recorded, but let the row follow `device_kid_events.error`. Call `integration_health::ok(db,
  "caldav_write", "device:<id>")` in the accepted-post transaction's aftermath when the stored error was `too_big`
  (read it before the `UPDATE` at `:1192`). Do the same where `account_tested` and `before_fetch` clear the stops they
  answer, or simply gate the stop class in `FOR_DEVICE` on `device_kid_events.error IS NOT NULL` for that phone.
  Test: too big, then a smaller set equal to the stored one, and the row is gone.

## Low

### L1. A stale retry alarm starts the VPN service in the foreground after the filter was turned off

- **Where:** `launcher/.../server/VpnRetryAlarm.kt:76-88` (the receiver always calls `writeAlwaysOn` and
  `KidVpnService.start`); `KidVpnService.stop` and `stopSelfCleanly` (the filter-off path) never run
  `VpnFilterWatch.check`, so §3.1's "cancelled at `UP` or `OFF`" never happens for `OFF` reached by a stop.
- **What:** the filter is down, so the alarm is armed. The parent then turns the filter off (or a pause starts) with no
  Bare Vibb, so `apply()` stops the service and no check runs. Up to 5 minutes later the alarm fires. `start()` finds no
  service running and uses `startForegroundService`. `onCreate` posts the "connecting" notification, and then
  `onStartCommand` stops because no shape is wanted. The kid sees a notification flash for nothing. That breaks
  "calm" on the kid's phone, but nothing is left in a wrong state.
- **Fix:** read `MobileNetworkRuntime.vpnFilterStateNow()` first in `onReceive`. On `OFF`, cancel and return. Also,
  or instead, call `VpnRetryAlarm.cancel` from `KidVpnService.stop`.

### L2. The filter page's "Nede i …" is frozen at the last report while the phone shows as connected

- **Where:** `server/src/handlers/device_pages.rs:1819-1839`.
- **What:** `down_ms` is the period's length when the phone reported. While the filter is down, reports go no more
  often than before (the 30-minute backstop, or a sync), so the page can say "Nede i 12 min" 40 minutes into an
  outage. The " · ved siste rapport" mark is added only when the phone is Offline or Disconnected.
- **Fix:** while the phone is connected, show `down_ms + (now - reported_at)`. That adds two durations measured on
  their own clocks, never two instants, so H3's rule holds. Or show the mark whenever the report is older than a few
  minutes.

### L3. MET's `cut` counts as a failure even though the forecast is stored and shown

- **Where:** `server/src/weather_cache.rs:589`.
- **What:** this follows §2.1's table, but a body MET cut short keeps its whole hours, so the kid sees weather. If
  cuts were routine (a long forecast near the size cap), every fetch would add a failure, and after 6 hours "Været
  hentes ikke" would show on every weather phone while the weather is on the lock screen.
- **Fix:** record `cut` as `ok` (its note stays in `weather_cells.last_error` for the logs), or make it a design
  note that this was weighed.

### L4. An uploaded backup becomes the newest and is never checked until a restart

- **Where:** `server/src/handlers/backups.rs:1596` (`backup-<now>-uploaded-<nanos>.zip`) and `backup_state` (`:592`).
- **What:** the upload is named with the current time, so it sorts as the newest file. It has no `file:` row, so the
  newest backup loses its "kontrollert". A failing check on the backup before it also stops showing. The upload is
  checked only by `check_newest_unchecked` at the next start.
- **Fix:** spawn `check_and_record` after a successful upload, as `perform_backup` does.

### L5. Copy for the backups folder: one (i) for two problems, and a startup line that says "use a named volume"

- **Where:** `server/templates/backups.html` (the one `settings.backups.check_info` for both `Check` and `Run`);
  `server/src/startup.rs:33`.
- **What:**
  - For a failed backup (`run_failed`), the (i)'s "Vibb åpner hver nye kopi og sjekker databasen i den" explains a
    check that never ran.
  - When `data/backups` isn't writable, the start's error says "In Docker: use a named volume". That points the owner
    away from the bind mount that §5 now asks for.
- **Fix:**
  - Give `Run` its own (i), for example "Ta en ny kopi nå; feiler den også, se serverloggen.", in nb and en.
  - For `data/backups`, word the line as the compose comment does: `chown 65532:65532 backups`.

### L6. Storytel's `LoginStatus` is transient for any status

- **Where:** `server/src/storytel.rs:982`.
- **What:** §2.1 classes `LoginStatus` as transient for 5xx, 408 and 429 only. A 400 or 404 from the login endpoint
  (Storytel changed its API) is not an outage the backoff mends. It shows as "Storytel svarer ikke" after 12 hours,
  which is the right fact at least. The builder didn't list this deviation.
- **Fix:** match `Status`'s arm (`>= 500 | 408 | 429` transient, the rest `None`), or record it as a design note.

### L7. `ok()`'s throttle still takes a write lock on every call

- **Where:** `server/src/integration_health.rs:131-138`.
- **What:** the `INSERT … ON CONFLICT DO UPDATE … WHERE` changes no row inside the 10 minutes, but SQLite still opens
  a write transaction for each Spotify and Storytel request. QA L10 wanted the per-request path cheap. It is cheap in
  I/O, but it serialises with every other writer.
- **Fix:** keep an in-memory `(key, scope) -> last ok written` map (a `Mutex<HashMap>` on `AppState`, or a
  `static`), and skip the statement inside `OK_EVERY` unless a failure was recorded since.

### L8. An unreadable `BOOT_COUNT` produces a period id the server drops

- **Where:** `launcher/.../server/VpnRetryAlarm.kt:101-106` (`-1`); `server/src/mobile_network.rs`
  (`clean_vpn_filter`: `period` must be `[0-9:]`).
- **What:** with `-1` the id is `"-1:<ms>"`. The server drops it, so `filter_down_intake` returns early and no event
  is raised, even though the row shows. `BOOT_COUNT` is readable on 14-17, so this is theoretical.
- **Fix:** fall back to `0`, which keeps the shape and is what the comment already relies on: a period then ends only
  when elapsed realtime runs back past its start.

### L9. Calendar codes are text: the `_ => None` arm drops a new code silently (builder deviation 1: accepted, with a note)

- **Where:** `server/src/calendar_feeds.rs` `class_of` and `tests::every_feed_code_is_classed`.
- **What:** the test finds codes with a regex over three forms. A code built any other way, from a `const` or a
  helper, gets past both the test and the arm. The test is a fair replacement for the exhaustive match the design
  asked for, because `FeedError.code` is `&'static str` across three modules.
- **Fix:** log the unclassed code in the `_` arm (`tracing::warn!`), so a miss shows in the log rather than as
  silence. Separately, `FOR_DEVICE` (`integration_health.rs:336`) is one line of about 2,000 characters. Split it with
  `\` continuations so the next mapping can be reviewed.

## The builder's deviations

1. **Calendar codes are text, checked by a test:** accepted (L9).
2. **A checksum mismatch is transient until refused, then a stop:** accepted. Before the third mismatch nothing is
   remembered, so a transient class is the honest one, and the refusal becomes `Fix` at once
   (`tracked_apps::class_of`, `record_health`'s `refused` check).
3. **`caldav_write`'s `too_big` is a stop that clears only at the next good write:** rejected (M2).
4. **`settings.notifications.switch.filter_down`:** accepted. Every existing switch key is `settings.notifications.switch.*`.
5. **On `/dns` a down phone's line replaces its DNS line:** accepted. Down supersedes an upstream or lookup line, and
   the bypass lines are still added before the `continue`.

## Checked and fine

- **§2.2's rule:** `raised` follows rules 1-4 exactly. The upserts keep `failing_since` across a run, and any success
  clears it. The throttle writes when the row is failing or new. `Title` groups per title with summed counts.
  `read_from_report` excludes `Integration`.
- **The scopes:** every `FOR_DEVICE` arm but M1's goes through a live mapping row. That covers Vibb One on every phone,
  disabled apps on none, weather only where it is on, a feed only where it is in force (the override, then the feed's
  own switch), and Storytel and Spotify by the policy.
- **The call sites:** a remembered refusal's skip records nothing. `OlderVersion` records `ok`. MET is family-wide.
  CalDAV's stops go to `account:` and are re-recorded while the account stays stopped. Spotify's `api_get` calls
  `mint` directly, so nothing is counted twice. `music_sweep` records NRK and RSS only, and not for a recheck.
  `blocklist` uses the typed `FeedFailure`.
- **Privacy:** codes are enum names or fixed strings, scopes are ids and file names. No URL, error text or token
  reaches a row. `CheckError::Network` and `FetchError` both map to `"network"`.
- **H3, the down period:** it is measured in elapsed realtime with `BOOT_COUNT`. A stored period of another boot, or
  one that starts after now, is dropped. A failed establish starts one at once, and a check only after the process's
  first minute. Every tunnel-up path goes through `switchTo`, which checks, so a recovery always ends the period. The
  server never subtracts two clocks: the event's instant is server-now minus `down_ms`.
- **The retry on Android 14-17:** no API above 34 is used (`setAndAllowWhileIdle` 23, `getStartElapsedRealtime` 24,
  `BOOT_COUNT` 24). The alarm is inexact, so it needs no exact-alarm permission. The `PendingIntent` is explicit and
  immutable, to a receiver that isn't exported. The background FGS start is covered by the Device Owner and
  `ACTIVATE_VPN` exemptions. The alarm re-arms in the receiver while the state is down. There is one retry chain:
  `retryTunnel` doesn't reschedule after a switch that ran, and `reshapeRetry` carries the doubling. Covered by the
  source-scan test.
- **The contract:** `server/testdata/mobile_network.json` and `launcher/app/src/test/resources/mobile_network.json`
  are byte-identical (`cmp`). `MobileNetworkTest` runs `states`, `periods`, `alarm` and `sync`, encodes `reports` and
  checks `report_after_ms`. `tests::mobile_network::the_contract` posts `reports` and runs `raise` and `clean`. Both
  sides compare the copies, and the CI path filters already cover the file.
- **The backup check (H1):** `restorable` needs `success`, a known version, that version's checksum, and none newer.
  Tests show an older backup passes, and that a newer version and a changed checksum fail. The scratch copy is
  unique (time, pid, counter), sits in `data/`, and is removed on every path. A failed write is `NoRoom`, which records
  nothing. `a_backup_restores` goes through `apply_restore_request`.
- **The EXDEV copy:** only `CrossesDevices` takes the copy path. The `.partial` is fsynced and then renamed, a failed
  copy removes it, and `snapshot`'s outer cleanup removes the scratch. `sweep_scratch` runs right after the writable
  checks, before the restore and `pre_migration_backup`, so it can't remove a live `.partial`. It also runs long
  before `check_newest_unchecked` makes a scratch. Nothing else renames into `data/backups`: the upload writes in
  place and the prerestore copies.
- **Migration 0158:** the table matches §2.1. Both `ALTER`s are additive with safe defaults
  (`push_filter_down` on). `retention` prunes after 30 days with a text comparison in the stored format.
- **Words in the UI:** nb and en are complete and match §6 word for word. Each title is a fact of six words or fewer,
  with no sub-lines. How-tos sit behind an (i). "kontrollert" is quiet. No forms were added, so no save can jump.
- **Push and event limits:** one event per period (`UNIQUE (device_id, kind, dedup_key)`), with the per-kind hourly
  budget and the urgent push budget on top. The phone needs at least 10 minutes down per period, so a flapping filter
  tops out at a few an hour. There is no event for a parent's off or a paused report, and Integration rows are
  Attention only.
