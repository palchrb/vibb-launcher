# C1 code QA: compatibility code out (2026-11-18)

Scope: `git diff origin/main...c1-compat-out` at `3f424460e` (steps 1-15 of `docs/review/2026-11-17-c1-inventory.md`):
server handlers, policy, retention, music bridge and AIDL, the launcher's policy decode and sync, the music app, the
shared contract files, `scripts/release-version.sh` and the docs. Read-only; nothing built or run (CI green on HEAD).

**Verdict: no High. One Medium (the release order for the kid's phone, which runs rc.7) and nine Lows: comments,
naming, one short fail-closed window after the update, and a test row.** Every removed "older server" read now
falls back to a safe value: off, unknown, or nothing let out.

## Medium

### M1. Release order: the kid's phone runs rc.7, so the server must go first

- **Where:** `launcher/app/src/main/java/com/kidslauncher/mdm/server/StatusCapabilities.kt:8`. The launcher now
  claims only `android_keyguard_v1`. Before C1, the server (`origin/main` `server/src/handlers/device_api.rs:364-376`
  and `:455-497`) gated several parts of the policy on those claims.
- **What breaks under the old server:** if the C1 launcher runs against a server from before C1, the old server
  treats it as an old launcher:
  - it leaves out `unified_push`, `server_tls`, the zones and `kid_caldav`;
  - it sends commands at most once (no receipts);
  - it serves `row` for lock reminders;
  - the Calls page says the phone "stopped reporting that it screens calls" and refuses the SMS-engine pairs.
- **The worst case is UnifiedPush.** `UpView.of` reads a missing `unified_push` as off, and the reconcile then drops
  the registrations and tells the apps they are unregistered. Element X would lose its push until the server
  catches up.
- **The opposite order is safe.** rc.7 (the kid's phone, PLAN "QR setup made robust" (1)) still claims everything,
  and the new server sends every key regardless.
  - The only loss is the music object: rc.7 refuses a `music` object without `mobile_data` (`origin/main`
    `MusicPlan.kt:133`) and keeps its last music settings, so they stay frozen until the launcher updates.
  - The rest of the policy is unaffected.
- **Fix: add to step 16, in PLAN and the release notes.**
  - The emulators get the RCs before the server tag, as the inventory says.
  - The kid's phone gets the C1 launcher and music RCs only **after** the C1 server is live (Watchtower).
  - Install Now on the kid's phone waits for the server tag.
  - If a C1 launcher ever meets an old server, expect UP apps to re-register afterwards.

## Low

### L1. Group MMS blocked between the launcher update and its first sync
- **Where:**
  - `launcher/app/src/main/java/com/kidslauncher/mdm/server/dto/CallPolicy.kt:38` and
    `launcher/app/src/main/java/com/kidslauncher/mdm/calls/CallRules.kt:98`: the `smsGroups` default went from `true`
    to `false` (L-10).
  - The cause is the cache write in `storeAcceptedPolicy`, `server/MdmSyncWorker.kt:1405`: `ServerJson` has no
    `encodeDefaults`, so a value equal to its default is never written.
- **Scenario:**
  - rc.7 never wrote `sms_groups: true` into `kid_mode_policy`, `last_call_rules` or BootCallPolicy's
    device-encrypted (DE) copy.
  - The C1 build reads those caches as `false`.
  - Until the first accepted sync after the update, every group MMS is `Blocked` (`MmsFlow.kt:482`) and group
    sends are refused (`SmsEngine.kt:541,651`).
  - A phone that stays offline after the update stays that way.
- **This fails closed:** the server always sends the key, and the first sync heals it.
- **Fix:** none needed in code. One line in the RC's release notes, or trigger a sync right after the self-update
  (it may already run).

### L2. A stray rename in `attention::Kind`
- **Where:** `server/src/attention.rs:64,154,250,315,357,408`.
- **What happened:** step 12e renamed `lock_glance::Note::NoNotificationAccess` to `CallsOnly` (intended there). The
  same rename also hit `attention::Kind::NoNotificationAccess`, which now reads `Kind::CallsOnly` while its slug,
  title and fact are still "notification-access".
- **Effect:** no change in behaviour, but the name is misleading.
- **Fix:** rename it back to `NoNotificationAccess`.

### L3. A comment says the opposite of the code: `allow_blocked`
- **Where:** `server/src/handlers/device_api.rs:439-440`. It says "a row queued before 0068 has none, and the phone
  then lets out every block, as it did".
- **What the code does since L-8:** a `null` `allow` lets nothing out (`WindowRelockPlan.kt`), and so does a
  payload that doesn't parse (`device_api.rs:446-449` sends `null`).
- **Fix:** "a payload that isn't one is sent as none: the phone then lets nothing out."

### L4. Launcher comments that say the opposite of the code
- `launcher/.../server/dto/PolicyResponse.kt:121-123`: "Missing from a fresh response = the server's own default
  (Element X, sender only)". Since L-5 it is `UNKNOWN` (missed calls only).
- `launcher/.../server/dto/PolicyResponse.kt:128-129`: "Missing = every calendar shown". Since L-9 it is `UNKNOWN`
  (Dagen off).
- `launcher/.../server/WindowRelockPlan.kt:343`: "the blocks go". With a `null` `listed` they no longer go.
- `launcher/.../timerules/TimeRequests.kt:204`: an orphaned KDoc ("The largest lift id in [policy]") now sits on
  `LOG_TAG`.
- **Fix:** reword the first three and delete the fourth.

### L5. The retention keeper clause in `replace_over_budget` guards nothing
- **Where:** `server/src/retention.rs:136`, `AND id IS NOT (SELECT MAX(id) FROM device_status WHERE device_id = ?2)`.
- **Why:** the only caller (`device_api.rs:1606-1608`) runs after the new report is inserted. `previous_id` is
  therefore never the `MAX(id)`, and the clause is always true.
- **Harmless:** the A-3 rewrite is otherwise correct.
  - `prune` keeps every report inside `STATUS_HISTORY_HOURS`, plus each phone's newest report from before the
    window. A phone that went quiet keeps its last word, and nothing is kept forever.
  - The old keeper's only reader, the Calls page's "stopped reporting that it screens calls", left with A-4.
  - `kid_lock::queue_pin_command` reads only the latest report since enrolment.
- **Fix:** drop the clause, or say in the doc comment that it only guards against a call made before the insert.

### L6. Fallback location policy: from a fix every 10 minutes to on request
- **Where:** L-3. With no `location_policy`, the launcher now uses `LocationPolicy()` (`on_request`, 30-minute max
  age) in `MdmSyncWorker.kt:301`, `BackstopAlarm.kt:48`, `WifiNetworksActivity.kt:130` and `PowerEvents.kt`.
- **Who hits it:** only a phone without a usable cache. `LastEnforcedPlan` doesn't carry `locationPolicy`, so this
  covers a corrupt or missing cache, not only an old server.
- **Effect:** such a phone now takes fewer fixes than before. That means less data, nothing permissive.
- **Fix:** none, but it needs a conscious OK.

### L7. The release script's self-test lost its minor-version-below rows
- **Where:** `scripts/release-version.sh:79-83`. `check launcher-v0.35.9 -` and `check music-v0.4.9 -` went.
- **What still covers it:**
  - Launcher: the contract's new `launcher-v0.35.0` row, through the contract loop.
  - Music: no row below `music-v0.5.0-rc.4` other than `-rc.3`, so "a lower minor version is refused" is no longer
    tested for music.
- **Fix:** put the two `check` lines back. They were never compatibility code; they pin the refusal the inventory
  keeps (E-4).

### L8. A duplicate i18n key (already on `origin/main`, found here)
- **Where:** `server/src/i18n/en.json:1586,1592` and `nb.json:1586,1592`, `"error.unknown_section"` twice.
- **Effect:** serde keeps the last value ("Unknown form - nothing was saved"). C1 sends more posts to this key
  (schedules, `/policy`, calls/settings with no `section`).
- **Fix:** delete the "Unknown section" / "Ukjent del" lines.

### L9. Old Storytel lines in the security log keep their words and their 180 days
- **Where:** `PhoneLine::StorytelLoginSent` left `server/src/security.rs`. The i18n keys
  `security.event.storytel_login_sent` and `security.detail.storytel_sent` stay.
- **Effect:** stored rows still show and are still pruned at `SECURITY_EVENT_DAYS` (`tests/cleanup.rs:809`).
- **Fix:** none. Delete the two keys once 180 days have passed since the last row (after mid-May 2027).
