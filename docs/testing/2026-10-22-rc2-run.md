  debugging off, Parent PIN, Child PIN `1357`, calls managed with "Mamma" +4791234567, Messages and Chrome allowed.

  "Hemmelig melding SECRET-42" came from `adb emu sms send`.

  the switch went through the PIN command (`PIN command: pin set (rev 1)`), not our keypad - the same as the F3 run.
  The keypad migration itself was covered by the d59 RC run.
- Logs: `logcat -v epoch -s BootCover BootCallReceiver BootHome HomeFront Application PinLock PinLockActivity
  AndroidLock KeyguardCover KidCallScreening WindowRelock VoipCalls LockTaskChrome MdmSyncWorker
  MdmDeviceAdminReceiver ActivityTaskManager:I`, our package's `am_anr`/`am_kill`/`am_proc_died` events, both kept
  across reboots, and the 0.2 s `topResumedActivity` sampler for part B. Recordings and screenshots came from the
  emulator console (it captures `FLAG_SECURE`). None are committed.

Notes for the next run:
- **The emulator was OOM-killed once** (exit 137, during an `adb reboot`) while another agent's `cargo test` ran. It
  was restarted without `-wipe-data`, and that boot counts as a crash boot (x1).
- **SystemUI's face times out after 10 s** without user activity (`activityTimeoutWM=10000`); an `am start` is no
  user activity. A swipe up for the pad has to come within those 10 s of the wake, and a console screenshot (~10 s)
  between the pad and the PIN lets the screen go off.
- **The bouncer opens with `input swipe 240 600 240 150 200`** right after SystemUI's face shows; the f3 run's
  `240 780 -> 250` works only in BFU.
- **With the kiosk off (a pause) the glance's lock task blocks every non-helper start** (`result code=101`), so
  Messages can't get over the glance; use a helper (`DeskClock` is one: `mLockTaskPackages` lists telecom,
  safetyhub, deskclock, phone and ours). Settings is hidden (`result code=-92`).
- **`am task lock stop` is refused** for a device-owner lock task ("Activity manager is in lockTaskMode").
- **Time rules use the phone's zone** (UTC here); the rule's own switch needs "Own rules" on (`section=switch
  custom_schedule_enabled=on` on `/schedules/device/1`).
- The worktree guard refuses shell lines that contain `cmd` or long compound loops: helpers went into script files.

## Findings

### R1 (Medium): the Emergency SOS screen is re-fronted over on a slow SOS start

The SOS gesture's `EmergencySosActivity` pauses the glance first; the probable-SOS mark is set only by the glance's
**stop** (`PinLockRuntime.kt:1652`, `noteProbableSos` `:1691-1698`). A pause inside the 3 s window waits
`SOS_PAUSE_GRACE_MS` = 700 ms (`RefrontPolicy.kt:318`, `pauseRefrontDelayMs` `:320-321`, scheduled at
`PinLockRuntime.kt:1635`). When the SOS screen takes longer than that to come up (a cold safetyhub: displayed at
+898 ms, +1197 ms), the check runs before the stop, finds no `sosFlow`, and re-fronts:

- As Android's face: `androidLossStep` (`RefrontPolicy.kt:192`) -> `re-front #1`, 3 of 4 tries. The SOS task goes
  `TO_BACK` and safetyhub's process dies a second later. Before 59b the face stopped on `androidGate` and never
  covered it (the d59 RC run: "the glance isn't in front - no re-front").
- In own mode: `Re-fronting the lock (#1)` at +715 ms over an SOS displayed at +559 ms, 1 of 3 tries (pre-existing).

The kid's five presses then show the glance, not the SOS countdown. The glance's own Emergency call still works. A
longer grace, or treating the SOS package's start (`LAUNCH_EMERGENCY`) rather than the stop as the mark, would close
it; the Jelly Star's cold start of the SOS app is the case to time.

### R2 (Low): kiosk off, an unlock on SystemUI's pad into a lock-task helper finishes that app

In a pause the glance starts its own lock task with the helpers (`mLockTaskPackages` = telecom, safetyhub, deskclock,
phone, ours). DeskClock started over the glance joins that lock task. After SystemUI's pad, the face's leave without
Home stops the lock task first (`lockLeave`, kiosk off: `stopLockTaskFirst = startedLockTask || lockTaskRunning`,
`LockTaskRoot.kt:87`; `go()` -> `stopLockTaskQuietly`, `PinLockActivity.kt:1064`, `:1080`). Stopping it from the root
clears the other locked tasks:

```
22:35:46.799 wm_finish_activity: [0,187186068,10,com.google.android.deskclock/com.android.deskclock.DeskClock,clear-task-all]
22:35:46.982 wm_resume_activity: [0,253214126,8,me.vibb.launcher.debug/com.kidslauncher.mdm.ui.HomeActivity]
```

So check 1's "the same with the kiosk off" holds for the Home rule but not for the app. Only helpers can be there
(any other start is refused with 101), and a VoIP call keeps lock task off, so the user's WhatsApp case is unaffected.

### R3 (Low): the switch moves the system palette to the lock wallpaper, and it stays

`setBoth` (`ui/wallpaper/WallpaperApplier.kt:182-187`) sets the night mark as `FLAG_LOCK` (id 3), then the unchanged
solid as `FLAG_SYSTEM` (id 4). SystemUI's `ThemeOverlayController` took the lock's colours (`where: 2`) and wrote
`color_source: lock_wallpaper`, `color_both: 0`; the home set brought the same colours as before (`where: 1`), and
nothing wrote the setting back. Design 59b §5 expected "the home set writes it back". The setting was still
`lock_wallpaper` after the rollback, whose wallpaper set (`lock=solid`, id 5) also changed no colours. The effect is
the palette of the pad and system UI seeded from the peach mark; check 7's "before = after" fails.

### R4 (Low): two time-rule screens after the unlock

A time rule that starts under the lit glance queues `the time-rule screen` (`LockActivity.start`,
`ui/LockActivity.kt:290`). At the unlock both `PinLockRuntime.afterUnlock` (`PinLockRuntime.kt:1937`) and the queue
(`KeyguardCover.runAfterUnlock`, posted at `PinLockRuntime.kt:705`) start it, 9 ms apart. `LockActivity` is
`standard` with `FLAG_ACTIVITY_NEW_TASK` only, so two instances stacked (`Hist #1`, `Hist #2` in task 16). Removing the
rule closed both. A Back on the first would show the second.

### R5 (Low, f3-run B6 again): one graceful reboot without the shutdown arm

g2 (`svc power reboot`) logged neither `Boot cover enabled (shutdown)` nor `lock-screen line: set`. The process at the
shutdown was g1's (pid 2686, born BFU "call path only", then the CE start); it was active ~1.5 s into the shutdown
(`Lock-up at screen-off`, `UNLOCKED -> LOCKED on ScreenOff`). The boot's HOME was the stock launcher (`Displayed
NexusLauncherActivity`), and F3R-2's locked-boot start put the cover over it, so the kid saw no stock launcher after
the PIN. g3, g4, g5 (and g1) armed, g3's from a process born BFU as well (pid 2602), so the birth isn't the cause. A capture of the whole logcat across g3's shutdown showed the arm; g2 had no such
capture, so whether `ACTION_SHUTDOWN` reached the receiver (`BootCover.kt:114`) is unknown. The restart line
("Type your PIN to start the phone") is also missing on such a boot.
