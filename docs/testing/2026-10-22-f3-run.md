# Design 59 F3 (the boot cover after the first unlock) - emulator run, 2026-10-22

Main at `70583aa9` (design 59 F3 with its code QA fixes F3C-1..7), branch `f3-run`. The run covered the emulator
checks of `docs/design/59-android-keyguard-design.md` "F3: the first unlock after a reboot" and
`docs/review/qa-f3-boot-cover-code.md`. It ran on the local headless AVD `handy36`: Android 16,
google_apis_playstore x86_64, 480x854 at 320 dpi, gesture navigation, English locale. The debug launcher of this
commit was used, with versionCode 116. A second build of the same tree with `-PversionCode=117` served as the
"update" in step 9.

## Setup

The setup was the same as `2026-10-22-d59-rc-run.md`, with these differences:
- A local server 0.37.0 from this commit, with a fresh data dir and the debug admin component. The data dir was
  deleted at the end.
- The PWA was scripted over HTTP:
  - Add the phone and make a setup code.
  - Turn Block USB debugging off, with the other restrictions at their defaults.
  - Parent PIN, Child PIN `1357`.
  - Calls managed, with the contact "Mamma" +4791234567.
- `-wipe-data`, provisioned per `docs/testing/emulator.md` §4, and enrolled through Vibb One's Settings.
- The PWA switched the Lock row to Android's lock (`/devices/1/kid-lock/keyguard`). The Child PIN was saved with
  a sealed copy, so the switch went through the PIN command (`PIN command: pin set (rev 1)`), not through our
  keypad. The apply then logged `Boot cover android mode on`, and `boot_cover_android` was in
  `/data/user_de/0/<pkg>/files`.

Logs:
- The recipe's two logs ran for the whole run, kept across reboots:
  - `logcat -v epoch -s BootCover BootCallReceiver BootHome HomeFront Application PinLock AndroidLock KidCallScreening ActivityTaskManager:I`.
    `BootHome` was added because `Boot Home started N ms ...` is logged under that tag, which the brief's list
    doesn't include.
  - The 0.2 s `topResumedActivity` sampler.
- The first sampler also read `dumpsys window` on every tick. After step 1's first boot it was cut back to the
  recipe's single `dumpsys activity activities`, to keep the guest's load down.
- Times below are seconds from the PIN's Enter (device clock), unless marked otherwise.

Notes for the next run:
- **The host was busy.** Another agent's cargo build ran next to the emulator, with a load average of 6 to 14.
  The emulator was OOM-killed twice (`qemu-system-x86 anon-rss: 9186328kB` on the first kill). Each time it was
  restarted without `-wipe-data`. qemu's RSS grows over many reboots: it is 3 GB after a fresh start.
- **BFU's lock screen turns the screen off after a few seconds.** A script that wakes the screen and swipes at once
  can miss the pad. `pin.sh` retries the wake and swipe until `pinEntry` is in the uiautomator dump.
- **The keyguard's emergency dialer on this image** is `com.google.android.apps.safetyhub/.emergencydialer.ui.DialPadActivity`,
  not AOSP's `EmergencyDialer`.
- **A placed 112 call puts the phone into emergency callback mode.** Telecom then logs
  `Skipping call filtering ... ecm=true` for about 5 minutes. Don't run screening checks right after it.
- **`am crash` is refused for the device owner.** `run-as ... kill -9` works, but it doesn't run the cover's
  uncaught-exception handler. Step 9 wrote the crash-guard record directly.

## Findings

### B1 (Medium): the locked-boot arm never fires once the BFU process is frozen

The locked-boot start waits for a screen-off with a runtime receiver: `BootCover.kt:180-201` (`waitForScreenOff`,
registered at :189). Before the PIN our process runs the call path only, and it has nothing in the foreground. Android
then caches and freezes it, and defers its context-registered broadcasts:

```
cached=true isFrozen=true
38ff81a 2306:me.vibb.launcher.debug/u0a217 not runnable because INFINITE_DEFER
      DEFERRED URGENT for registered d47700a
```

So `SCREEN_OFF` reaches `atLockedBoot` only after something thaws the process. In practice that is the PIN, and then
`unlocked=true`, so the result is NONE.

What happened:
- After `adb reboot` (fz1: 60 s with the screen on, then 12 s off) and after a crash reboot (x1: about 55 s), there
  was no `Boot cover started`, and the stock launcher showed after the PIN.
- It worked only in b2 and e1, where the screen-off came within about 5-10 s of `LOCKED_BOOT_COMPLETED`, and in c2,
  where a call had just thawed the process.

On a real phone, a crash or hard-reset boot usually ends with the screen on, and the screen times out later. So
F3's arm for non-graceful boots mostly won't fire. Graceful boots are unaffected: there the shutdown arm makes the
cover the boot's HOME.

A smaller related race: `interactive` is read fresh when the deferred broadcast is handled (`BootCover.kt:177`,
`BootCoverPlan.kt:224`). In b1 the BFU `SCREEN_OFF` came 4 s after `KEYCODE_SLEEP`, after the wake, so it was read as
"screen on". It then waited again silently (`:181`).

Possible directions (not changed here):
- Keep the process out of the cached state while it waits, for example with a short direct-boot-aware foreground
  service.
- Or treat the arrival of `SCREEN_OFF` as the screen-off itself, instead of re-reading `isInteractive`. This needs
  the delivery to happen in the first place, so it fixes only the race.

### B2 (Medium, cause not found): twice, the boot's HOME went to the system chooser instead of the cover

In two consecutive graceful boots (co1, r1), `startHomeOnAllDisplays` started
`android/com.android.internal.app.ResolverActivity` ("Select a Home app": Pixel Launcher, Vibb One (debug),
Vibb One (debug)) instead of `BootCoverActivity`:

```
SystemServerTiming: startHomeOnAllDisplays
ActivityStartInterceptor: Starting home with component specified, uid=0
START u0 {act=android.intent.action.MAIN cat=[android.intent.category.HOME] ... cmp=android/com.android.internal.app.ResolverActivity
```

- The cover was enabled (`Boot cover enabled (shutdown)`), and DPM still listed both HOME persistent preferred
  activities as resolved.
- After the PIN the chooser was the top, with the kiosk off:
  - co1: from +0.7 s until the screen timed out at +62 s, because the call kept our Home back.
  - r1: from +0.3 s to +11.8 s.
- Tapping "Pixel Launcher" there would open the stock launcher. Hidden apps stay hidden there, but it is a way out
  of our Home until the next Home start.
- At those moments the unlocked chooser listed three HOMEs. That is two HOME PPAs resolvable at once (16b QA #8),
  because the cover was enabled while unlocked.

The other 9 graceful boots of the run started the cover. In BFU, `cmd package resolve-activity` gave
`BootCoverActivity` both before and after:
- Every boot before and after these two.
- A deliberate repeat of co1's preceding state: the cover left enabled under a call for 30 s with applies running
  (h1 -> h2b).

Both failing boots followed a boot in which the cover had stayed enabled while unlocked and applies ran (s5d -> co1,
co1 -> r1). But the deliberate repeat didn't reproduce it, and the host was heavily loaded (boot_completed in 36-48 s
in those boots). Without root, `package-restrictions.xml` couldn't be read.

Worth a device check: repeat graceful reboots after a call held through the first unlock, and watch for
`ResolverActivity` in the boot's HOME start.

### B3 (Low): the boot's Home pass waits behind the main thread's queue, not just `initRest`

`PinLockRuntime.kt:543` posts `BootCover.init` + `BootHome` with `handler.post`, so it runs after every message
queued while `initUnlocked` ran (`Application.kt:256-284`). In g2, 12.2 s passed between `Unlocked setup took 8917 ms`
and `Boot cover disabled (main process after unlock)`, followed by `Choreographer: Skipped 724 frames`. In that window
the main thread ran the work that the system queued during the setup:
- `BadgeListenerService.recount`'s verification
- `KidVpnService`'s create/start (`DnsFilterEngine: Loaded ...`, `KidVpnService: Filter up and always-on`)
- `TimeRuleAlarm`

So `Unlocked setup took` covers only part of the gap. The design's "Not shaved" reasoning considered only the work
inside `initRest`. A `postAtFrontOfQueue` for the boot pass may be worth measuring on the release build, since the
cover hides the wait.

A related effect on a slow start (h2b): the main thread was busy long enough that `KidVpnService` hit a service
ANR, and the system killed the process:

```
am_anr: [0,2617,me.vibb.launcher.debug,...,executing service me.vibb.launcher.debug/com.kidslauncher.mdm.server.KidVpnService, waited 20076ms]
am_kill: [0,2617,me.vibb.launcher.debug,0,bg anr,...]
```

The restarted process decided `LOCKED` (`androidBoot=false`), so the kid had to type the PIN a second time. The cover
covered the gap, so no stock launcher showed.

### B4 (Low/Nit): the cover's 500 ms `START_HOME` nudge fires in the normal path

In k2 and r2 the main thread took 960 ms and 819 ms between the take-over (`Boot cover disabled (main process after
unlock)`) and `HomeFront: Home brought to the front`. The cover ran its nudge in that window:

```
Boot cover starts Home: taken over 751 ms ago, still in front
```

The start is a harmless double start (singleTask), as the design expects. But the nudge is meant only for a process
death, and `COVER_HOME_NUDGE_MS` (500) is shorter than the normal pass on this build. If the extra start ever matters,
a longer nudge, or one counted from the cover's last resumed tick, would keep it to the death case.

### B5 (Low): the cover's 30 s hand-over starts Home during a live call

`BootCoverActivity.kt:184-193` (`HAND_OVER` -> `startHome()`, :204) has no call check. `BootCover.init` and
`BootHome` keep Home back while a call is live, but the cover's own fallback doesn't. In s5d and h1, with a call held
through the PIN:
- The cover stayed (`stays under the call`).
- After 30 s: `Boot cover disabled: no take-over 30146 ms after the unlock` and its typed HOME start brought Home
  while the call was still up.
- At the call's end: `Home already up`.

In those runs the call screen was already behind the cover, so nothing was hidden. That happened because the kid
(the script) pressed Home to reach the pad during the call. When the call screen is in front of the cover, the same
start would move the home task over it. It isn't observed here, but the code reads that way. Checking
`BootHome.callLive`-style facts isn't possible in the `:bootcover` process. Keeping `HAND_OVER` from starting Home
while the cover is stopped (`!visible`) would avoid it.

### B6 (Low, unexplained, under heavy load): one graceful reboot without the shutdown arm

r3 (`svc power reboot`) logged `lock-screen line: set`, but no `Boot cover enabled (shutdown)`:
- The boot fell back to the locked-boot wait, and the stock launcher showed from +0.6 s to +12.1 s.
- The process at the shutdown had been restarted after B3's ANR in the boot before.
- The previous boot's full logcat was gone, so it couldn't be told whether `ACTION_SHUTDOWN` reached that process.
- Not seen in the run's other graceful reboots, which all logged the arm, apart from t1, whose guard was tripped on
  purpose.

### Notes

- **N1.** After `adb reboot` or a crash, SystemUI shows its own "Unlock for all features and data", not "Type your
  PIN to start the phone". This is by design (§3.2: the line is set at `ACTION_SHUTDOWN`), but the kid then has no
  hint after a crash.
- **N2.** When AMS finishes the cover after its own hand-over (g1), the cover's `onStop` sees `isFinishing`
  (`BootCoverActivity.kt:115`). So no `Boot cover leaves` line is logged, and the recipe's gap number is missing for
  that boot.
- **N3 (pre-existing).** A call during the first unlocked setup reaches Telecom slowly (com.android.phone was busy
  too). Once ringing, it has no call screen until our main thread is free. In s5b the call was RINGING from +24.6 s,
  but `InCallActivity` showed only at +40 s, after the caller had hung up. Before the PIN, calls are screened
  quickly (the call-path-only process).
- **N4.** Home is on top well before its first frame: for example, on top at +21.7 s and drawn at +27.4 s (g2). In
  the boots where the stock launcher hands over by itself (b2, x1, k1), `NexusLauncherActivity` started our
  `HomeActivity` (uid 10182) before our own Home start. The cover stays in either case.
