# Launcher rc.2 candidate - targeted emulator re-check, 2026-10-22

Main at `126e7e9d` (the rc.2 candidate plus design 59b fix round 2 for the rc.2 run's R1-R6), branch `rc2-recheck`.
The re-check covered the fix round's items only: R1 (59b §10 check 4b), the SOS mark at "Lås opp", R4, R3 (check
7, as colours), the R2 reproduction, and a short sanity pass. It ran on the local headless AVD `handy36`, as in
`2026-10-22-rc2-run.md` (debug launcher, versionCode 116).

## Setup

The setup was the same as `2026-10-22-rc2-run.md`:
- A local server 0.40.0 from this commit, with a fresh data dir and the debug admin component. The data dir and the
  cargo target dir were deleted at the end.
- `-wipe-data`, provisioned per `docs/testing/emulator.md` §4, and enrolled through Vibb One's Settings.
- The PWA was scripted over HTTP. It set the restrictions at their defaults with Block USB debugging off, the Parent
  PIN, Child PIN `1357`, calls managed with "Mamma", and Messages and Chrome allowed. An SMS "Hemmelig melding
  SECRET-42" came from `adb emu sms send`.
- The PWA's Lock row switched to Android's lock. The Child PIN had a sealed copy, so the switch went through the PIN
  command (`PIN command: pin set (rev 1, secure now=true)`), and Android's PIN is `1357`.
- The same logcat tags as the rc.2 run, our package's events, and the 0.2 s top sampler for the reboot.

Notes for the next run:
- **The setup script's hardening step posts nothing.** `pwa_setup.py`'s form regex misses
  `action=".../hardening#restrictions"`, so it saves every restriction **off** (safe boot stays on). Here the
  defaults were posted again by hand (all on but `disallow_debugging_features`) and checked on the page. Check
  `/devices/1/advanced` after the script.
- Device epoch is ~0.9 s behind the host's here; a host-time filter on the log needs ~2 s of slack.
- On this AVD the SOS screen is "Touch & hold for 3 seconds to start" (no auto countdown). Back doesn't close it, and
  its Cancel is at (273, 733).
- The time-rule screen is easiest to see with a rule that starts while the glance is kept lit (`keepon.sh`).
  Deleting a rule needs `scope=1` in the form.

The ask itself never logged the mark: the pad doesn't pause the glance, and `androidLossOurs` would cover it if it
did.

**N1 (Low/Note, new with fix round 2):** the face's screen-on often has a 2-5 ms pause/resume pair, `resumed` ->
`paused` -> `resumed`, 5-35 ms after `screen-on`. `sosMarkAtPause` now turns that pause into `probably Emergency SOS`.
This happened at 46 of 59 android-mode screen-ons here, and in 8 of 10 in a power-press run. The resume right after it
clears the mark (`sosFlowUntilElapsed = 0`) and the pending check, so nothing yields. In this run no `exempt screen: sos`
came without a real SOS (6 yields, 6 SOS tries). The cost is a misleading log line at most wakes, which makes the
mark useless as evidence of a real SOS in field logs. A guard such as "a pause followed by a resume within a few ms
is no SOS", or logging the mark only when the 700 ms check runs, would quiet it.

The lost tap at +1 s happened once, right after four SOS Cancel cycles. Later taps at +0.7-1.0 s all worked, so it
wasn't analysed further.

**N2 (Low, look; not R3):** after the reboot in android mode, SystemUI never applied its wallpaper-seeded overlays.
`com.android.systemui:accent/neutral/dynamic` stayed disabled, with `mNeedsOverlayCreation=true` for 5+ minutes. The
boot already wrote Android's default palette (`Writing boot animation colors 4: ffd9e2ff`, 00:27:51), before the
rollback at 00:28:56. Three wallpaper sets and a screen-off didn't recreate the overlays, though the log says
`Wallpaper changed, allowing color events again`. The seed was unchanged, so SystemUI probably saw no colour change
to act on. A reboot in own mode brought them back (`mNeedsOverlayCreation=false`, the original colours). So after an
android-mode boot (BFU, the boot cover as HOME, Pixel's `ThemeHomeDelay`) the pad and system UI use Android's default
blue-grey seed instead of the night ground's. The cause isn't known: whether the cover as HOME delays the theme, or
any secure-PIN boot on this image does, wasn't separated. It is subtle in colour, and a check for the Jelly Star.

## 6. Sanity

- `power20.sh 1.2` (20 presses = 10 off/on cycles, console recording), three runs: from the glance, from a lit
  Messages sign-in screen, and from the Messages list with the SECRET-42 conversation. Each run gave `relock lines:
  0`, `lock-ups: 10`, `screen-on lines: 10`, and 20 `screen_toggled`. No `exempt` or `re-front` line came.
- First frames (20 fps): the glance, often with SystemUI's large clock blended in for one frame (the §6 no-AOD
  candidate; more often here than the rc.2 run's 2 of 10), or the night ground with the mark and SystemUI's clock.
- **N3 (emulator artifact, not a finding):** in 3-5 of 10 wakes per run the first recorded frame was a **stale**
  picture. In run 1 it was DeskClock with its status bar at 12:21, recorded at 12:22, after DeskClock's task had
  been cleared and wasn't in Recents. In runs 2-3 it was a blank white screen with a 12:24 status bar, still shown at
  12:26 after the Messages list had been on screen. It was never the content shown last before the lock (the
  SECRET-42 list never appeared), it has rounded display corners, and it didn't change between wakes. So it reads as
  a stale host framebuffer in the emulator's capture at display-on, not a window of the phone. It does mean check 10
  can't be judged from these recordings when the stale frame happens to look like the night ground (Home's solid is
  the same colour). Check 10 needs the Jelly Star.
- `svc power reboot` (android mode): the shutdown arm (`Boot cover enabled (shutdown)`, `lock-screen line: set`), then
  `Boot cover started at the locked boot (android mode, interactive true)`. At the PIN: cover +0.3 s, Home +12.9 s
  (drawn +22.7 s), `Boot cover leaves` 19189 ms after the unlock. **0** `NexusLauncherActivity`/`ResolverActivity`
  samples. This boot was slow (`Unlocked setup took 3238 ms`): Home came 12.7 s after the unlock reached the process,
  so the cover's own nudge fired first: `Boot cover starts Home: taken over 3328 ms ago, still in front`. This is the
  designed fallback, not the B4 normal path. The kid still saw only the cover between the PIN and Home.
- Our package's events: no `am_anr`, `am_crash` or kill.
