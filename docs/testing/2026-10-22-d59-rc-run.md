# Design 59 (Android's lock screen) - RC run on the emulator, 2026-10-22

Main at `f4972ced` (design 59 steps 1-4 with their code QA fixes, the new PWA look), branch `d59-rc-run`. The run
covered `docs/design/59-android-keyguard-design.md` §8, plus the device checks that the steps' "as built" sections

## Setup

The setup was the same as `2026-10-22-hybrid-prototype-run.md`:
- A local server 0.37.0 from this commit, with a fresh data dir and the debug admin component. The data dir was
  deleted at the end.
- The PWA was scripted over HTTP:
  - Add the phone and make a setup code.
  - Turn Block USB debugging off. The other restrictions stayed at their defaults, with safe boot on through the
    Child PIN.
  - Parent PIN, Child PIN `1357`.
  - Calls managed, with the contact "Mamma" +4791234567.
  - Messages and Chrome allowed.
- The phone was provisioned per `docs/testing/emulator.md` §4, using the debug launcher of this commit, and enrolled
  through Vibb One's Settings: the server URL, then "Enroll with code".
- A Messages chat "Hemmelig melding SECRET-42" came from `adb emu sms send`.

The lock was switched to Android's lock only from the PWA: the Lock row on Lock Screen & PINs, which posts to
`/devices/1/kid-lock/keyguard`.

Logs used the tags `AndroidLock PinLock PinLockActivity KeyguardCover LockTaskChrome CameraLock MdmDeviceAdminReceiver
WindowRelock MdmSyncWorker KidCallScreening`, kept across reboots. Screenshots came from the emulator console, which
captures the `FLAG_SECURE` glance. They are not committed.

Notes for the next run:
- The first `dpm set-device-owner` right after a `-wipe-data` boot failed with "already some accounts on the
  device" while `dumpsys account` showed 0. This was a race with DPM's `hasIncompatibleAccountsTask`. A retry a
  minute later worked.
- `am crash` is refused for the device owner ("Can not crash protected package"). Kill the process with
  `adb shell run-as me.vibb.launcher.debug kill -9 <pid>` (debug build only).
- `am start` of our Home while locked doesn't bring up SystemUI's own face, because lock task brings our task
  forward. Use `com.google.android.deskclock/com.android.deskclock.DeskClock`, as the prototype run did.
- For a "legacy" Child PIN (saved before 0.37, no sealed copy), I set `kid_pin_sealed` to NULL in the test server's
  SQLite. Without that, the switch queues `set_kid_pin` at once and the keypad migration never runs.

## Findings

### F1 (Low, pre-existing, own lock only): a stale `BlockedAppActivity` recents task keeps lock task LOCKED in a pause

How it happened:
1. APP_SWITCH on today's lock (kiosk on) started the recents provider. Lock task turned that start into
   `android/com.android.internal.app.BlockedAppActivity`, in `Task #4 type=recents A=1000:android`, which joined
   `mLockTaskModeTasks`.
2. The parent pause then applied (`PIN lock helpers (kiosk off)`).

After that:
- `LockTaskController` showed `mLockTaskModeState=LOCKED`, `mLockTaskModeTasks= #0 Task{... #4 type=recents
  A=1000:android}` and `mLockTaskPackages u0:[]`.
- The dialog "App is not available - Pixel Launcher is not available right now" was in front.
- `am start` of Messages failed with `Activity not started, unknown error code 101`.
- One Back ended it (`mLockTaskModeState=NONE`).

`launcher/CLAUDE.md` (the 16d residual: "a Recents start while LOCKED leaves a stale BlockedAppActivity task")
describes the task, but not that it keeps a pause in LOCKED. A child in a pause would see the dialog and be unable
to open apps until Back.

On Android's lock this doesn't arise, because the locked keyguard refuses the key before any start.

### F2 (Low): a pause's relock cancels an open PIN pad

"Unlock" was tapped as `end-windows` applied:
- `16:23:06.209 Lås opp: requestDismissKeyguard`
- apply at `:06.552` and `:07.232`
- `16:23:07.509 Android's PIN pad: cancelled`, then the glance.

The answer came, so this is not the prototype's dead ask (B2). The child has to tap "Unlock" again.

### F3 (Low): the first unlock after a reboot shows the stock launcher for about 10 s

After the PIN on SystemUI's pad:
- The top was `com.google.android.apps.nexuslauncher/.NexusLauncherActivity` from 1 to 10 s.
- Our Home came at 11 s: `HomeFront: Home brought to the front: boot 4` at 16:42:29.6. The decision
  `Process start: UNLOCKED` was logged at 16:42:17.0.

### F4 (Nit, design text): removing the Child PIN in android mode leaves the keyguard enabled

§8 step 15 expects `get-disabled -> true`. The build writes UNTOUCHED (`keyguard: mode=UNTOUCHED features=0x2
maxTimeToLock=0 disabled=false`), because `wantKeyguardDisabled` (`PinLockState.kt:257-258`) needs a Child PIN, and
`keyguardMode` (`KeyguardCoverPlan.kt:57`) returns UNTOUCHED without one. This is what own mode has always done
without a Child PIN.

The result is Android's swipe-only lock screen, with no credential. The phone opens with a swipe, as the step
intends. Either the design line or the expectation should change. No security effect.

### F5 (Nit, PWA): "Set" and "Send the Child PIN again" together for a moment

Right after the phone answers `pin set`, and before its next status report, the card shows
"Child PIN to the phone · Set · 18:32" together with the "Send the Child PIN again" button (16:32:40). About 2 s
later the report arrives and the button goes. The button's rule reads the report, which still names the older rev.
