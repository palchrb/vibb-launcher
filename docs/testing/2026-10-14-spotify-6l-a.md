Part B (the real SDK and a Premium account) was not attempted. No product code was changed.

**Result: 24 pass, 5 fail, 16 blocked (45 checks: A1 25, A2 20).** Two bugs in the music app stop every Spotify play
within about a second:
- **F1, Critical: a crash.** Every play, pause, seek or stop that reaches the player through the media session

  and the renderer pauses.

Every check that needs audio to keep playing is blocked behind these two bugs. The emulator's memory also cut the run
short (see Setup).

## Findings

### F1 - Critical: every play, pause, seek or stop through the media session crashes the music app (StackOverflowError)

- **Where:** `music/app/src/main/java/me/vibb/music/spotify/SpotifyRenderer.kt` lines 1750-1757, the inner class
  `SpotifyPlayer(looper) : SimpleBasePlayer(looper)`:

  ```kotlin
  override fun handleSetPlayWhenReady(playWhenReady: Boolean): ListenableFuture<*> =
      handling { if (playWhenReady) play() else pause() }
  override fun handleSeek(mediaItemIndex: Int, positionMs: Long, seekCommand: Int): ListenableFuture<*> = handling {
      if (mediaItemIndex == C.INDEX_UNSET || mediaItemIndex == index) seekTo(positionMs.coerceAtLeast(0)) else seekTo(mediaItemIndex, 0)
  }
  override fun handleStop(): ListenableFuture<*> = handling { pause() }
  ```

- **Why it recurses:** inside an inner class Kotlin resolves an unqualified call to the receiver's own members first.
  `play()`, `pause()` and `seekTo(..)` are `BasePlayer`'s (`SimpleBasePlayer`'s), not `SpotifyRenderer`'s
  `override fun play()`/`pause()`/`seekTo()` (lines 466, 495, 502, 523). So `BasePlayer.play()` calls
  `setPlayWhenReady(true)`, which calls `handleSetPlayWhenReady` again, and so on until the stack overflows.
  `SonosRenderer`'s player calls `controller.playPause()`, so it doesn't have this problem.
- **Repro** (any one of these):
  1. Open the player of a Spotify entry and tap the big play/pause button.
  2. Drag or tap the seek bar.
  3. During a cold start (`--slow-ready 15`), tap the button while it shows pause.
  4. `adb shell am force-stop me.vibb.music.debug; adb shell input keyevent MEDIA_PLAY`.

  Not affected: the now-playing bar's play button and a cover tap (they don't go through the session player), and
  next/previous (`KidPlayer` sends them to `skipNext`/`skipPrevious`).
- **logcat** (`logs/a1-seek-logcat.txt`, `logcat-a2.txt`, `a1-headset-logcat.txt`, `a2-slow2-logcat.txt`):

  ```
  E/AndroidRuntime: FATAL EXCEPTION: main
  E/AndroidRuntime: java.lang.StackOverflowError: stack size 8188KB
  E/AndroidRuntime:   at me.vibb.music.spotify.SpotifyRenderer.handling(SpotifyRenderer.kt:1705)
  E/AndroidRuntime:   at me.vibb.music.spotify.SpotifyRenderer$SpotifyPlayer.handleSetPlayWhenReady(SpotifyRenderer.kt:1751)
  E/AndroidRuntime:   at androidx.media3.common.SimpleBasePlayer.setPlayWhenReady(SimpleBasePlayer.java:2243)
  E/AndroidRuntime:   at androidx.media3.common.BasePlayer.play(BasePlayer.java:113)
  E/AndroidRuntime:   at me.vibb.music.spotify.SpotifyRenderer$SpotifyPlayer.handleSetPlayWhenReady$lambda$5(SpotifyRenderer.kt:1751)
  ... (repeats)
  ```

  The seek variant goes `SpotifyPlayer.handleSeek(SpotifyRenderer.kt:1753)` → `SimpleBasePlayer.seekTo(SimpleBasePlayer.java:2529)` → ….
- **Fix:** qualify the calls: `this@SpotifyRenderer.play()`, `this@SpotifyRenderer.pause()`,
  `this@SpotifyRenderer.seekTo(...)`.
- **Tests to add:**
  - A JVM/Robolectric test that drives `renderer.player` through the `Player` API (`play()`, `pause()`,
    `seekTo(ms)`, `seekTo(i, 0)`, `stop()`) and checks the renderer's intent.
  - A `GuardsTest`-style source scan that forbids unqualified `play()`/`pause()`/`seekTo(` inside `SpotifyPlayer`.

### F2 - High: the WebView takes audio focus from our own renderer, so every Spotify play pauses within a second

- **Where:** `SpotifyRenderer.onFocus` (line ~1445: `FocusChange.LOSS -> focusHeld = false; if (pwr)
  pause(PauseCause.FAULT)`) together with `acquireFocus()`/`AndroidSpotifyPorts.requestFocus`.
- **This answers design 26c §5.6's device check** ("whether the WebView requests focus itself for its media"):
  - **It does.** The headless WebView's Chromium media session (`org.chromium.content.browser.AudioFocusDelegate`)
    requests `AUDIOFOCUS_GAIN` (USAGE_MEDIA, CONTENT_TYPE_UNKNOWN) when the stub's audio element starts.
  - Android then hands our own `AudioManager` listener `onAudioFocusChange(-1)`, and the renderer pauses as for any
    other app.
  - The current code takes the "renderer keeps its request" branch (step 5a's deviation 11). That branch is wrong
    on this WebView (133, Android 16). The real SDK plays through the same media element and Chromium session, so the
    Jelly Star will very likely behave the same - part B's check.
- **Repro:** any Spotify cover tap (A1 or A2, list or context mode). It happened on every one of about 20 starts.
- **logcat** (`logs/logcat-a2.txt`):

  ```
  08:30:34.405 I/MediaFocusControl: requestAudioFocus() from uid/pid 10217/3952 AA=USAGE_MEDIA/CONTENT_TYPE_MUSIC clientId=…me.vibb.music.spotify.AndroidSpotifyPorts$$ExternalSyntheticLambda0@add6f19 … req=1 flags=0x2
  08:30:45.411 I/MediaFocusControl: requestAudioFocus() from uid/pid 10217/3952 AA=USAGE_MEDIA/CONTENT_TYPE_UNKNOWN clientId=…org.chromium.content.browser.AudioFocusDelegate@b5c9407 … req=1 flags=0x0
  08:30:45.425 I/AudioManager: dispatching onAudioFocusChange(-1) to …AndroidSpotifyPorts$$ExternalSyntheticLambda0@add6f19
  08:30:45.425 D/VibbSpotify: spotify: audio focus LOSS
  08:30:46.013 D/VibbSpotify: spotify: wake and Wi-Fi locks released
  ```

  `dumpsys audio` afterwards shows the Chromium `AudioFocusDelegate` (same uid) on top of the focus stack.
- **Suggested fix: §5.6's other branch, which the evidence supports.**
  - The renderer **doesn't request focus itself** while the Spotify renderer is attached. The WebView's own session
    holds it: Chromium requests focus on play, pauses its media on a permanent loss, and pauses then resumes on a
    transient one.
  - Map what the page reports instead: a `paused` state while we want play is an external pause, i.e. `Paused(FAULT)`
    or `Interrupted`, the same mapping `SpotifyTracker` already does for states.
  - The duck (`vibb.volume(0.3)`) can't come from our listener any more. Either accept Chromium's own duck handling
    or leave ducking out.

  Weaker alternatives:
  - Keep our request but ignore a LOSS while our own page is starting or playing. There is no public API to tell
    that the new focus owner is our own uid, so this would be a heuristic.
  - `setMediaPlaybackRequiresUserGesture(false)` (already needed for autoplay) doesn't change Chromium's focus
    behaviour, and WebView has no public switch to turn its media session's focus off. So this has to be handled in
    our code.

  Re-check calls (`CALL_HOLD` still pauses through the launcher) and the bedtime pause after the change.

### F3 - Medium: offline (and on the network gate), next and previous move the item

- **Expected:** emulator.md §6l A2 "No Wi-Fi, offline": "next and previous say the same and don't move".
- **Observed:** with airplane mode on and "Trenger internett" showing, next moved from track 2 "Månesang" to track 3
  "Uten artist". Each step logged `spotify: no start - NEEDS_INTERNET` / `stopped - UNREACHABLE`

### F4 - Low (test harness): the fake's auto-consent can't be followed by a browser

- The server's `/music/spotify` CSP is `form-action 'self' http://127.0.0.1:8731`. Chromium applies `form-action` to
  the whole redirect chain of the login form's POST: 303 to the fake's `/authorize`, then the fake's immediate 302 to
  `http://127.0.0.1:43117/callback`. It refuses the last hop: console
  `Refused to send form data to 'http://127.0.0.1:3205/music/spotify/login' because it violates … "form-action 'self'
  http://127.0.0.1:8731"`.
- So §6l A1's "the browser lands on …/callback?code=FAKE-CODE-1 ("can't connect")" can't happen in Chromium.
- The real Spotify isn't affected: it shows a consent page (`show_dialog=true`), and the callback navigation starts
  from Spotify's document.
- Workaround used here: follow the 303 by hand and read the callback address from the fake's `Location` header.
- **Fix:** let `scripts/fake-spotify.py`'s `/authorize` answer a tiny page with a link or button to the callback
  (auto-clicked is fine) instead of a 302, or note it in §6l.
