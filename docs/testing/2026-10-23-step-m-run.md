Branch `d59d-step-m` (from `main` 4889adf7). The question: with step M (59d §8.12) does a reboot that the shutdown
did not arm boot to the cover and Android's pad on the image where it used to hang (six-inch run F1), and is our Home
still the unlocked HOME (F6)? Screenshots in `screens/step-m/` (540 px wide).

## F1 reproduced on `main`


The clear and the five adds took ~475 ms on the main thread. Before a2 the file's order was HomeActivity, cover - and
a2, b1 and c1 needed no re-seat. The order is arbitrary per boot, as read in AOSP (`Settings
.writePersistentPreferredActivitiesLPr` writes `filterSet()`, an `ArraySet` of identity-hashed objects).

**Bug found and fixed in the run (a1).** The take-over's stamp didn't land: `AtomicFile: Failed to rename
.../boot_cover_taken.new to .../boot_cover_taken` - the cover, polling the stamp every 250 ms through
`AtomicFile.readFully`, deleted the main process's in-flight `.new` (`openRead` deletes a `.new` next to an existing
base). The cover saw no take-over, was stopped under Home but never finished (`state=STOPPED`), and would have run its
30 s hand-over on its next resume. Fixed in `BootCoverGuard`: the stamp is a plain temp file renamed over it and read
from the stamp itself; the record (`read`) reads the base file too, never `readFully` (`BootCoverManifestTest` pins
both). a2, b1 and c1 ran the fixed build.

## Other observations

- **Duplicate PPAs at every boot** (not ours to fix; noted for step M's docs): after a2, b1 and c1 the file held 20
  PPA entries, four of each - Android 15's policy engine re-adds every PPA at every boot
  (`DevicePolicyEngine.reapplyAllPoliciesOnBootLocked`; PPAs have no skip-if-unchanged flag) and PMS appends without a
  dedupe. Before step M the F6 purge cleared them (it removes every entry with the filter); now the re-seat does (five entries
  before a2, after a1's re-seat). Harmless for resolution (a duplicate names the same component).
- **The automatic asks run out early**: at every boot the cover was relaunched twice within ~10 s (`finishDrawing of
  relaunch`, after `ApplicationInfo updating ... assets added: .../com.android.systemui-neutral-*.frro` - the theme
  overlays coming in), and each new instance's resume asked: `automatic 1 of 3`, `2 of 3`, `3 of 3` within 12 s, so
  after one Back only a tap asks. Step F's rule, not step M's; the pad itself stayed up.
- `input text` didn't reach the pad's PIN field on b1's "Enter PIN" keypad; tapping the keys did (a1 had the text
  field variant).
