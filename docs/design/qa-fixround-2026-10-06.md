# QA: fix round 2026-10-06 (code and security)

Reviewed 2026-10-06: `86a5988c..f2e37b0f` (`handy`, master) against docs/testing/2026-10-06-emulator-run.md "Fix round 2026-10-06". S `cargo test` 178/178 pass; L `testDebugUnitTest` 407/407 pass. H = fix before the device run, M = fix in this round, L = fix or record.

## Findings
1. **H, calls/emergency: the post-hang-up reconcile can drop a call that is being placed, including a 112 redial.** `OngoingCalls.callUiShouldClear` (L `calls/OngoingCalls.kt:20-21`) clears every call when `telecomInCall == false`, even if we hold a live one. The 2 s timer after any DISCONNECTED (`KidInCallService.kt:34`) asks `TelecomManager.isInCall()`. That call counts only `CallsManager.ONGOING_CALL_STATES`, which leave out NEW and CONNECTING (AOSP Telecom `CallsManager.java:346-349`, `hasOngoingCalls`). So: a call ends, the kid redials within 2 s, and the new call is still CONNECTING when the timer fires. Emergency calls can stay CONNECTING for seconds (radio on, domain selection). Our list and notification are then cleared, `InCallActivity` finishes, Hang up can't reach the call, and `hasLiveCall` is false for the PIN lock. The call stays connected with no UI of ours. Telecom does show emergency calls in our UI: `InCallController.bindToServices` wraps the default dialer in `EmergencyInCallServiceConnection`, and the system dialer is only the fallback when we fail. So the KDoc at `KidInCallService.kt:18` ("always shown by the preloaded dialer") is wrong. `reconcileAtStart` (`OngoingCalls.kt:70`, `inCall ?: false`) has the same weakness. **Fix:** in the timer and in `reconcileAtStart`, drop only DISCONNECTED calls. Trust `isInCall == false` only from `onUnbind`/`onDestroy`, or only when none of our calls is NEW/CONNECTING/DISCONNECTING. Add `callUiShouldClear(listOf(STATE_CONNECTING), false) == false` to `CallUiReconcileTest`, which pins the opposite at the moment. Fix the KDoc.
2. **M, push: FIDs in `message.token` work today but only for now.** I checked the implementer's claim and it holds, so no revert is needed. Firebase: "To send to a single, specific device, you can target either its Firebase Installation ID (FID) or its registration token… During the migration period, the `token` field also accepts FIDs. However, since the `token` field is deprecated and will be removed, we recommend using the `fid` field" (firebase.google.com/docs/cloud-messaging/send/admin-sdk). The Android client page marks registration tokens deprecated and says to target the FID from `onRegistered()` (…/cloud-messaging/android/client). The SDK 25.1.3 API matches L: `register`, `unregister`, `onRegistered` and the `firebase_messaging_installation_id_enabled` meta-data. S still sends `"token": token` (`server/src/fcm.rs:472`). Once `token` stops taking FIDs, every send would fail, the token would be cleared and renewed, and the cycle would repeat. Push would then be broken while SSE carries on. Upgraded phones also keep a legacy token, and `onNewToken` is no longer overridden (`KidFcmService.kt:65`), so a rotated legacy token is only replaced after FCM rejects it. **Fix:** S sends FIDs as `message.fid` and legacy tokens as `message.token`. An FID is 22 chars of base64url with no `:`; a token contains `:`. Better, L reports which kind it holds. L does a one-time RENEW to an FID when the stored token isn't FID-shaped, so `token` can be dropped later.
3. **L, auto-lock outside management.** `screenTimeoutAction(policy != null, …)` (`server/AppEnforcer.kt:336`) enforces the timeout and `DISALLOW_CONFIG_SCREEN_TIMEOUT` on a policy that isn't managed (no allowlist, calls unmanaged). Hardening is lifted in that case (`hardeningManaged`). `Keep` on `policy == null` leaves the restriction and the observer on after an unenrol. The KDoc of `Keep` (`ScreenTimeout.kt:25`) says the fallback plan keeps the timeout, but a pre-upgrade `LastEnforcedPlan` (no `screenTimeoutSeconds`) releases it. **Fix:** Release when `!hardeningManaged(...)` or when the policy is null and the phone was managed before. Correct the KDoc.
4. **L, PIN lock budget is tested only with a 24 dp gesture bar.** `PinLockLayoutTest.kt:55`. I recomputed the budget from the XML: keys are 54 dp at 48+24 dp bars but 48.1 dp at 48+48 dp (3-button navigation), right at the minimum. Below that, the compact steps take over. If step 3 still doesn't fit, `coerceAtLeast(MIN_DP)` makes the centred keypad overflow and clips its top and bottom rows (Emergency call and Parent code stay visible). **Fix:** add a 48+48 dp case. Once the clock is gone, shrink keys below 48 dp rather than clip.
5. **L, PWA scroll restore: safe, but the test only checks that the script is there.** XSS: none. The script writes no DOM; it reads same-origin `sessionStorage` and passes a number to `scrollTo`. There is no CSP today, so the inline script runs, but a future strict CSP would need a hash or `'unsafe-inline'` for it (`templates/partials/head.html:15`). Redirects work: the path is compared with the page that submitted, so POST→redirect→same page restores, a redirect elsewhere or a `#fragment` doesn't, and the key is consumed on the next load. GET forms also restore (harmless). `pages_restore_scroll_after_auto_save` (`server/src/tests/device_api.rs:697`) checks string presence only. **Fix:** move the script to `/static/scroll-restore.js` like `register-sw.js`. A JS test (path match, 20 s expiry, hash skip, `form.submit()` hook) would make it meaningful.

## Checked, OK
- **One call at a time:** emergency is exempt in all three gates: `placeCall`, redirection and the `onCallAdded` backstop. A call being placed (NEW/CONNECTING/SELECT_PHONE_ACCOUNT) doesn't count. Incoming calls aren't affected. The 112 tile still falls back to `EmergencyDialer`. `isEmergencyOutgoing` can't throw.
- **Silent call channel:** LOW importance only while `InCallActivity` is started. A ringing call that leaves the screen with the display on gets a fresh heads-up. The notification id clash is fixed (1005).
- **Provisioning activities:** exported, `BIND_DEVICE_ADMIN` is signature-level (system only). They only call `setResult`, change no state and can't be used against a provisioned phone.
- **Screen timeout:** S accepts only 15/30/60/120/300/600. L clamps to 15-600 s and turns ≤0 into 60, never "never". A malformed type fails the policy decode, so the cached policy stays. DPMS allowlists `SCREEN_OFF_TIMEOUT` and writes with a clean identity, and `UserRestrictionsUtils` lets SYSTEM_UID past `DISALLOW_CONFIG_SCREEN_TIMEOUT`, so the kid can't change it and the DO can. The observer puts the value back.
- **Insets:** all 8 layouts that dropped `fitsSystemWindows` now call `KidInsets.apply` (home, lock, pin lock, in-call, phone book, kid Settings, Wi-Fi, Bluetooth), with system bars and cutout plus the XML padding.
- **Language:** `LocaleManagerService` doesn't check `DISALLOW_CONFIG_LOCALE`, so the per-app language still works [needs device test]. Locale and zone validation keeps malformed values out of the QR.
