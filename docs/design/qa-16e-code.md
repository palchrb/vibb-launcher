# QA 16e code review - 1ee2298e (2026-10-07)

Status: all five findings fixed in the fix-round commit after `1ee2298e` (each marked below).

Build: worktree of 1ee2298e, `./gradlew --no-daemon testDebugUnitTest assembleDebug -PwarningsAsErrors=true` succeeds (727 tests, 0 failures; `BootMarkPlanTest` 8). `bash -n` and `shellcheck -S warning` pass on `smoke-test.sh`. Not device-tested. Paths are under `launcher/app/src/main/java/com/kidslauncher/mdm/`.
1. **High: the wait never checks that Home's mark is on screen.** `bootMarkStep` (`lock/BootMarkPlan.kt:83`) holds every BOOT ask for 3 s, whether or not our Home is up. If `HomeFront.bring` fails, or `BootHome.startIfDue` throws (`lock/HomeFront.kt:38`, `lock/PinLockRuntime.kt:323-328`), ProcessStart runs with homeFirst=false. Its `show(BOOT)` (`PinLockRuntime.kt:366`) then holds for 3 s with the stock launcher or FallbackHome in front and usable. Before 16e, this path showed the lock at once. When Home was started, the 1 s `LOCK_FALLBACK_MS` re-front (`:374`, `:872`) is also held until 3 s. So a Home that never resumes leaves the boot's front open for 3 s instead of 1 s. Fix: give `bootMarkStep` a `markUp` input: Home has resumed in this process and not paused or stopped since (set in `onHomeResumed`, cleared in `onHomeStopped` or a new pause hook). A BOOT ask without it shows at once; the showLockLater start only starts the clock. Add tests for both.
   **Fixed:** `bootMarkStep(state, ask, markUp, now, coverFrame, exempt)`: a BOOT ask without `markUp` shows the lock at once and ends the wait. `markUp` is set only in Home's locked resume (`PinLockRuntime.onHomeMarkUp`, right before its `show`) and cleared by `onHomeCovered` (pause, stop, lost focus). The `showLockLater` start only starts the clock (`bootMarkClock`), so a Home that never resumes gets the old 1 s fallback, and a failed or throwing `BootHome` (homeFirst=false, Home not up) shows the lock at once. Tests: `BootMarkPlanTest` "waits only while Home's mark is up".
2. **Medium: only Home's `onStop` counts as "Home covered"** (`ui/HomeActivity.kt:514`, `PinLockRuntime.kt:172`). With the kiosk off, nothing is in lock task during the wait, because only PinLockActivity enters it. The assistant's voice-interaction window, the power menu, or a translucent or dialog activity can come over the mark without stopping Home. They then keep the front until the backstop: up to 3 s, where before 16e it was about 0. Fix: also end the wait in Home's `onPause` (not for a recreation) and in `onWindowFocusChanged(false)`. Ending early only shortens the mark.
   **Fixed:** `HomeActivity.onPause`, `onStop` and `onWindowFocusChanged(false)` call `PinLockRuntime.onHomeCovered` (not for a recreation): the mark is down and the wait ends (`Home paused`/`Home stopped`/`Home lost focus`), the lock comes through `bootMarkEnd`.
3. **Low: the LOCKED chrome and the main thread wait on the hold's reads.** On a ProcessStart without homeFirst, `show(BOOT)` (`PinLockRuntime.kt:366`) runs before `refreshChromeNow` (`:367`). Through `bootMarkHolds` (`:203-207`) it makes Telecom, Audio and AlarmManager binder calls, reads BOOT_COUNT, and calls `BootCoverGuard.read` (DE file I/O). Home's locked resume (`HomeActivity.kt:407`) makes the same reads. At boot, system_server is slow. Fix: while `bootMark != Over`, run `refreshChromeNow` before `show` (`show` starts nothing first anyway). Read the cover's frame once, in init's IO coroutine (no frame yet = 3 s from the ask).
   **Fixed:** in `dispatch`, while `bootMark != Over` the LOCKED edge's `refreshChromeNow` runs before `show` (`chromeFirst`); otherwise 16c's order. The cover's frame is read once in an IO coroutine at `init` (`coverFrameMs`; not read yet = 3 s from the ask), and BOOT_COUNT is read once at `init`. `bootMarkStep` checks `markUp`, the window and the end before the exemption reads, so the binder calls run only when it would hold.
4. **Low: the wait keys only on BOOT_COUNT against a value stored with `apply()`** (`BootMarkPlan.kt:23`, `lock/PinLockStore.kt:99`). These cases wait as well: (a) A missing key: the first start of this build after its update. The screen-on ProcessStart is held, and only `showIfLocked` shows the lock, 1 s later. (b) A lost write: every restart in that boot waits over the kid's app, since `boot_home` is set and no Home is brought. (c) A process that started with the screen off: the 3 s begin at the first screen-on, possibly hours later. Fix: `bootMarkDue` also requires `elapsedRealtime()` under a bound (e.g. 5 min), and a first ask after the bound counts as `Over`. Test this.
   **Fixed:** `bootMarkDue(..., sinceBootMs)` requires the process start within `BOOT_MARK_WINDOW_MS` (5 min) of the boot, and a first ask (or the clock) after it is `Over`; `swapMarkBoot` uses `commit()`. (a) the update to this build and (b) a restart after a lost write are long after the boot, and with #1 a restart without Home's mark up never waits anyway; (c) a late first screen-on doesn't wait. Tests in `BootMarkPlanTest`.

   **Fixed:** no dump with the mark SKIPs both dump checks. A third check captures `logcat -d -v brief -s PinLock` once and greps it: `Process start:` (else SKIP), `Boot mark: the lock waits N ms` and `Boot mark over:` (else FAIL).
