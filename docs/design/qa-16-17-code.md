# QA code review: design 16 (e5b5f5a4) and design 17 (9fad6f27), 2026-10-06 - L = `launcher/app/src/main/java/com/kidslauncher/mdm/`
Read-only, tests not re-run. Checked OK: every Home start is the typed HOME intent; with the kiosk on Home roots lock task, the lock's 1 s fallback and `rootLeave` never strand an unlocked root lock, Home is asked at most every 3 s (no loop); BFU untouched (BootHome/VoipCalls run from `initRest`, CE prefs; HomeActivity and the listener stay non-DBA); `LockTaskChrome` is still the only DPM writer (VoIP is an input of `lockTaskWhileLocked`); Svar = FSI with ALLOW_IF_VISIBLE/ALLOWED, Avvis = EXTRA_DECLINE_INTENT, the ring's contentIntent is never kept; no notification text read or logged; the lock's system-call yield is `isInManagedCall` (SelfUpdate/BootHome/AppEnforcer keep `isInCall`, the conservative side); the smoke test greps captured dumps; server `lock_state` compatible both ways (`#[serde(default)]`, old servers drop the field).

1. **High - a VoIP ring or its end puts the lock over the system dialer's call, the emergency flow and the alarm.** L lock/PinLockState.kt:168-176 (`VoipRinging`/`VoipEnded` always `showLock`), lock/PinLockRuntime.kt:252-256, lock/VoipCalls.kt:187.
   A ring during a system-dialer (emergency) call, the Emergency-call dialer or a ringing alarm covers it with the card. A phone call answered during a VoIP call (calls unmanaged: audio leaves IN_COMMUNICATION -> NONE -> `VoipEnded`) is covered too. The lock is then resumed, so no re-front check ever yields back: the call can't be seen or hung up, the alarm can't be stopped. Our ringtone also plays over a live phone call. Fix: give both events `systemCall`, the emergency flow and the alarm, like `ProcessStart`/`RemoteLock` (no `showLock`, the re-front loop decides). Ring and wake only when no call, emergency flow or alarm is on.
2. **Medium - the wake can't work on the existing lock, and the stale bit wakes it later.** L lock/PinLockActivity.kt:142-149, 205-208. While LOCKED with the screen off the lock exists and is stopped, so `setTurnScreenOn(true)` only arrives in `onNewIntent`, after the start.
   AOSP decides a sleeping display's top activity at the start (ActivityStarter `resumeTargetRootTaskIfNeeded` -> AR `shouldBeVisible` -> `canTurnScreenOn`), and `ActivityClientController.setTurnScreenOn` only stores the bit. So the ring likely doesn't wake the screen. The bit is cleared only from `onResume`, so it stays set and the next unrelated lock start (`VoipEnded` after a missed or declined ring) wakes the phone in a pocket. Fix: start a small ring activity with a manifest `android:turnScreenOn="true"` (it is known at the start), and clear the lock's bit on a timer posted from `applyWake`.
3. **Medium - the ring card hides Emergency call, the keypad and Parent code for the whole ring.** res/layout/view_voip_ring.xml:7-19 (match_parent, clickable), L lock/PinLockActivity.kt:102-106, 186-188.
   A failed Avvis (CanceledException, or a decline PI that is an activity, sent with no BAL options at lock/VoipCalls.kt:264-267) leaves the card up. With #4 a stuck ring locks the kid out. Fix: keep Emergency call (and Parent code) on the card, or cover only the keypad. Let Avvis always hide the card for this ring, and send the decline with the visible-sender options.
4. **Medium - RINGING has no cap.** L lock/VoipCallPlan.kt:117-119 returns RINGING before any `timedWindowActive` check, so the yield ("voip"), the no-ScreenOn rule and the no-lock-task rule last as long as an allowed app's CALL+FSI notification exists. Re-rings keep the record, so the 3 h cap never bounds rings.
   Fix: add a ring limit (e.g. 2 min from the ring's first sight, stored with the record) and the 3 h cap to that branch. Past either, return NONE (the lock comes back; the package stays pinned while its call service lives).
5. **Medium - the ringer runs only on phase edges.** L lock/VoipCalls.kt:186-188, lock/PinLockRuntime.kt:208. A ring that began UNLOCKED goes silent once a screen-off (often the timeout) locks the phone, because the LOCKED status-bar flags make NMS clear Element's insistent sound and ours never starts: the reported missed-call bug persists for that case.
   Fix: evaluate "ring = RINGING && LOCKED && !silenced" on every mode change too, and silence only on a screen-off that finds the lock already LOCKED and ringing. DND: `notificationPolicy` (VoipRinger.kt:35) is the manual policy; use `consolidatedNotificationPolicy` (public in android-36), so that an active Mode that blocks calls also stops our vibration.
6. **Low - `voipPinned` is too wide.** L lock/PinLockActivity.kt:250, lock/LockTaskRoot.kt:47. It also applies with the kiosk on (the design says kiosk off only). It also covers the NONE+pinned state, which has no limit (the call service outlives the cap, or audio leaves IN_COMMUNICATION), and for that whole time the kiosk-off lock is re-front-only.
   A lock that is already resumed when the pin clears never runs `ensureLockTask` again; it only runs from `onResume` or the fallback. Fix: `voipPinned = !kioskOn && phase != NONE`, and call `ensureLockTask` from `voipListener` when that changes.
7. **Low - a restored record.** L lock/VoipCallPlan.kt:136-141, lock/VoipCalls.kt:228-236. Before the listener reports, IN_CALL holds on `startup || audio`: audio alone (any app's MODE_IN_COMMUNICATION) keeps it up to 3 h if the listener never reconnects, against QA #5's AND. `ringEndedElapsedMs` isn't stored, so after a crash or update with a stale record the first report starts a fresh 15 s grace (~30 s without a lock: `ProcessStart` doesn't show it in IN_CALL). Fix: store ringEnded (or set it to the restore time) and drop the audio-only OR.
8. **Low - IN_CALL can take a ring's content intent.** L lock/VoipCallPlan.kt:67, badges/VoipCallReader.kt:44. Any foreground-service CALL notification without an FSI is "the call", and `LockResumed` sends its contentIntent. An incoming CallStyle ring posted without an FSI by a call service (Signal/Molly ring from theirs) would be sent unasked. Fix: never IN_CALL when `EXTRA_CALL_TYPE == CallStyle.CALL_TYPE_INCOMING` (an int, not text), and add that to `VoipCallGuardTest`.
9. **Low - server.** server/src/kid_lock.rs:123-128, 214-219 put device-supplied strings into a copy-paste `adb shell appops set <package>` command. Askama escapes the HTML but not the shell, so a tampered report reaches the parent's terminal. Fix: in `sanitize_lock_state`, keep only valid package names (`^[A-Za-z][A-Za-z0-9_]*(\.[A-Za-z][A-Za-z0-9_]*)+$`).
10. **Low - the smoke test.** scripts/smoke-test.sh:553 - the Recents and swipe-up checks pass without the kiosk's lock task (no BlockedAppActivity is possible then). Fix: skip them unless `lock_task_state` is LOCKED.

## Resolution (2026-10-06)

1. **Fixed.** `VoipRinging`/`VoipEnded` carry our call, the system dialer's (Telecom-managed, emergency included) call,
   the emergency flow and the alarm; with any of them in front the step neither shows nor wakes the lock but sets
   `LockStep.recheck` - the re-front loop yields to them and brings the lock back after them. `refrontAction` checks
   VoIP last (system call, emergency, alarm first; the alarm exemption still ends on its own yield). The ring is the
   pure `voipRingWanted` (RINGING, LOCKED, not silenced, no other call, emergency flow or alarm), re-evaluated on
   every VoIP pass (the 2 s poll included) and every lock-mode change (`PinLockRuntime.syncVoipRinger`). Tests:
   `PinLockStateTest`, `RefrontPolicyTest`, `VoipCallPlanTest`.
5. **Fixed.** The ring follows `voipRingWanted` on every mode change, so a ring that began unlocked starts ringing
   when a screen-off locks the phone; a screen-off silences only a lock that was already LOCKED and ringing
   (`screenOffSilencesRing`, per ring). DND reads `consolidatedNotificationPolicy` on 36 (the manual policy on 34/35).
