# QA 16c code review (commit e9850624, 2026-10-07)

In a worktree of e9850624, `./gradlew --no-daemon testDebugUnitTest assembleDebug -PwarningsAsErrors=true` is green: 675 tests, 0 failures (`HomeGateTest` 6). **I found no path where Home shows its content or takes touches while LOCKED.** `decide` runs from `initUnlocked`, which runs on the unlock or through `KidAppComponentFactory` before any component that isn't direct-boot-aware, so no CE storage is read before the unlock and the mode is set before Home's `onCreate`. Every mode change goes through `dispatch` and its listeners, so the LOCKED edge swaps in the night ground in the same message that starts the lock, and the UNLOCKED edge always binds the content. A configuration change or `recreate()` re-gates in `onCreate`. A crash restart is decided LOCKED. Home is excluded from Recents. A time rule at start now starts the lock early, which still fails closed. For `MARK_DONE`, Home's own locked resume roots lock task and starts the lock, and ProcessStart starts it again with no 1 s wait. The boot-cover hand-over and our call screen (`showCall`) are unchanged. On the chrome thread, `LockTaskChrome` is still the only writer: the executor runs passes one at a time, in order, under the monitor, and each pass reads the mode, plan, fence and VoIP pin when it runs, so a stale pass can't win or unpin a lock that is in lock task.

1. **Medium - the locked chrome now lands after the lock is up** (`PinLockRuntime.kt:234,244,276-286`). Before this commit `refresh` ran on the main thread, so the lock could not resume until the status bar was off and `DISALLOW_CREATE_WINDOWS` was on. With the kiosk on, the features had also lost NOTIFICATIONS/HOME/OVERVIEW; with it off, our package was pinned. Now there is a window of one pass, plus any wait on the monitor, while the screen is on: at a process start (two `apply()` passes), RemoteLock, CallsEnded and VoipEnded. In that window the shade, Overview and overlays work over the lock until the re-front loop brings it back. This loosens the "always in lock task while LOCKED" rule (qa-10-code #7). Fix: resolve `pinLockHelpers()` before taking the monitor in `applyPlan` (`LockTaskChrome.kt:46-58`). In a LOCKED pass, write the status bar and `DISALLOW_CREATE_WINDOWS` first. Record the window in the 16c status and add a device check: pull the shade right at a LOCKED process start, with the kiosk on and off.
   **Fixed**: the LOCKED edge's pass runs on the main thread again, right after the lock's start, so the lock resumes only after it (`PinLockRuntime.refreshChromeNow`); the other passes stay on the chrome thread. A LOCKED pass writes in `chromeWriteOrder` (status bar, `DISALLOW_CREATE_WINDOWS`, then lock task; the reverse when unlocking). No PackageManager work runs under the monitor: `applyPlan` resolves the helpers first (numbered, the newest kept), and the main-thread pass uses cached helpers only (missing: our package alone, then a chrome-thread pass adds them). Every pass reads the state under the monitor, so the newest wins. The window and the device check are in the 16c status. Tests: `HomeGateTest` (write order, helpers outside the monitor, show then chrome on the LOCKED edge).

3. **Low - if `decide` throws, Home goes dark and no lock is shown** (`Application.kt:209-213`, `PinLockRuntime.kt:124-131,158`). Nothing else sets `decided`, so it stays false for good. `init` calls `decide` again; that throws out of `init`, so there is no ProcessStart and no screen receiver. The mode stays DISABLED, so Home's resume starts no lock, and `pinSetStored` (unreadable means set) keeps the night ground. The kid has neither Home nor a PIN pad until a reboot. The trigger is only theoretical: CE prefs read after the unlock. Fix: on failure set the mode to LOCKED with `decided = true`, which fails closed but leaves a lock that can be unlocked, and catch the error inside `init`.
   **Fixed**: pure `lockActiveAtStart` (unreadable = active), so `decide` always decides: LOCKED, with the lock shown. `init` catches the PIN and inactive reads, so the receiver and ProcessStart always run. The lock's own reads are covered too: an unreadable crash guard counts as armed, an unreadable wrong-PIN count leaves only the parent code, and the parent code always opens the lock. Tests: `HomeGateTest`.
