# QA step 11b code review: call-screen avatar, ongoing-call card, camera lock, qa-11-code fixes (84d315d5..af60dafc)

Reviewed 2026-10-06 on `master`. L = `launcher/app/src/main/java/com/kidslauncher/mdm/`. Ran: L `testDebugUnitTest`, 505 green. **No H.** No camera can stay suspended for good. Cameras are always controllable, so the first `apply()` that runs with an empty `CameraLock.held` unsuspends any camera its plan doesn't want suspended. The worst case below is "until the next `apply()`", which is at most the 30-minute backstop sync. M = fix in this round, L = fix or record.

## Findings
1. **M, L `apps/AppFilter.kt:53-59`, `Application.kt:83-89`: every lock cycle removes the camera from Home and puts it back.** `AppFilter` drops every suspended package from the grid. At each LOCKED, `onPackagesSuspended` → `loadApps()` → Home's `observeForever` renders a grid without the camera. At the unlock Home first shows that stale grid, and the camera tile pops back in after `onPackagesUnsuspended` → `loadApps()` → icon render. The grid is alphabetical, so every later tile shifts under the kid's first tap. That is also two full app reloads and icon renders per screen-off/unlock. The time-rule `LockActivity` usable list (`ui/LockActivity.kt:193`) can show the camera unusable right after an unlock for the same reason. **Fix:** count `CameraLock.held` as not suspended in `AppFilter.isMdmSuspended` and `LockActivity`, and skip `loadApps()` when every package in the callback is in `held`.
2. **L, L `lock/CameraLock.kt:96-121, 70-73`, `lock/CameraLockPlan.kt:69`: three ways a camera stays suspended after the unlock until the next `apply()`.** (a) Release clears `held` only after the DPM unsuspend and the prefs commit. An `apply()` pass that reads the camera's state in that gap sees "not suspended", but the package is still in `held`, so it suspends it again, now without a record. (b) `locked` is captured when the task is queued. If `refreshTargets` reads `chromeLocked` just before an unlock, it can queue `true` behind the unlock's `false`, and the camera is suspended and recorded for the whole unlocked session. (c) A target that is already suspended at LOCKED counts as enforcement's and is never recorded or released. Three causes: a lost or corrupt `camera_lock.xml`, the `commit()` result ignored at :99-100, or case (a). **Fix:** remove the packages from `held` before unsuspending, and clear the record afterwards. Have `sync` read `PinLockRuntime.mode == LOCKED` when it runs. Don't suspend when the record commit fails. After a Release, if a target is still suspended and not in `lastPlanSuspend`, request an `apply()` off the camera thread. The existing `requestApply` at :118 also runs on that thread and waits on `AppEnforcer`'s lock, which contradicts the class doc, so move it off as well.
3. **L, L `lock/CameraLock.kt:140-142`: third-party camera-action handlers go dark at every screen-off.** Non-system handlers of `STILL_IMAGE_CAMERA`/`VIDEO_CAMERA` are targets too. Any allowlisted app that declares one of these actions, such as a camera-first messenger, is suspended whenever LOCKED, which is most of the day. A DPM-suspended app has its notifications hidden and can't ring the device, so its calls and messages are silent until the unlock. The same reasoning already keeps chat apps that answer `ACTION_IMAGE_CAPTURE` out. **Fix:** of the third-party handlers, suspend only the one the gesture actually resolves to (the `resolveActivity` default), or record this as a residual and log which non-system packages are suspended.
4. **L, L `ui/HomeActivity.kt:159, 527-575`, `calls/InCallActivity.kt:127`: Home's call ticker can outlive `onStop`.** `callsListener` posts a `renderCallCard` lambda, which `onStop` doesn't remove. If that lambda runs after `onStop`, it re-arms `callTicker`, which then ticks every second with Home stopped (or destroyed by a recreate, holding the activity) until the call ends. Each tick, and each `InCallActivity` render, also makes an `isEmergencyNumber` binder call on the main thread. **Fix:** set a `started` flag in onStart/onStop and return from `renderCallCard` when it is false; cache the emergency verdict per call handle.
5. **L, docs `docs/testing/emulator.md` §6d: the camera check covers only gesture → lock → PIN.** Add: reboot and `am crash` while LOCKED (the camera is suspended again, then released by the PIN); the PIN lock switched off, or an Android PIN set, while LOCKED (released without an unlock); a sync running during the unlock (the camera stays usable); the Home grid keeps the camera tile; and what Android shows instead of the camera - for DPM suspension Settings' admin-support dialog ("Learn more") - with the kiosk on and off: it must not stay usable over the lock.

## Verified (no finding)
- **Camera lock targets** are camera handlers ∩ controllable, minus our package and `.debug`, the system and default dialer, the keyboards, the PIN-lock helpers (emergency dialer, Telecom, system dialer, clock), the kiosk helpers and Play core (Play Store, Play services, GSF). SystemUI, `com.android.phone` and other headless system packages are never controllable.
- **Update fence.** The fence and the orphan sweep only touch non-controllable HOME candidates and the camera lock only controllable packages, so they never overlap. `apply()` keeps both `fenceHeld` and `held`. Fence creation and the sweep both hold `AppEnforcer`'s lock, so a fence that is going up is never swept.
- **Time rules.** A camera that enforcement suspends at the lock is never claimed. A camera that enforcement starts to suspend later stays suspended at the unlock (`lastPlanSuspend`). When a rule ends while LOCKED, `apply()` unsuspends the camera and `refreshTargets` suspends it again, with a gap of milliseconds.
- **Start, crash, unenroll, lock off.** The record survives a reboot, crash or update. A process that starts LOCKED engages the camera lock again; one that starts not LOCKED releases everything, and `apply()` settles the rest. Unmanaged, lock switched off, crash guard tripped or Android credential set: each gives `Configured(false)` → DISABLED → release. Not device owner: the record is cleared, the same as the fence.
- **B1 call-screen avatar.** Before the first unlock (and while still "unlocking") `callAvatar` returns the silhouette, so there is no `ContactPhotos`, `KidAvatars` or CE access. `defaultCc` and `TelephonyManager` are DE-safe. Emergency calls get the silhouette and, on Home, no name; the call path is unchanged.
- **B2 ongoing-call card.** A tap only starts the explicit `InCallActivity`, which finishes when no call is left. The listener and ticker are removed in `onStop`. The card hides and the contacts row comes back once `hasLiveCall` is false.
- **qa-11 fixes.** A DEFERRED install neither fences nor backs off and keeps the APK. A group summary is cancelled only when every non-ongoing child would be.
