# QA: design 08 (UI polish) - code review

Scope: L `ca83d1a..e0cdf09`, S `d8de63c`, `dd93be2` (branch `handy`). Tests: L `testDebugUnitTest` green, S `cargo test` 144 passed.
Verified OK: the device route `GET /api/devices/wallpapers/{hash}` joins `device_wallpapers` on the device (`device_api.rs:1026-1053`) and validates the hash first. Upload holds `WALLPAPERS` lock across store and insert, and delete prunes after commit. Prune scans its own dir and skips `.tmp`. The backup prefix is `wallpapers/`, and recovery deletes the row (FK cascade). EXIF-swap crop is correct (`photos.rs:198-225`, `portrait_crop`). Picker ids are re-validated against the allowed list (`effectiveWallpaper`). Sync deletes every image that is no longer allowed, then applies (`WallpaperStore.kt:226-260`). Lock screen gets navy unless opted in. KidSettings re-checks `lockReason` on resume and on the pref change (`KidSettingsActivity.kt:60-69,116`), is `exported=false` and has no long-press. Phone-book tile only widens (`showPhoneBookTile`). LockActivity/PhoneBook/emergency logic is unchanged except font and ground. Icons are rendered on `Dispatchers.Default` with key = app|size|density. One RGB_565 decoded bitmap is sampled to the screen with a bounds check.

## Findings

1. **High - unmanage lifts `DISALLOW_SET_WALLPAPER` before navy is put back.** `AppEnforcer.kt:199-206` clears every `!set` hardening restriction at the very start of `apply()`. `resetIfOurs` only runs in `applyHardening` at the end (`AppEnforcer.kt:358-363`). In between, ~150 lines can throw (VPN, kiosk, browser policy), and the comment says that is why the clears come first. So the restriction is lifted while our photo is still the system wallpaper, and if anything throws, the reset doesn't run in that pass at all. This breaks the binding "reset ... before the restriction is lifted". Required: call `WallpaperApplier.resetIfOurs` in the early clear loop just before SET_WALLPAPER is cleared, or skip SET_WALLPAPER there and clear it only after a successful reset. Add a pure test that the plan orders reset before the clear (e.g., extract the clear-order list).
2. **Medium - a private photo can stay on the system wallpaper with no record of it, so it is never reset.** (a) `setBoth` (`WallpaperApplier.kt:145-150`): when `FLAG_SYSTEM` succeeds with the photo but the lock `setBitmap` returns 0 or throws (caught at :154), it returns 0. `recordAttempt` then keeps the old record. On a first apply, or after a reset, `appliedKey` is null, so `resetIfOurs` returns at :122 on unmanage and the photo stays after the restriction is lifted. (b) `resetIfOurs` saves an empty record even when its `setBitmap` failed (:129-132), so a failed reset is never retried. Required: set LOCK before SYSTEM (or record "ours possibly applied" as soon as the SYSTEM call returns non-0). Only clear the record after a successful reset (id != 0). Otherwise fall back to `WallpaperManager.clear(FLAG_SYSTEM or FLAG_LOCK)` and retry on the next pass.
3. **Medium - a revoked photo stays on the system wallpaper for up to a day after a refused/failed apply.** On untick or delete, `sync` calls `applyIfNeeded` with the new key. If that `setBitmap` fails, `wallpaperApplyPlan` returns `Skip("already tried today")` (`WallpaperApplyPlan.kt:250`) until tomorrow. Meanwhile the photo remains in `/data/system/...` and in recents/lock (if it had lock opt-in). The binding says "replaced at once". The once-a-day backoff exists to avoid a PNG-encode loop, but it should not apply to removal. Required: when the applied key's image is no longer allowed (or the file was just deleted), treat it like Reset: navy, or `clear()` if setBitmap fails. Retry on every sync until the record no longer names a revoked hash. Add a `wallpaperApplyPlan` test for "applied image revoked + attempt failed today → Reset/Apply, not Skip".
4. **Medium - the picker can loop forever decoding thumbnails.** `thumbs` is a 2 MiB LRU (`WallpaperStore.kt:80-82`). Each decode `put`s and calls `notifyListeners` (:214-215). KidSettings' listener calls `render()` (`KidSettingsActivity.kt:58`), which calls `thumbnail()` for every photo tile (:239) and re-queues each evicted one. At xxhdpi a 64 dp thumb of a 1080x2400 image is 270x600 RGB_565 = 324 KB, so 7+ allowed photos never fit. The result is continuous decode on the store thread plus a full re-render on the main thread (rebuilt grid, `cachedPolicy()` parse, Wi-Fi/BT state, brightness `progress` reset mid-drag, a binder `getWallpaperId`) for as long as the screen is open (inferred count; the mechanism is verified in code). Required: decode thumbs at tile size (`inSampleSize` + scale to ~sizePx, or cache a scaled copy), size the LRU for the allowed count, notify only the picker (not a full `render()`), and don't notify when the cache already had the hash.
5. **Low - icon rendering now touches shared app drawables off the main thread.** `DetailedAppInfo.getIcon` returns the one cached `getBadgedIcon` drawable, which the drawer also draws. `renderAppIcon` (`KidAvatars.kt:120-155`) now runs on `Dispatchers.Default` and calls `setBounds` on its layers/legacy drawable (:144, :152) without restoring them. `monochrome.mutate()` (:133) tints the shared parent's own layer (mutate() returns the same object). Before this change the same calls were made on the main thread. Required: render from `drawable.constantState?.newDrawable()?.mutate()` (or restore bounds) so the background pass never mutates the drawer's instance.
6. **Low - `WallpaperGround.apply` makes a binder call on the main thread on every render.** `WallpaperApplier.systemShows` calls `WallpaperManager.getWallpaperId` (`WallpaperApplier.kt:71-79`) and reads prefs. It runs on Home resume, on every store notification, and in PhoneBook/KidSettings `render()`. Cheap, but it is IPC, and it multiplies under #4. Required: cache the `systemShows` result in `WallpaperStore.State` (computed on the store thread after an apply or refresh).
7. **Low - escape guard coverage.** `KidScreensEscapeTest.kt:30` guards `ui/kidsettings`, `ui/quickcontrols`, `ui/wallpaper` and `server/QuickControls.kt`, but not `ui/HomeActivity.kt`, `ui/home/*` (the new Settings tile and swipe) or `calls/PhoneBook*`. It also doesn't catch string actions (`"android.settings."`, `"android.intent.action.SET_WALLPAPER"`). Required: add those paths and the string prefixes. The long-press test matches one exact source line, which is brittle; assert on the `homeGrid` model/adapter behaviour instead, or keep it and accept that.
8. **Low - S: a cosmetic failure blocks the whole policy, and backups race with prune.** `device_api.rs:237` uses `policy_wallpapers(...).await?`, so a wallpaper query error makes `/api/devices/policy` fail (time rules, calls) for that device (inferred; same DB). Use the empty list plus a log. `Store::add_to_zip` (`photos.rs:390-407`) reads files without the store lock. A delete+prune between `read_dir` and `fs::read` fails the whole backup run via `?`. Skip `NotFound` entries instead. This pattern predates this change for contact photos; wallpaper deletes make it more likely.
9. **Info - not verifiable here.** The Quick Controls "no switches" root cause is still not recorded (08 status, QA 08 #9). Every [device] item in `qa-08-design.md` is untested: `setBitmap` id != 0 under the restriction, lock screen colour by default, untick → replaced within one sync, unmanage → navy then lift, bedtime over KidSettings/Wi-Fi, gfxinfo/heap. Findings 1-3 should be re-checked on the Jelly Star with `adb shell dumpsys wallpaper` after unmanage and after a forced lock-set failure.
