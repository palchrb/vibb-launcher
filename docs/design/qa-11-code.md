# QA step 11 code review: kiosk escapes (3bd1fb55, 865ab6f8, 5224b48b, 7fadac42, 95e7b8d8, ded523b3)

Reviewed 2026-10-06 on `master` against 11-kiosk-escapes.md ("Decisions after QA review", "Implementation status") and qa-11-design.md. L = `launcher/app/src/main/java/com/kidslauncher/mdm/`, S = `server/src/`. Ran: L `testDebugUnitTest` 485 green, S `cargo test` 190 green. **No H**: I found no way for the fence to outlive a running build with the release code. M = fix in step 11, L = fix or record.

## Findings
1. **M, L `server/UpdateFence.kt:124-127, 216`: losing the record strands the fence for good.** `check()` reads a missing record as "no fence". A corrupt `update_fence.xml` loads as an empty map, because SharedPreferencesImpl swallows the parse error, and a hotfix or refactor build that drops or renames the file ends up the same way. The fenced HOME packages then stay DO-suspended for good (Pixel quickstep/Recents, A3). Every later fence also skips them as `ALREADY_SUSPENDED`, so no fence ever records or releases them. **Fix:** an orphan sweep under `AppEnforcer`'s lock, at process start and in `duringApply` whenever no record exists. It unsuspends, through DPM (idempotent, removes only our suspension), every HOME candidate that is not controllable, not protected and not ours. Nothing else in L suspends such packages: `AppEnforcer` only suspends controllable ones and `PlayRuntime` only Play. Report `last_release = "orphan"`, and add a pure selector with a test.
2. **L, L `server/MdmSyncWorker.kt:584` → `AppInstaller.kt:102-104`: the gate is stale at the point of no return.** The window gate runs before the archive parse, the SHA-256 and the copy into the session, which take seconds. `SelfUpdate.onScreenOn` (`SelfUpdate.kt:98-101`) only cancels the alarm. A wake or an incoming call in those seconds still commits, although design §2.2 says "cancelled by SCREEN_ON" (QA #8: such a call rings unscreened). **Fix:** run the gate again (screen off, no live call, no emergency) inside `beforeCommit`. On a miss, abandon the session and keep the pending APK, without dropping it or setting a backoff.
3. **L, L `server/SelfUpdate.kt:110-113`: screen-off time falls back to the process start.** With the screen off and `screenOffSinceElapsed == null`, the code falls back to `Process.getStartElapsedRealtime()`. That case covers the gap after a SCREEN_ON and before the late SCREEN_OFF broadcast lands on the busy main thread. A sync in that gap reads "off for hours" and commits right after a power-button press, at night or once overdue. **Fix:** use the process start only while no screen event has been seen in this process; otherwise count 0.
4. **L, L `server/MdmSyncWorker.kt:626-629, 646-650`, `server/AppInstallReceiver.kt:56-63, 85`, S `kiosk_escapes.rs:259-262`: pending-APK failures are retried by downloading again.** A commit that doesn't go through (no space for the session copy, `commit()` throwing) clears the attempt and drops a verified APK with no backoff, so the full APK is downloaded again at every sync (the regression QA #10 warned about), yet the card says "after an hour". `PENDING_USER_ACTION` deletes the file (`status != SUCCESS`) but keeps the pending entry and clears the attempt, so each sync in the window does `REPLACE_PENDING`, a new download, a new fence and a new session that is never abandoned. `DOWNGRADE`, `NOT_OURS`, `UNPARSEABLE` and a wrong signing key are deterministic, yet downloaded again every hour and fenced every night. **Fix:** on a commit failure keep the pending APK and back off with `recordFailed`; abandon the session on `PENDING_USER_ACTION`; make deterministic refusals stick until the tag changes; add a signer check to `pendingApkCheck` (archive `GET_SIGNING_CERTIFICATES` against our `signingInfo`) before fencing; fix the `commit_failed` card text.
5. **L, L `server/UpdateFence.kt:447-465`, S `kiosk_escapes.rs:161-174`: the fence's state and refusals never reach the parent.** `state` and `unsuspendable` come from the live record. The status report goes out before the commit (`MdmSyncWorker.kt:221` vs `:256`), and the new process releases at its start (screen off). So "fenced", "Android refused to pause …" and a partial fence are practically never reported. `lastRelease` lives only in memory. A phone that went silent while its last report said "fenced" shows "installing right now" forever. **Fix:** keep a last-fence summary (reason, unsuspendable, role held, times) as new keys (only ever add keys), report it, and let the card age out "right now".
6. **L, L `badges/BadgeListenerService.kt:50-60`: cancelling a group summary takes its children with it.** NMS `cancelGroupChildrenLocked` cancels every non-ongoing child of a summary a listener cancels, whatever the child's FSI, category or channel. A child the rule keeps (alert channel, CALL/ALARM, FSI) under a summary it cancels goes too. **Fix:** never cancel a `FLAG_GROUP_SUMMARY` notification unless every active child of its group would be cancelled. Add a test.
7. **L, L `server/AppEnforcer.kt:392`: the essential set misses OEM cell-broadcast apps and needs a B1 check.** Essentials are resolved only from `SMS_CB_RECEIVED`, but CellBroadcastService finds the alert app through `ACTION_SMS_EMERGENCY_CB_RECEIVED`. Also query that action, so an OEM-named alert receiver stays. B1 should also classify Play services' system-update "restart" notification: the rule cancels it today, so a patch can wait for an unplanned reboot.
8. **L, S `kiosk_escapes.rs:190-192, 242, 108`: i64 arithmetic on phone-supplied values.** `now_ms - since` and `len + dropped` overflow: they panic where overflow checks are on (debug/test) and wrap in release. `dropped` and `pending_since_ms` are stored uncapped. **Fix:** use `saturating_*` and clamp both when sanitizing. Add a test with `i64::MIN`/`i64::MAX`.

## Verified (no finding)
- **Fence always ends:** reboot (boot count); crash before commit (no or uncommitted session in a non-committing process); pre- or post-kill failure (result broadcast, session gone, alarm); `PENDING_USER_ACTION`; success without replacement; > 10 min; unknown `v`; unmanaged or not device owner (a DPM throw still clears the record); switch off (next `apply()`/check); replaced (front, screen off, or the 2 min wall/process-age backstop). Fresh processes also run `apply()` (in-memory `lastEnforcedLockKey`), so release doesn't hang on `UpdateFence.init` alone. A downgrade is refused before fencing.
- **Status bar:** single owner (`LockTaskChrome`), latch invalidated on every fence/release, no lock-order inversion (AppEnforcer → LockTaskChrome only). **Home/lock after `MY_PACKAGE_REPLACED`:** Home is started in `onReceive`; ProcessStart and then `showIfLocked` are posted after it, so the lock ends on top; same on the failure path.
- **Clock/timezone tricks: harmless.** Locked while managed (`AppEnforcer.kt:762-773`); even if changed they only move a commit that still needs 30 s screen-off, no call and the fence; a clock set back only delays. **APK:** `noBackupFilesDir`, unique names, cleaned at start and after results; size, SHA-256, package and versionCode checked before fencing.
- **Notifications:** own/`.debug`, FSI, insistent, ongoing, essential categories and essentials kept; nothing cancelled while the policy is unknown, the switch is off, unmanaged or overridden; input has no text fields; logs carry package/channel only. **Server:** reports re-serialized and capped, switches always sent, auto-escaped template, redirect without a fragment keeps `scroll-restore.js` working (no PWA jump). Pure tests match the QA acceptance tables; the gaps are the cases in 1-8.
