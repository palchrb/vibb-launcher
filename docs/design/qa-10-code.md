# QA step 10 code review: own PIN lock + call screens

Reviewed 2026-10-05: S `c101836` `6d7a36b` `e2ce962`, L `df2c651` `a0c689b` `88294b2` `e7c6ccf` `e078ee1` (`handy`) against 10-lock-and-call-ui.md (decisions) and qa-10-design.md. S `cargo test` 168/168 pass; L `testDebugUnitTest` 376/376 pass. H = fix before the device run, M = fix in step 10, L = fix or record. [inferred] = from platform/OEM behaviour, not proven here.

## Findings
1. **H, calls: Back on the call screen while LOCKED strands the call.** `InCallActivity` (L `calls/InCallActivity.kt:62-73`) has no Back handling, so Back (or a slip) finishes it or moves it back, and the PIN lock is in front. The lock has no "back to call" control (`lock/PinLockActivity.kt:120-132`), and the call notification can't be reached (shade off while LOCKED). A ringing allowed call can't be answered: the 300 ms retry (`KidInCallService.kt:150-161`) has already run. An active call can't be hung up and speaker/mute can't be used until the PIN. Android's keyguard had "Return to call", so this is a regression. **Fix:** swallow Back in `InCallActivity` while any call exists. In `PinLockActivity.onResume`, start `InCallActivity` again if `OngoingCalls.calls` isn't empty (or show a "Back to call" button). Add a test: lock resumed during a ringing call → in-call UI started.
2. **M, lock: a power-button screen-off during a call can leave the phone unlocked.** `step` ignores a `ScreenOff` with `proximityNear == true` (`lock/PinLockState.kt:76`), and `CallsEnded` never locks (`:88`). A proximity screen-off doesn't change interactivity, so it very likely sends no `ACTION_SCREEN_OFF` at all [inferred]. Any SCREEN_OFF during a call is then the power button or a timeout. With the phone at the ear or in a pocket (near), the press is ignored, the call ends with the screen off, and the next power press opens the phone unlocked. The test `PinLockStateTest:46` pins this behaviour. **Fix:** in-call SCREEN_OFF → LOCKED regardless of proximity, or at least `CallsEnded` while `!interactive` → LOCKED + show. [device] Logcat SCREEN_OFF during a proximity blank.
3. **M, lock: LOCKED during a call shows whatever is in front.** If the phone becomes LOCKED during a call (power button from UNLOCKED, or a remote lock), nothing is shown: `ScreenOn` shows nothing while `inCall` (`PinLockState.kt:81-82`). The PIN lock isn't started, so with the kiosk off there's no lock task, and no re-front loop runs. Until the call ends, anyone who presses power gets the last app (Home is the only backstop, `HomeActivity.kt:303`). **Fix:** on ScreenOn/RemoteLock while LOCKED and `ourCall`, start `InCallActivity` (the call screen in front, inside the lock task). Or start the lock with a "Back to call" button (same mechanism as #1).
4. **M, re-front: the "alarm ringing" exemption is any front task, from any app's alarm.** `refrontAction` yields for 10 min after any `AlarmManager.nextAlarmClock` time (`lock/RefrontPolicy.kt:308`, `PinLockRuntime.kt:324-331`), whoever set it. With the kiosk on, an allowlisted third-party app can call `setAlarmClock` (an alarm or reminder app the kid sets while unlocked). For 10 min after it fires, its ring screen or full-screen intent, or any other allowlisted app that reaches the front, isn't re-fronted. The decision exempts only the default clock app's alarm screen. **Fix:** remember the alarm only when `nextAlarmClock.showIntent.creatorPackage` is the system clock app (`alarmAppPackage`, FLAG_SYSTEM). End the window when the lock resumes after the alarm, not after a fixed 10 min. Add a `RefrontPolicyTest` case.
5. **M [inferred], lock: system in-call UI → "Add call" opens the full dialer over the lock.** With the kiosk off, `pinLockHelpers` pins the system dialer (`server/LockTaskHelpers.kt` `pinLockHelpers`, `AppEnforcer.kt:622`). `telecomInCall` yields for the whole of any call (`RefrontPolicy.kt:306`). If our dialer role isn't held (calls unmanaged), any incoming call (anyone can call a stolen phone) shows the system in-call UI. Its "Add call"/contacts entry opens the dialer's main screen (call log, contacts, keypad). That screen is a pinned package, and the re-front yields to it until the call ends. **Fix:** pin the system dialer as a lock helper only when our dialer role isn't held. Then add "Add call"/dialer from the system in-call UI to the device checks, and to the privacy text if it is reachable. [device] Kiosk off, calls unmanaged: answer over the lock → Add call.
6. **L, crash guard counts more than crashes.** QA #14 says config changes and process kills must not count. `configChanges` (`AndroidManifest.xml:151`) leaves out mcc/mnc (SIM swap), locale, fontScale and density, so these recreate the activity and add an uncleared start. `onDestroy` clears only when finishing (`PinLockActivity.kt:146-151`), and the code says a kill in the first 30 s counts. Three in 2 min switch the lock off for at least 10 min. **Fix:** in `onDestroy`/`onSaveInstanceState` with `isChangingConfigurations`, drop this start, and add `mcc|mnc|locale|fontScale|density|layoutDirection` to `configChanges`. Add a test.
7. **L, screen-off fast path does PackageManager work before the lock starts.** `dispatch` runs `LockTaskChrome.refresh` before `show()` (`PinLockRuntime.kt:127-137`). With `helpers == null` (no kiosk-off apply yet in this process), that is the full helper resolution on the main thread (`LockTaskChrome.kt:72-74`), which widens the screen-on content-flash window. **Fix:** call `show()` first or post the chrome, and resolve helpers at `init`.
8. **L, S text is off by one.** `device_detail.html:249` says "After 4 wrong PINs the phone waits 30 s", but 4 tries are free and the 5th wrong PIN starts the 30 s (`PinBackoff.kt:163-171`). **Fix:** "After 5 wrong PINs".
9. **L, S: the override cross-check is PBKDF2 on the async worker, and the kid-PIN save has a race.** `update_policy` runs `override_conflicts` (210k PBKDF2) inline (`devices.rs:1361`; `hash_pin` was already inline). `update_kid_lock` checks the override (`devices.rs:1463-1500`) and then writes without re-checking it, so a parallel "remove unlock code" can leave a kid PIN with no parent code. **Fix:** `spawn_blocking` the cross-check, and add `AND override_pin_hash IS NOT NULL` to the kid-PIN `UPDATE` (zero rows → `needs_override`).

## Checked, OK
Backoff only extends (reboot/clock ±, counted and committed before PBKDF2, reset on new hash); the parent code works offline and during the wait (own wall-clock 5/15-min lockout, unchanged); lock task while LOCKED (kiosk on: list untouched, minus NOTIFICATIONS/HOME/OVERVIEW, KEYGUARD kept; kiosk off: ours + system helpers, own `startLockTask`, stopped on unlock; Home doesn't stop it); unlock restores features (apply requested when there's no plan); emergency via Telecom, dialer fallback pinned with the app block on and off; incoming call → hang-up → `CallsEnded` → lock; in-call UI shows only answer/decline or speaker/mute/hang-up; S: kid PIN 4-6 digits, needs an override, cross-rejected both ways, `lock_state` re-serialized to known fields (no unlock times), hash only in the policy response; L backup off + extraction rules.

## Re-check 7aaf962 (system dialer not pinned while our dialer role is held)
Verdict: **safe for emergency calls, but it doesn't close #5.** AOSP LTC (scratchpad copy): `isActivityAllowed` (:418-430) is the BLOCK_ACTIVITY_START_IN_TASK check. It runs only with the BLOCK bit and has no emergency exemption. `isLockTaskModeViolationInternal` (:379-401) lets through, with KEYGUARD, the emergency dialer, `ACTION_CALL_EMERGENCY` and *any* start of `getSystemDialerPackage()` (:455-461, case 3).
- PIN lock, kiosk off: the features are fixed at `PIN_LOCK_FEATURES_KIOSK_OFF` = KEYGUARD|GLOBAL_ACTIONS|SYSTEM_INFO, never BLOCK (`LockTaskHelpers.kt` `lockTaskWhileLocked`). The block check doesn't run, and case 3 lets the unpinned system-dialer in-call UI start, so it shows and the call can be hung up. The emergency dialer stays pinned.
- PIN lock, kiosk on: the kiosk list is untouched (`pinLockHelpers` isn't used). `featuresWhileLocked` keeps the BLOCK bit when it's set. With the block on, `EnforcementPlan.kt:188` still pins `systemDialer` (step 9 fix intact). With the block off, case 3 applies. Both work.
- Normal kiosk (unlocked) with the block on: the system dialer is pinned (`:188`). OK.
- #5 residual: by case 3, kiosk off with KEYGUARD lets the system dialer's package start whether or not it's pinned. So unpinning it removes no reach. The "Add call → full dialer" path depends only on whether the system in-call UI shows (calls unmanaged, or the emergency UI). Keep #5 as a device check and in the privacy text. The commit message's rationale (that pinning was what let the dialer's full UI stay over the lock) is wrong, but the change is harmless.
