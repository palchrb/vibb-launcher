# QA step 10 design review: own PIN lock + call screens (10-lock-and-call-ui.md)

Reviewed 2026-10-05 against L/S `handy`. Claims checked in code; the AOSP facts in §1 were not re-checked. H = must fix before implementing, M = fix in step 10, L = fix or record.

## Findings
1. **H, §3/§4: with the kiosk off, the lock is only a re-front, and it can be beaten.** `setStatusBarDisabled` blocks the shade and quick settings, but not the Home/Recents nav buttons or gestures. From Recents the kid can pick any task (thumbnails show app content), use split screen, or long-press for the Assistant. Each escape gets 500 ms in the app, and after 3 re-fronts a minute the lock gives up. Override and pause are kiosk-off too, and the lock stays on during both. **Change:** while LOCKED, always run `PinLockActivity` in lock task. With the kiosk off: lock-task packages = ours + the emergency/dialer helpers (no third-party app), `startLockTask()` with features `KEYGUARD|GLOBAL_ACTIONS|SYSTEM_INFO`, and `stopLockTask()` on unlock. With the kiosk on, the kiosk list is never touched. `setStatusBarDisabled` then becomes a backstop only. Pure `lockTaskWhileLocked(kioskOn, …)` with a test.
2. **H, §2(c)/§3: the re-front cap fails open, and anything counts as "a system screen".** An allowlisted app that relaunches itself (alarm, camera gesture, full-screen intent, a messenger) wins after 3 tries. A rotation also fires `onStop` and uses up the budget. **Change:** skip re-front only for a named exempt set: our call task, the system dialer/emergency task, and Telecom. Every other front task is re-fronted at 0.5 s → 2 s → 5 s and the lock never stops. Only fights with exempt screens count toward the cap, and each is reported. Ignore `onStop` when `isChangingConfigurations` or when finishing after a correct PIN. Lock the screen to portrait. Entered digits and the backoff timer survive recreation.
3. **H, §5: the `BootClock` pattern has the wrong polarity for a backoff.** `timedWindowActive` (`RestrictionsPause.kt:28-39`) returns false (window over) on a new boot count, or as soon as either clock passes the end. Reused as is, a reboot or a forward clock jump ends the wait, the opposite of "reboot restarts the full wait". **Change:** add a pure `backoffRemainingMs(start, now…)` that keeps waiting while either clock says time remains. A different boot count restarts the full wait from now and persists the new start (`commit()`). Count the failure before running the PBKDF2 check and undo it on success, so a reboot or kill mid-check can't skip it. `PinBackoffTest`: reboot, clock ±1 day, and a kill mid-verify.
4. **H, §3: the LOCKED state can be true while no lock is on screen, and then time rules are switched off.** If the process dies and restarts while the kid is in an app (screen on), the state is LOCKED but nothing is shown until Home resumes or the screen goes off. In that gap, `LockActivity.start` and `TimeRulesRuntime.recheck` do nothing, so bedtime and the parent lock reason are lost. The screen receiver also lives only as long as `CommandListenerService` (`onDestroy` → `stopped`, `:138`). **Change:** never suppress the time-rule screens. Start them, then bring the PIN lock above them. On process start with LOCKED and the screen interactive, start the PIN lock at once. Register the screen-off/on receiver process-wide (from `Application`) whenever the lock is active.
5. **M, §6: the end of a call isn't handled while LOCKED.** (a) Re-front is off during a call, and when the call ends nothing re-shows the lock if another task got on top (a call answered from the lock, then Recents with the kiosk off). (b) A power-button screen-off during a call never locks, because the design treats every in-call screen-off as proximity. **Change:** when the last call ends and the state is LOCKED, explicitly start `PinLockActivity`. While a call is active, a screen-off when the proximity sensor (which `InCallActivity` already uses) reads "far" means LOCKED when the call ends. Add `PinLockStateTest` cases for both.
6. **M, §4/§10 Q1: the parent override can't be optional.** Without the "Foreldrekode" link, a forgotten kid PIN plus an unreachable server leaves only calls (no adb when `DEBUGGING_FEATURES` is set). **Change:** the link is mandatory: add it to the mock, nb + en. S refuses `new_kid_pin` while no override PIN is set. The link works during the kid PIN backoff (its own 5/15-min counter). PBKDF2 runs off the main thread; `LockActivity.kt:131` calls `verifyPin` synchronously today, so fix that too. Note: override PINs are ≥6 digits (`devices.rs:1317`) and kid PINs exactly 4, so the two can't collide. The S cross-check only matters if the kid PIN length is ever made configurable; keep it, but it guards nothing today.
7. **M, §1/§7: safe mode now skips every lock.** Before, the Android PIN covered a safe-mode boot. Now our app doesn't run in safe mode, and `DISALLOW_SAFE_BOOT` is off by default (`Hardening.kt:25-27`). **Change:** while the kid lock is active, the device page warns unless the safe-boot block is on, and the privacy text mentions it. [device] Record what safe mode shows on the Jelly Star.
8. **M, §6: the full-screen-intent backup is probably gone while LOCKED.** Dropping `NOTIFICATIONS` (lock task) and `setStatusBarDisabled` both disable notification alerts, which very likely includes full-screen intents. Incoming-call UI then rests on one `startActivity` (`KidInCallService.kt:129-133`), and a failure means a ringing call nobody can answer. **Change:** if the start fails while LOCKED, retry once after 300 ms and report `in_call_ui_failed` in the call state. [device] Check whether full-screen intents fire with the shade disabled. The 01-09 rule "an allowed call is always answerable" must be shown to hold with the lock on.
9. **M, §3/§4: with no keyguard, system "lock-screen" entries behave as unlocked.** Double-press power opens the full camera, not the secure camera. The power menu on the vendor skin may offer wallet, device controls or a Settings gear. The emergency dialer's "Emergency information" opens in edit mode. The Assistant is not in a locked state. **Change:** with finding 1, all of these must end on the lock. [device] Try each one, kiosk on and off. Anything that gets through goes in the privacy text or is blocked (for example, hide or suspend the Assistant app unless it is allowlisted).
10. **M, §3: overlays.** `DISALLOW_CREATE_WINDOWS` is set only when a budget is set (`EnforcementPlan.kt:205`), so an allowlisted app with `SYSTEM_ALERT_WINDOW` (chat heads) can draw over the lock. **Change:** also set it while LOCKED (fast DPM call, next to the lock-task features), or deny the `SYSTEM_ALERT_WINDOW` appop to third-party apps whenever the lock is active.
11. **M, §3/§10 Q4: alarms.** Covering the ring screen sets up the re-front fight from finding 2 every morning, and the kid has to type the PIN to silence it. **Change:** decide explicitly. Recommended: exempt only the ring activity of the clock package that handles `AlarmClock.ACTION_SET_ALARM`, from re-front while it is front, and bring the lock back when it closes. Otherwise state that the alarm keeps ringing until the PIN, and take a screenshot.
12. **L, §5/§8: kid PIN hash in the policy.** Brute-forcing 4 digits offline at PBKDF2 210k takes seconds on a GPU. That is acceptable for a privacy lock: anyone who can pull the CE prefs off a phone with no credential already has the photos. Conditions: the hash never goes into DE/`boot_call_policy`, logs, status or server pages; mdm prefs are excluded from backup and device transfer (`allowBackup="true"`, `AndroidManifest.xml:91` → add `dataExtractionRules`/`fullBackupContent` exclusions); the device page says the kid PIN isn't a secret against forensics and shouldn't be reused. 4 free tries plus a 15-min cap is about 100 tries a day, so about 50 days on average for one PIN. Record that as the accepted rate.
13. **L, §3: screen-time keyguard test.** "`ScreenTimeTracker.kt:70` keyguard test now always false" is wrong for unmigrated phones and the boot window. **Change:** count `keyguardLocked || pinLocked` and keep the existing test.
14. **L, §2(b): define the crash guard.** **Change:** persist an attempt count with `commit()` in `onCreate` before any work, and clear it after 30 s resumed. Only `PinLockActivity` crashes count, not re-fronts, config changes or process kills. After the guard trips, re-arm at the next sync at most once every 10 min (no 2-min crash cycles). Each trip is reported (`crash_guard`).
15. **L, §7: migration gap.** After the runbook removes the Android PIN, the phone has no lock at all until the next `apply`. **Change:** `MdmDeviceAdminReceiver.onPasswordChanged` (and an apply at boot) runs the lock check at once, and the runbook's last step checks that the lock appears.
16. **L, §6: call guarantees in the redesign.** Holds by design: the listeners are answer/hang up/speaker/mute only (`InCallActivity.kt:44-47`). **Change:** while LOCKED, no reject-with-message, contact sheet, keypad or photo tap-through. An unknown PSAP callback inside the emergency callback window rings and is answerable over the lock and shows the number. A hang-up always ends on the lock (finding 5).

## Acceptance criteria
- [local] `PinLockStateTest`: process start with the screen on → the lock is started; last call ended while LOCKED → lock re-started; power-off during a call (proximity far) → LOCKED; time-rule start while LOCKED → both started, PIN on top.
- [local] `PinBackoffTest`: a reboot restarts the full wait; clock +1 day / −1 day doesn't shorten it; failure counted before verify; a new hash resets it. A `RestrictionsPause`/`BootClock` test pins the inverted polarity.
- [local] `lockTaskWhileLocked` (kiosk off → ours + helpers only, KEYGUARD|GLOBAL_ACTIONS|SYSTEM_INFO; kiosk on → list unchanged); re-front policy (exempt set, never stops, config change ignored); crash guard; screen time `keyguardLocked || pinLocked`.
- [local] S `tests/step10.rs`: kid PIN refused without an override PIN; policy JSON has no kid hash in any DE/boot field; status has no unlock times; warnings for `crash_guard`, `android_credential` and safe boot allowed.
- [local] Merged-manifest test: `PinLockActivity` not direct-boot-aware (`DirectBootComponentsTest`), portrait, excluded from recents; backup rules exclude the mdm prefs.
- [device] Kiosk **off** and on, 20× each: Home, Recents, split screen, Assistant (long-press power/Home), double-press power camera, power menu entries, emergency dialer → Emergency info, an allowlisted chat-head overlay. All end on the lock, or are listed in the privacy text.
- [device] Allowlisted alarm and a full-screen-intent app firing while locked: the lock wins, or the agreed exemption is visible; no fight after 1 minute (logcat re-front count).
- [device] Incoming allowed call while locked, kiosk on and off: UI within 1 s 20/20. Full-screen intent with the shade disabled: record whether it fires. Answer → Recents (kiosk off) → hang up → lock. Power button mid-call → lock at call end.
- [device] `am crash`/kill of the process while the kid is in an app with a bedtime rule active → lock and then the bedtime screen appear without a screen-off.
- [device] 5 wrong PINs → reboot and `date` change (adb, debug build) don't shorten the wait; the parent code works during the backoff with the server unreachable (airplane mode).
- [device] Safe-mode boot with and without `DISALLOW_SAFE_BOOT`: record what is reachable. Runbook PIN removal → our lock is active within 5 s without a sync.
- [screenshot] Lock with the "Foreldrekode" link (nb + en, 320 dp); the backoff state; incoming PSAP-style unknown number over the lock; in-call while locked shows only speaker, mute and hang up; alarm decision (covered or exempt).
