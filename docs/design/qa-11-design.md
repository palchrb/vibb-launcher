# QA step 11 design review: kiosk escapes - update fence, notification auto-cancel (11-kiosk-escapes.md)

Reviewed 2026-10-06 against L `launcher/` (master, fbe6be25). Code claims checked; the AOSP facts in §1 were not re-checked. H = must fix in the design before implementing, M = fix in step 11, L = fix or record.

## Findings
1. **H, §2.3 "Never brick": the release isn't guaranteed, so the claim "the fence can't outlive a running new process" is false as written.** Release paths are Home/lock resumed *in lock task* (never with the kiosk off), a 2-min backstop armed only after `MY_PACKAGE_REPLACED`, install failure, and "process start with a fence > 10 min old". Gaps: reboot mid-install (old build restarts within 10 min, probably no result broadcast [needs device test]); kiosk off; `STATUS_PENDING_USER_ACTION` (`AppInstallReceiver.kt:48-54` only logs); SUCCESS in a process that was never killed (`isLauncher` is server data, the APK may be another package); unmanage/unenroll. In each case the other HOME packages stay suspended and the shade stays disabled indefinitely. A process death between `setPackagesSuspended` and the prefs write also leaves suspensions that nothing records. **Change:** write-ahead: commit the planned set + sessionId + our `lastUpdateTime` + boot count *before* suspending, and record only what the platform actually suspended (the request minus the failures it returns). Pure `fenceRelease(record, ourLastUpdateTime, sessionState, bootCount)`: release when our package was replaced since the fence, the session is gone/terminal, or the boot count changed. Run it at every process start, on every result broadcast (any status), at boot, in `apply()`, and from an AlarmManager backstop armed at fencing. Unmanaged/unenroll and a server switch `update_fence=false` release too.
2. **H, §2.1: the fence is a contract between two builds.** The old build writes the record and the new one must release it. A later build that renames the prefs or drops `UpdateFence` strands the fence forever on every phone that updated into it. **Change:** own prefs file with a `v` field. A test pins the file, keys and the v1 parse. A CLAUDE.md rule: release code is never removed. An unknown `v` still unsuspends the recorded packages.
3. **H, §1 row 1/§2 timeline: the kill isn't at `commit()`.** Commit is async (`AppInstaller.kt:89` returns at once). Verification and integrity checks run first, then the freeze and kill, so the kill comes seconds after commit. Commit is the point of no return: the screen-on cancel and the "no call" gate can't act after it. If the kid wakes the phone between commit and freeze, the PIN lock resumes in lock task in the **old** process. §2.3's "release once Home or the lock resumed in lock task" then releases the fence too early, and the full window follows. **Change:** state the timing. Never release from the committing process while its session is open (finding 1's rule). A2 logs commit → `Force stopping` → `MY_PACKAGE_REPLACED` → release.
4. **H, §2.1/§2.3: the status bar has one owner.** CLAUDE.md says `LockTaskChrome` is the only place that sets it, and it caches `appliedStatusBar` (`LockTaskChrome.kt:30,155-158`). After a failure before the kill (signature mismatch, downgrade, storage: the common failures), "release, then `LockTaskChrome.refresh`" sees cached false == wanted false and never re-enables the shade. With the PIN lock off, it stays disabled. In the new process, `PinLockRuntime.init`'s refresh (`PinLockRuntime.kt:127`) clears the fence's bar at once when unlocked. **Change:** the fence is an input to `lockTaskWhileLocked` (`statusBarDisabled = locked || fenced`) and goes only through LockTaskChrome; `UpdateFence` never calls `setStatusBarDisabled`. Add `LockTaskHelpersTest` cases.
5. **M, §2.1/§2.3: `apply()` and time rules vs the fence.** "Not in `controllablePackages`; `apply()` never would" holds only for system HOMEs with no launcher icon. A third-party HOME is always controllable. `apply()` (`AppEnforcer.kt:266-296`) unsuspends it mid-window if allowlisted. If a time-rule lock starts during the window (it suspends every controllable app), release unsuspends the launcher during bedtime. **Change:** `fencePlan` excludes `controllablePackages` (enforcement owns them; or release re-runs `apply`). Fence and release take `AppEnforcer`'s lock.
6. **M, §2(b): fence exclusions (the boot-loop class).** `fencePlan` must never include `android`, SystemUI, FLAG_PERSISTENT packages, the FallbackHome package (resolved, not "Settings"), our package incl. `.debug`, the dialers, Telecom, the emergency dialer, IMEs, `lockTaskHelpers`/`pinLockHelpers` or `PLAY_NEVER_RESTRICT`. Each exclusion gets a test row. A3 must pass on the Jelly Star (its own launcher package) before the server switch defaults the fence on.
7. **M, §2(b)/A3: the tail between our new process and release.** Home is ours again, but gesture Home/Recents still go through the suspended quickstep (RecentsActivity intercepted; with Settings hidden the admin-support dialog can't start). A swipe may hang or do nothing. **Change:** release as soon as Home or the lock is in front (lock task not required) or the screen is off. A3/A4 cover the tail in both nav modes, plus power-menu Emergency and `adb emu gsm call` with the fence up.
8. **M, §2(a): calls in the window.** The freeze also kills `KidCallScreeningService`, the redirection service and our InCallService. A call arriving after commit rings **unscreened** in the system in-call UI for about 1 min. **Change:** document the gap. The commit gate uses `OngoingCalls.hasLiveCall` + Telecom (not `isInCall` alone, see the fix round) + 2 min after an emergency call/ECBM. A2 variant: call from a blocked number mid-window.
9. **M, §2.3: Home vs lock order, failure path.** `bringHomeToFront` (`AppEnforcer.kt:544-555`, REORDER_TO_FRONT) can run after ProcessStart showed the lock, putting Home over the lock until the re-front loop fires (0.5 s). A failure after the kill restarts the old build via the result broadcast, and nothing brings Home back there. **Change:** start Home, *then* ask `PinLockRuntime` to show the lock if LOCKED. Do the same on the failure path.
10. **M, §2.2: the pending APK.** It sits in `cacheDir` (`MdmSyncWorker.kt:457`, OS-reclaimable) for hours. Clearing the attempt marker re-downloads it at the next sync (only installed/failed tags and `attemptStartedAt` are checked, `:414-433`). **Change:** keep it in `noBackupFilesDir` and check size + SHA-256 before fencing. Add a `pending` state to `TrackedAppUpdateState`: a newer tag replaces it, a withdrawn one drops it. Verify the package name is ours with `getPackageArchiveInfo` before fencing. Commit under `syncMutex`.
11. **H, §3: the generic rule would cancel life-safety alerts.** GMS is the main target, but it also posts Android Earthquake Alerts. The cell-broadcast package differs between AOSP and mainline (`com.android.cellbroadcastreceiver[.module]` vs `com.google.android.cellbroadcastreceiver`). **Change:** resolve the exemptions (the `SMS_CB_RECEIVED` receivers as in `HelperKind.CELL_BROADCAST`, emergency dialer, Telecom, system dialer, the SMS role holder while SMS is on, `alarmAppPackage`, IMEs). Never cancel a notification with a `fullScreenIntent`. "Allowlisted" = the effective allowed set (allowlist ∪ messaging apps ∪ time-rule usable apps). B1 lists GMS's channels and classifies each one. Add a server switch, default on only after B5.
12. **M, §3: re-post loops.** Each cancel fires the app's `deleteIntent`, and GMS may re-post at once. **Change:** a per (package, channel) budget, e.g. 3/min. Past it, `snoozeNotification(key, 1 h)` (no delete intent) and report. Nothing is cancelled while the policy is unknown. Decisions come from a cache, with no PackageManager work on the main thread.
13. **M, §3: privacy.** The listener receives whole notifications, text included. **Change:** the pure input carries only package, `Notification.channelId` (never the Ranking's conversation channel or shortcut id, which can encode a contact), category, flags and "has FSI". Never log `sbn.key`/tag (tags can hold thread ids). Status counts are capped (≤ 20 entries, ids ≤ 64 chars) and S sanitizes them like `sanitize_lock_state`. The privacy text names the listener.
14. **L, §2.4: adb installs.** Unfenced is fine: adb is gone on managed phones by default. emulator.md says so. A dev `adb install -r` must also release a stale fence, which finding 1's `lastUpdateTime` rule does (debug versionCodes don't change). A4, not A2, exercises the real path.

## Acceptance criteria
- [local] `UpdateFenceTest`: `fencePlan` excludes every package in finding 6, controllable and already-suspended ones; only actually-suspended packages are recorded; the record is written before suspending.
- [local] `fenceRelease` table: replaced, session gone/failed/pending-user-action, other boot, success without replacement → release; old process with the session open → keep; v1 record and an unknown `v` → release.
- [local] `LockTaskHelpersTest`: status bar = locked || fenced; release after a pre-kill failure re-enables the bar despite the cache.
- [local] Commit gate: screen off ≥ 30 s, no live call (incl. CONNECTING), no emergency exemption; pending-APK state machine (newer tag, withdrawn, hash mismatch).
- [local] `nagToCancel` table: own/`.debug`, allowlisted/effective set, AOSP and Google cell-broadcast names, FSI, CALL/MISSED_CALL/ALARM/STOPWATCH, ongoing, unmanaged, policy unknown, budget → snooze. The input type has no text fields. S tests: `update_fence` and the counts are sanitized and capped.
- [device] A2 + timing (finding 3); wake between commit and freeze → no early release; `adb reboot` mid-install → fence released at boot, kiosk on and off.
- [device] Signature-mismatch APK → packages unsuspended **and** shade back with the PIN lock off; time-rule boundary inside the window → launcher stays suspended until apply decides.
- [device] A3/A4 tail in both nav modes on Pixel and Jelly Star; power-menu Emergency and an incoming call (allowed and blocked) mid-window.
- [device] B5 plus: a cell-broadcast test alert and the earthquake-alert demo stay, and a re-posting nag ends snoozed. Since `cmd notification post` posts as shell with no category, use a real missed call and a clock alarm for the "stays" checks.
