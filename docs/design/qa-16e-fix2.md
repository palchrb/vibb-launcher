# QA 16e fix 2 - 511bc2cb (2026-10-09)

Status: all findings fixed in the commit after `511bc2cb` (each marked below).

`BootMarkPlanTest` passes (10 tests); `bash -n smoke-test.sh` passes. Not device-tested. Paths are under `launcher/app/src/main/java/com/kidslauncher/mdm/`.
1. **High: the frame wait holds the lock while neither the mark nor the lock is on screen.** `Waiting` (`lock/BootMarkPlan.kt:143,161`) starts at Home's locked resume (`ui/HomeActivity.kt:410-411`), but on the emulator Home first drew 1.8 s later. Home's theme sets `windowDisablePreview`, and `BootHome` starts Home from our uid, so no starting window covers that gap. The previous top's last frame (the stock launcher or FallbackHome) stays up for up to 3 s. Before 16e the lock's navy starting window (`PinLockTheme`) came at once. On API 34, WM probably gives touches to no window of an activity that isn't visible-requested, but nothing here proves it. A Home that was never focused also can't report covers that don't pause it (the assistant or the power menu, kiosk off): `onWindowFocusChanged(false)` comes only after a gain. Home's late frame then holds 3 s more under them, up to ~6 s after the ask (before: 3 s). This reopens qa-16e-code #1 and #2. The literal rule "show the lock while Home hasn't drawn" would kill the mark on every boot, because Home's resume always asks before its first frame. Fix: count the mark as up only from Home's first `onWindowFocusChanged(true)` after its locked resume (on API 34, focus goes only to a drawn, shown layer), and start the 3 s there (or at the cover's frame) instead of at the `OnDrawListener` (`ui/home/NightGround.kt:41`, which runs before the frame reaches the screen and before Home's fade-in). Bound the wait for it by the pre-16e `LOCK_FALLBACK_MS` (1 s from the wait's start), not `BOOT_MARK_MS`: no focus by then means the lock. Worst case is then 1 s of the old front plus 3 s of the mark, and a slow emulator safely shows no mark.
   **Fixed:** the mark counts as shown only from Home's first `onWindowFocusChanged(true)` after its locked resume with the night ground drawn (pure `homeMarkShown`; `PinLockRuntime.onHomeMarkShown` from the focus gain, the ground's first frame and the locked resume), the 3 s start there or at the cover's frame (`bootMarkShown`), and `Waiting` lasts at most `LOCK_FALLBACK_MS` (1 s) from the wait's start: no focus by then means the lock (`Home's mark never shown`). The `OnDrawListener` only sets `NightGround.drawn`.
2. **Low: the 300 ms pause grace (`lock/PinLockRuntime.kt:110,233`).** Once Home has focus, a real cover still ends the wait at once. A focusable window over Home takes its focus (`ui/HomeActivity.kt:522`), and a non-focusable top activity leaves focus null, which also counts as a loss. The re-delivered HOME intent pauses Home only on the client side and doesn't move focus. So the grace adds a blind spot only before the first focus: a translucent activity or Recents over Home goes unseen for 300 ms. #1's focus rule closes that. If the emulator still logs `Home paused` after the system's HOME start, log the gap from the pause to the resume before raising the grace.
   **Fixed (documented):** kept the 300 ms grace; the blind spot is described at `HOME_PAUSE_GRACE_MS`, in the 16e status and in `launcher/CLAUDE.md` - before the first focus it is bounded by the 1 s `Waiting` deadline.
3. **OK: the backstop.** Entering `Waiting` or `Holding` (re)posts it, every end removes it, and every end goes through `endBootMark` (SHOW/RECHECK). The lock always comes, at the frame deadline or at frame + 3 s. The bound from the first held ask, though, is ~6 s, not the 3 s the design text implies ("never later than before 16e"). With #1 it becomes 4 s. Pin that bound end to end in a test.
   **Fixed:** with #1 the bound is 1 s + 3 s; `BootMarkPlanTest` "the lock comes at most 1 s + 3 s after the wait began - end to end" walks every path (clock or first ask, cover or not, shown at any time or never, asks every 100 ms, the backstop) and pins it, plus the exact 3 s from the focus and the 1 s fallback without one.

Fix: FAIL below 2500 ms only for `Home paused`/`Home stopped`/`Home lost focus` when no UI dump caught another window (if one did, the "nothing but the mark" check reports it). SKIP, with the reason, on `never drew`, the exemptions, `AT_ONCE` asks and `the lock is up`. Also, N counts from `onDraw`, before composition and before Home's fade-in. It overstates, so it can PASS a mark that was really up for less than 2.5 s. #1's focus timestamp fixes this.
   **Fixed:** the end's reason comes from the pure `bootMarkOverWhy`; the smoke check FAILs only `Home paused`/`Home stopped`/`Home lost focus`/`Home's mark not up` below 2500 ms when no UI dump caught another window (and a `the mark's 3 s are up` below 2500 ms, a bug), and SKIPs with the reason on never shown, no wait, exemptions, `AT_ONCE` asks and `the lock is up`. N counts from the focus timestamp now.
