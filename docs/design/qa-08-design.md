# QA: design 08 (UI polish) - review before implementation

Scope: `08-ui-polish.md` against 01-07 and code on `handy` (L = kids-launcher-mdm, S = kid-phone-server). Verified OK: QuickControls rows use DO APIs only (`QuickControls.kt`, no `Settings.ACTION_*`/`Panel` in `ui/quickcontrols/*`); app long-press menu is hide/rename only (`ContextMenuActions.kt:104-137`, no app info); LockActivity is started over any of our activities (`TimeRulesRuntime.kt:204`, `MdmSyncWorker.kt:171`, Home pref listener); mask path S→DTO is correct (`devices.rs:1215-1224`, `device_api.rs:226`, `PolicyResponse.kt:58`, SnakeCase); `DISALLOW_SET_WALLPAPER` owner exemption matches AOSP; Nunito 3.602 name table: OFL 1.1, copyright line has no Reserved Font Name.

## Findings

1. **High - §3 Apply (privacy).** `setBitmap(..., FLAG_SYSTEM or FLAG_LOCK)` puts a parent-uploaded photo on the keyguard, which kiosk always enables (`LOCK_FEATURE_KEYGUARD`, `devices.rs:202`): anyone holding the locked phone sees it. The system also keeps its own copy under `/data/system/users/0/` (not our CE dir; may be included in the system wallpaper backup), contradicting "nothing to DE". Required: images go to `FLAG_SYSTEM` only; `FLAG_LOCK` gets a colour/gradient (picked built-in, or navy) unless the parent ticks "also on lock screen" per image (default off). The upload page says that the image is stored on the phone and shown to the child. Document the system copy in §3.
2. **High - §3 Removal.** Nothing says what happens to a private photo once the parent un-assigns or deletes it, or unmanages the phone. `WallpaperCache.sync` must delete files that are no longer allowed, and when the removed hash is the applied system wallpaper, re-apply the fallback right away in the sync path (not only on Home `onResume`). On unmanage: re-apply navy (or `WallpaperManager.clear()`) before the restriction is lifted. S: deleting a wallpaper cascades `device_wallpapers`; uploads start assigned to no device.
3. **High - §3 Upload shape.** (a) `process()` shrinks before `apply_orientation` (`photos.rs:132-140`); that only works because a centred square looks the same in every orientation. For `Portrait` the fit box must use the oriented size (swap w/h for EXIF 5-8), otherwise a phone-camera portrait (EXIF 6) comes out at 810×1080. (b) "Fit in 1080×2400, no crop" turns a landscape photo into 1080×810, which the phone centre-crops and upscales about 3×. Required: crop to the screen aspect (9:20, centred) on S, or cover-fit so the short side is ≥ 1080 px and the long side ≤ 2400 px. Add tests: an EXIF-6 portrait and a landscape photo give upright output with the expected size.
4. **Medium - §3 Apply loop/perf.** "Re-apply if the id changed" plus a silent refusal (`setBitmap` returns 0 when it is disallowed or unsupported, and doesn't throw) or an unmanaged phone (restriction cleared, so the parent sets their own wallpaper) means a 1080×2400 PNG encode on every Home resume (seconds of work on a slow phone) and a fight with the parent. Required: apply only while managed. Store the id that `setBitmap` returns, and treat 0 as failure, retrying once per key per day with the result logged. Check `isWallpaperSupported`/`isSetWallpaperAllowed` first. Never run this on the main thread or on every resume.
5. **Medium - §1 Icons on the main thread.** `roundAppIcon` (load + render) is called from `onBindViewHolder` (`HomeGridAdapter.kt:81-83`), not from `refreshApps`. Required: build the finished bitmaps (monochrome/full/legacy plus palette seed) in the `refreshApps` `Dispatchers.Default` block and pass a key→bitmap map to the adapter. `onBind` only reads the map and shows a `tileColor` placeholder circle when an icon is missing. `mutate()` the monochrome drawable before `setTint` (it is shared). The cache key includes size and density.
6. **Medium - §3 Bitmaps on a small phone.** The Home theme already shows the system wallpaper (`styles.xml:96-101`, `windowShowWallpaper=true`). Drawing our own bitmap on top means two full-screen bitmaps (about 10 MB each in ARGB_8888) plus one more per screen if each activity decodes its own. Required: choose one approach: Home either goes transparent over the system wallpaper once it is applied, or sets `windowShowWallpaper=false`. Keep one process-wide decoded bitmap (RGB_565, `inSampleSize` for the window size) decoded off the main thread, with a bounds check and `Throwable` caught as in `ContactPhotos.decode` (`ContactPhotos.kt:87-101`), and reject anything over 1080×2400 (or 2400 px on the long side). Compute `WallpaperInk` once per hash and cache it.
7. **Medium - §3 Legibility.** `scrimAlpha` only covers white ink. Dark ink on a light photo needs a white scrim checked against `lum - sd`. The 0.45 cap can't reach 4.5:1 for white text on a bright photo (white needs a background luminance ≤ 0.18; at lum 0.9 that takes alpha ≥ 0.8). Required: a symmetric formula. When the cap can't reach 4.5:1, fall back to a label shadow or pill behind the label. Average luminance in linear light. For gradients, use the worst stop for the chosen ink (max for white, min for dark). Tests: a mid-grey photo with high std-dev, and white/dark ink on #F4F1EA.
8. **Medium - §3 S storage.** The wallpaper store and prune need the same discipline as `photos::FILES` (`photos.rs:189-217`): the lock, a scan of `data/wallpapers/` only, `.tmp` files skipped. Required: a distinct backup zip prefix (`wallpapers/<hash>.jpg`), the `recover_missing` equivalent at startup, and a route that copies `contact_photo` (`device_api.rs:989-1012`) with a join on `device_wallpapers`. Tests: a device gets 404 for another device's image, and pruning one directory never touches the other.
9. **Medium - §2 Mask diagnosis.** The diagnosis is sound but incomplete. Two more causes: (e) `FreshDecode.Failed` (`PolicyGate.kt:46-60`) keeps the old cache (the device page shows `fresh_decode_failed`); (f) on the emulator the installed debug package is not the device owner (case a). Required: record the actual cause found on the emulator in the design before closing the issue. `NoPolicyYet` also covers running on `LastEnforcedPlan`, and each state has its own nb/en text.
10. **Medium - §2/§3 Escape guard.** KidSettings must not gain any system surface. Required: a JVM/lint test that fails if `ui/kidsettings`, `ui/quickcontrols` or `WallpaperApplier` reference `Settings.ACTION_`, `Settings.Panel`, `ACTION_SET_WALLPAPER`, `getCropAndSetWallpaperIntent`, `ACTION_APPLICATION_DETAILS_SETTINGS` or `Intent.createChooser`. The picker is our own grid only. The Settings tile has no long-press (`GridTile.App` only, keep it that way).
11. **Low - §3 Hardening.** "`value()` → null ... like the others" is inaccurate: every other restriction has a server switch (`Hardening.kt:46-56`). Fine as a launcher-only restriction, but say so explicitly. `AppEnforcer` maps it to `UserManager.DISALLOW_SET_WALLPAPER`, and it is cleared when unmanaged (after finding 2's reset).
12. **Low - §1 Font provenance.** The source is a copy in a session scratchpad (ephemeral). Required: pin the googlefonts/nunito tag v3.602 URL and the TTF SHA-256 in the doc, commit the `varLib.instancer` command under `scripts/`, keep the name "Nunito" (no RFN), and check that æ/ø/å render.
13. **Low - §2 Accessibility.** The 44 dp back button is below 48 dp: make the touch target 48 dp. Wallpaper tiles need a contentDescription with label and "selected" state (not border alone). Switch rows get a label for TalkBack. Checked: `tileColor` grey #868E96 against white is 3.3:1, OK for a glyph.
14. **Low - §1/§4 Phone-book tile and locks.** The tile rule is sound (only widens), and the screenshot diagnosis is a hypothesis until the uiautomator check runs. KidSettings, Wifi and Bluetooth screens are only reached from Home after its lock redirect, and LockActivity is started from background paths. Still test a bedtime boundary with KidSettings and the Wi-Fi subscreen open. Captive-portal and BT-pairing system dialogs are pre-existing, not new.

## Acceptance criteria

- [local] Tests: `HomeModelTest` (tile rule, Settings last, `gridMetrics`, `contactRow`, `tileColor` ≥ 3:1), symmetric `scrimAlpha` cases (#7), `effectiveWallpaper`, `wallpaperApplyPlan` (managed only, id 0 = failure with backoff), `HardeningTest` SET_WALLPAPER set while managed and cleared when unmanaged, DTO without `wallpapers` decodes, escape-guard test (#10).
- [local] S tests: EXIF-6 portrait and landscape uploads are upright at the expected size (#3); oversize or wrong type → 400; route 404 for an image not assigned to this device; prune of wallpapers vs photos is isolated; backup has `wallpapers/` and recovery restores it; deleting a wallpaper cascades.
- [local] Snapshot: the policy key test includes `launcher_ui.wallpapers`; `OFL.txt` is in assets and listed in LegalInfo; font SHA-256 recorded.
- [device] Jelly Star: our `setBitmap` succeeds with DISALLOW_SET_WALLPAPER set (returns id ≠ 0); Photos "set as wallpaper" is blocked; the lock screen shows a colour (not the photo) by default; un-assigning the applied photo replaces the system wallpaper within one sync; unmanage resets to navy, then lifts the restriction.
- [device] Mask root cause recorded (prefs grep + device page `policy_state`); toggling the mask on S updates an open KidSettings without reopening it.
- [device] Bedtime boundary while KidSettings or the Wi-Fi subscreen is open → LockActivity in front, Home press stays locked, 112 works. No Android Settings screen is reachable from any KidSettings control (tap every row, long-press every tile).
- [device] Slow phone: Home cold start with 20 apps has no frame > 32 ms from icon work (`adb shell dumpsys gfxinfo`); heap with an image wallpaper less than 15 MB above the colour-wallpaper baseline.
- [screenshot] §6 items 1-9 nb/en, plus: bright photo and mid-grey busy photo with legible labels (4.5:1 sampled under labels); dark-ink wallpaper with dark status-bar icons; TalkBack reads the selected wallpaper.
