# QA/security code review - step 9 part B (S d6b4e3f, 1f4388e; L ab06b2a, 06d655d, e783f8e, 06ab4b5)

Severity: P0 = emergency or fail-open, P1 = fix before the device test, P2 = fix or document, P3 = nit. AOSP refs are the copies in the session scratchpad (LTC = LockTaskController, ASI = ActivityStartInterceptor). Tests: S `cargo test` 150 passed; L `testDebugUnitTest` green.

## Findings
1. **P0 - the system dialer's in-call UI is blocked in kiosk.** `EnforcementPlan.kt:179,184`, `AppEnforcer.kt:608`. Before step 9, LTC:467-472 let any start of the system-dialer package through in kiosk, because KEYGUARD is always set. The BLOCK bit is checked first (ASI:364-374 → LTC:419-431: lock-task packages only, no emergency exemption), and the dialer isn't pinned when calls are managed, when calls are unmanaged and it isn't allowlisted, or during a no-calls rule lock. In those cases its InCallActivity becomes BlockedAppActivity. Effects: 112 from LockActivity, the 112 tile or the keyguard connects, but the kid can't see the call or hang up. On unmanaged phones incoming calls can't be answered in kiosk. [inferred] When calls are managed, Telecom moves emergency calls to the system dialer's UI (02-calls.md:139), which is blocked too. QA 09 #3 assumed the dialer was unreachable before, but LTC case 3 already allowed it, so pinning it adds no exposure. **Fix:** with `blockActivityStart`, pin `systemDialer` (drop `- setOfNotNull(systemDialer)` at :184 and the forbidden entry at AppEnforcer:608). Flip the assertions in `LockTaskHelpersTest:41,86`. Extend device check D1 to the in-call screen and an incoming call in kiosk, with calls both managed and unmanaged.
2. **P0 - the emergency-dialer fallback can open a forbidden package.** `EmergencyDialer.kt:30-38`, `AppEnforcer.kt:593`. `resolve()` takes the first *system* handler of `DIAL_EMERGENCY`. [inferred] When `config_emergency_dialer_package` is the system dialer (Google Dialer phones), that handler is the system dialer. `lockTaskHelpers` then removes it as forbidden, so `open()` lands on BlockedAppActivity. `open()` still returns true, because an intercepted start doesn't throw, so no other path is tried. **Fix:** #1 covers this. Otherwise, pin whatever `resolve()` returns, or skip handlers in `forbidden`. Add a test where the dialer handles `DIAL_EMERGENCY`.
3. **P1 - Home is pulled to the front on every apply while a role change keeps failing, including during a call.** `AppEnforcer.kt:504` checks `action != NONE`, not whether the role actually changed. A TAKE that throws (OEM refusal, the case HomeActivity's daily role prompt exists for) or a failing RELEASE repeats on every apply (sync, push, recheck). Each time it takes the kid out of the allowed app and hides the parent's role prompt. A parent toggling calls during a call (an emergency call too) puts Home over the in-call screen. This is not an endless loop: Home's onResume re-applies only when the lock key changes (`MdmSyncWorker.kt:651`). **Fix:** bring Home forward only if `dialerRoleHeld` changed in this pass and `TelecomManager.isInCall` is false.
4. **P2 - permissions are over-granted after the hand-back.** `AppEnforcer.kt:475`. On RELEASE (calls unmanaged), CALL_PHONE, READ_CALL_LOG, READ_CONTACTS, READ_PHONE_STATE, CAMERA and POST_NOTIFICATIONS become policy-fixed for good. After that the user can't revoke them, and `canReadCallLog` is true again, so B3's "no call-log reads while unmanaged" holds only on phones that were never managed. **Fix:** once RELEASE has succeeded and the role isn't held, set those permissions back to `PERMISSION_GRANT_STATE_DEFAULT`. That clears POLICY_FIXED without revoking, so nothing is killed. Add a pure test.
5. **P2 - the "open with" dialog isn't pinned.** The helpers pin `ACTION_CHOOSER` (intentresolver). The disambiguation screen for an implicit intent with 2+ handlers and no default is ResolverActivity in package `android`, which B4 listed but the code dropped, so it ends on BlockedAppActivity [inferred]. **Fix:** resolve an ambiguous VIEW intent (`resolveActivity` returns the resolver) and pin that package. Add it to D2.
6. **P2 - helper resolution is fragile.** `AppEnforcer.kt:573` `activity()` takes `firstOrNull`. If the first system match is a forbidden package (for example the dialer or camera for `ACTION_CALL`), the real helper (Telecom) is dropped silently [inferred]. **Fix:** take the first match that isn't forbidden, and log or report the resolved helper set so device checks can see it.
7. **P2 - the kill switch default is wrong for an older server.** `PolicyResponse.kt:74`, `PolicyGate.kt:126`. `blockActivityStart` defaults to `true`, so a launcher updated before the server (no migration 0029) turns the block on with no off switch (QA 09 #4). **Fix:** default `false`; our server always sends the key.
8. **P2 - the Element X URI isn't encoded.** `MessageButtons.kt:39,56` put the mxid into `matrix:u/...?action=chat` and `element://user/...` raw. `isMatrixId` and S `valid_matrix_id` (`calls.rs:573`) accept `/?#&%`. A legal localpart with `/` breaks the URI, and a parent-typed `@a:b?action=join&via=x` changes the action. Only the parent can enter the value and the package is explicit, so the kid can't inject anything. **Fix:** validate against the Matrix grammar on both sides (localpart `[a-z0-9._=\-/+]`, server `host[:port]`) and `Uri.encode` the id segment. Add tests with `/`, `?` and `#`.
9. **P3 - auto-refresh loses parent input.** `device_calls.html:5` reloads every 5 s for up to 2 minutes. That includes the 400 page from add/update-contact errors (`calls.rs` `render`), so the error message and the typed contact are lost. **Fix:** set no `auto_refresh` on error renders, or refresh only the warnings.
10. **P3 - small issues.** `signalRoleChange` (`AppEnforcer.kt:214`) also runs inside a sync, so each in-sync TAKE/RELEASE queues one redundant sync. `BootCallPolicy.kt:207-215` now has `callLogForWindow`'s old KDoc stacked above `canReadCallLog`'s. `ContactSheet.openMessage` catches only `ActivityNotFoundException` (a SecurityException crashes it).

## Verified OK
- **Pending rule fails closed:** "waiting" only while the report predates the change and the change is under 5 minutes old. A newer disagreeing report is always a warning. Both times use the server clock.
- **Block bit:** masked out of `lock_task_features` on both sides.
- **Own-permission fix:** decided on the DPM grant state. It runs before TAKE and RELEASE and on every managed apply. No kill path from our own code.
- **Keyguard bits:** ORed in, and only our bit is cleared.
- **B3:** gated on READ_CALL_LOG plus `isUserUnlocked`. No stale flag.
- **Pinned in our own package:** our in-call screen, the link blocker, LockActivity and the PIN exit all live there, and the offline override exits kiosk, so the block adds no parent lockout.
- **Emergency paths:** LockActivity and the PhoneBook 112 tile never use `ACTION_DIAL`.
